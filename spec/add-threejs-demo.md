# 記事へのThree.jsデモ掲載（add-threejs-demo）

記事に、素の Three.js で実装したデモを掲載するスキル。CG記事（`/cg/**`）では、あわせてそのデモで実際に動いているコードも掲載する。色彩記事（`/color-theory/**`・`/color-fields/**`）ではデモだけを置き、コードは載せない（→「色彩記事への適用」）。引数で記事 slug を受け取り、記事を解析してデモ案を提案し、合意された案を実装して記事に差し込む。

## 目的・背景

- CG記事に載せるデモの狙いは 2 つある。
  - **内容の理解を助ける** — 静的な図解では伝わりにくい、空間・変換・投影などを操作しながら確かめられるようにする。
  - **実際の応用例を示し、読者の創作への橋渡しとなる** — 記事の理論が実際のコードでどう書かれるかを見せ、読者が自分の制作に持ち帰れるようにする。
- 後者のため、デモとあわせて**そのデモで実際に動いているコード**を記事に掲載する。掲載コードが「一度も実行されていないコード」になることを避けるのが、この仕様全体で最も重視した点。
- 既存の図解は SVG（`svg-diagram-component`）で作られており、静的な図では表現できない題材を扱う手段が無かった。
- **色彩記事では 1 つ目の狙いだけを取る。** 読者に持ち帰ってもらうのは色の理論であって Three.js の書き方ではないため、コードは掲載しない（2026-08-09 に適用範囲を拡張。→「色彩記事への適用」）。

## スコープ

### やること

- CG記事（`app/src/routes/cg/**/+page.svx`）を対象とした、Three.js デモの実装とコードの掲載。
- 色彩記事（`app/src/routes/color-theory/*/+page.svx`・`app/src/routes/color-fields/*/+page.svx`）を対象とした、Three.js デモの実装（コードの掲載は行わない）。
- 記事へのデモの差し込み（import・デモ直前の `:::Action`・コンポーネント使用箇所・コードブロック〈CG記事のみ〉・フロントマターの `visual: true`）。
- 記事に残っている `:::Todo` の実装（デモ案の提案を飛ばし、ブロックを差し込みで置き換える）。
- `:::Todo` が無い記事でのデモ案の提案とユーザーによる採否の合意。
- 記事に載らない定型処理を担う共通モジュール（`_shared`）の整備。

### やらないこと

- **記事本文の執筆**。本文は `author-style-writer` の担当で、**このスキルは執筆完了後に呼ばれる**。デモの説明文や、地の文からデモへの言及は書かない（デモの直前に置く `:::Action` だけは例外としてこのスキルが書く）。
- **色彩記事への Three.js コードの掲載**（→「色彩記事への適用」）。
- **既存の Threlte 製 3D デモ（`PCCSColorSolid3D.svelte`・`MunsellColorSolid3D.svelte`）の移植**。Threlte 実装のまま据え置く。
- 「Web」タグの新設。**既存の `図解` タグ（`visual: true`）で代替する**。
- 掲載コードと `scene.ts` の逐語一致、およびそれを検証する自動テスト。
- アクセシビリティへの特別な配慮（Tweakpane を素直に使う）。
- 自動で動き続けるアニメーション（操作したときだけ動かす）。

## ユーザーストーリー・主要ユースケース

- 著者が `author-style-writer` でCG記事を書き上げ、デモが欲しい箇所に `:::Todo` を置いた状態で `/add-threejs-demo <記事slug>` を実行し、`:::Todo` の内容がそのまま実装されてブロックが置き換わる。懸念があるときだけ代替案が示される。
- `:::Todo` を置かずに書き上げた記事で `/add-threejs-demo <記事slug>` を実行し、提案されたデモ案から載せたいものを選んで実装させる。
- 著者に載せたいデモの構想がある場合は、提案フェーズを飛ばして `/add-threejs-demo <記事slug> <デモの内容>` で直接指定する。
- 読者は記事を読みながらデモを操作して理解を確かめ、直後に掲載されたコードを自分の制作に持ち帰る。

## 機能要件

### 引数

```
/add-threejs-demo <記事slug> [<デモの内容>]
```

- **`<記事slug>`（必須）** — 記事の slug（例: `basic-transformations`・`pccs-color-system`）。`app/src/routes/cg/`・`app/src/routes/color-theory/`・`app/src/routes/color-fields/` を検索して実体を解決する。
  - **0 件・複数ヒットの場合は確認して止める**（`svg-diagram-component` と同じ流儀）。CG記事と色彩記事の両方に当たった場合も同じ。
  - slug が重複する場合のみ、ユニット込みで `transformation/basic-transformations` のように渡す。
- **`<デモの内容>`（省略可）** — 作りたいデモの内容。指定の有無で動作パターンが分かれる。

### 動作パターン

`<デモの内容>` の有無と、記事に `:::Todo` が残っているかで分かれる。

- **パターンA-1（`<デモの内容>` なし ＋ 記事に `:::Todo` あり）** — デモ案を提案せず、`:::Todo` の本文をデモの内容の指定として読み、そのまま実装する。挿入位置は `:::Todo` の位置（改めて合意しない）。
- **パターンA-2（`<デモの内容>` なし ＋ `:::Todo` なし）** — 記事を解析してデモ案を提案し、ユーザーの採否を待ってから実装する。
- **パターンB（`<デモの内容>` あり）** — 提案フェーズを飛ばし、指定された内容のデモを実装する。`:::Todo` があっても引数の指定が優先。

### `:::Todo` の扱い（パターンA-1）

- **`:::Todo` はデモの依頼として扱う。** 記事に書き溜められたプレースホルダがすでに「何が欲しいか」の指定になっているため、そこへ案の表を重ねるのは二度手間になる。
- **`:::Todo` ブロックは、デモの差し込み（`:::Action` ＋ `<CanvasWrapper>`、CG記事はさらにコードブロック）で丸ごと置き換える。** `TODO` の文字列を記事に残さない（`svg-diagram-component` のパターンCと同じ）。
- **静的な2次元の図で足りると判断した `:::Todo` も、`svg-diagram-component` へ回して打ち切らない。** その判断を伝えたうえで、**3D・操作にするなら何を見せられるか**を代替案として示し、指示を待つ（→「懸念・代替案」）。勝手にデモ化もしない。色彩記事ではこの場面が増える。
- **`:::Todo` が複数あるときは出現順に 1 本ずつ**（→「実装の粒度」）。着手前に、拾った `:::Todo`・担当・実装順の一覧だけを示す（案の表は作らない）。
- **`:::Add` / `:::Delete` / `:::Fix` / `:::Pending` は依頼として拾わない。** 文章の加筆メモ・削除予定・採否検討中の文章・既存のものへの修正指示であり、新規デモの依頼ではない。

#### 懸念・代替案

- **`:::Todo` 通りに実装することへの懸念、またはより良い見せ方があるときは、実装前に「`:::Todo` 通りの案」と「代替案」を対比で示し、指示を待つ。** 指定どおりに作ることを、読み取れないデモを作る理由にしないため。
- 懸念の例: 静的な2次元の図で足りる／操作が記事の主題から外れる／1 デモに詰め込みすぎ（分割の代替案）／色の見えが歪む／掲載コードが主題から離れる。
- **「静的な2次元の図で足りる」ときの対比は、「静的な図で足りるという判断（＝`svg-diagram-component` の担当）」と「3D・操作にするなら何を見せられるか」の 2 案。** 3D にすると何が増えるか（回して見える奥行き、動かして変わる量）を具体的に書き、静的な図を選ぶ判断材料にする。`svg-diagram-component` の案内だけで止まってよいのは、3D にしても足せるものが本当に無いときだけ。
- **静的な図で進めると決まった `:::Todo` は消さずに残す**（デモを実装しないので置き換えるものが無い）。`/svg-diagram-component <図の名前>` をコピペできる形で案内する。
- **代替案は懸念があるときだけ。** 無ければそのまま実装する。提案フェーズを取り戻すために代替案をひねり出さない。示すのは 2 案の対比だけで、パターンA-2 の表には戻さない。
- **`:::Todo` 通りで進める指示が出たら、そのまま実装する**（懸念を蒸し返さない）。
- **`:::Todo` の中身が引数で渡された場合（パターンB）も同じ。** 指定の届き方で判断を変えない。

### デモ案の提案フォーマット（パターンA-2）

会話上に表で案を列挙し、番号で採否をもらう。`AskUserQuestion` は選択肢が 2〜4 個に固定されるため、件数が可変なこの用途には使わない。

表の列は次のとおり。

| 列 | 内容 |
| --- | --- |
| `#` | 案番号 |
| 視点 | 理解 / 応用 |
| 何を見せるか | デモで見えるもの |
| 操作 | Tweakpane で操作するパラメータ（操作なしも可） |
| 記事に載るコード | `scene.ts` から載せる部分の見込み |
| 挿入位置 | どの節の直後に入れるか |
| この案の弱み | 不採用の理由になりうる限界 |

- **件数は記事次第**。「1 つの視点に 1 デモ」に縛らない。片方の視点が 0 案でもよい。
- 「**この記事に Three.js デモは向かない**」と申告して止まることも許す（例: 知的財産権・CGの歴史）。
- 提示は 5 案程度を上限とする。
- **各案に必ず「弱み」を書く**。AI が自分の案を売り込むだけになるのを防ぐため。
- **挿入位置まで案に含める**ので、採否の合意と同時に挿入位置も合意される。
- ユーザーは番号で `1と3` のように返す（実装順の指定も可）。

### 実装の粒度

- 採用された案を**1 つずつ実装して都度報告**する。複数案が採用されても一度にまとめて実装しない。

### 記事への反映

デモ 1 本ごとに、対象記事へ次を行う。

1. `<script>` ブロックにデモコンポーネントの import を追加する（`CanvasWrapper` が未 import であればあわせて追加）。
2. 合意した挿入位置に `<CanvasWrapper><Demo /></CanvasWrapper>` を差し込み、**その直前に `:::Action`** を置く。どのパラメータを動かすと何が起きるか・どこに着目すれば記事の主題が読み取れるかを対で書き、casual な意志形（「〜してみよう」）で結ぶ。パラメータ名は Tweakpane のラベルと揃える。文面は下書き扱いで、完了報告に載せて著者が直せるようにする。
3. **その直後に ` ```ts ` のコードブロック**で掲載コードを置く（**色彩記事では省く**）。**タイトル付き（` ```ts:タイトル `）にはしない** — `lib/remark/code-title.js` が remark 段階で `html` ノードに差し替えるため、後段の shiki のハイライトが効かなくなる。
4. フロントマターに `visual: true` が無ければ追加する。
5. **`:::Action` 以外の説明文は書かない。**

### 完了報告

- 挿入した記事と位置
- 作成したファイル
- 記事に載せたコード（元になった `scene.ts` の関数名と、外した部分）
- `visual: true` を付与したかどうか
- **書いた `:::Action` の文面**（著者が直す前提の下書きとして、そのまま引用する）
- **このデモで何を操作でき、何が読み取れるか**（`:::Action` に書ききれなかったものを含め、あとから言及を書き足す材料として報告に添える）
- Tweakpane 初回導入時は `npm install` が必要である旨

## 実装規約

### 実装方式

- **素の Three.js で実装する。Threlte は使わない。**
- パラメータをユーザーが操作するデモでは **Tweakpane** を使う。素の `<input type="range">` による代替は設けない。

### ファイル構成

```
app/src/lib/demo/threejs/
  _shared/                              記事に載らない定型処理
  <ユニット>/<記事slug>/<デモ名>/
    scene.ts                            記事に載せる本体。three にのみ依存
    <デモ名>Demo.svelte                 薄い殻（canvas のマウントと Tweakpane 配線）
```

- ディレクトリは**ユニット込み**（`threejs/transformation/basic-transformations/`）。CG記事は今後大量に増えるため、slug の将来的な衝突を避け、記事の在り処と対応が取れるようにする。**色彩記事のデモは `threejs/color/<デモ名>/`**（→「色彩記事への適用」）。
- **デモごとにサブディレクトリを作る**。1 デモが 2 ファイル以上になるため、フラットに置くと見通しが悪くなる。
- Svelte コンポーネントは `<デモ名>Demo.svelte`（PascalCase）とする。

### 責務分担

- **`_shared/`（記事に載らない）**
  - renderer の生成（DPR 上限は `min(devicePixelRatio, 2)`）
  - rAF ループ
  - `ResizeObserver` によるリサイズ
  - `dispose`
  - **画面外でのループ停止（必須）**
  - Tweakpane パネルの生成とテーマ変数
  - OrbitControls（掲載コードに載らないため共通化する）
  - WebGL 非対応・コンテキストロスト時のメッセージ表示
- **`scene.ts`（記事に載せる）**
  - その記事固有のシーン構築・行列計算・ジオメトリ生成・パラメータ適用
  - **`_shared` を import しない。`three` にのみ依存させる**（掲載コードがそのまま読者の手元で動く条件）
  - 公開 API は `export const createXxxScene = (ctx) => ({ update?, dispose? })` の 1 関数
  - `ctx` には `renderer` も渡す。**そのデモに固有で、かつ必須の renderer 設定**（`localClippingEnabled` など）は `scene.ts` 側で書き、記事に載るコードに含める（それが無いと読者の手元で同じ絵にならないため）

### 掲載コードの規約

- **記事に載せるコードは、実際に動いている `scene.ts` から作る。** 記事用に書き下ろしたり、他のAPIから翻訳したりしてはならない。
- **`scene.ts` との逐語一致は求めない。** 記事側は「読者がそのまま書き下せる形」を優先し、デモの都合で入っている構造は外してよい。
  - 関数の殻を外し、中身をトップレベルのコードとして並べる。
  - 引数を実データに置き換える（`createWireframeGeometry(vertices, edges)` → `createWireframeGeometry(VERTICES, EDGES)`）。
  - `update()`・`dispose()` に渡すためだけの戻り値を落とす。
  - 関数の doc コメント（`/** */`）を、ブロックの見出しになる `//` コメントに変える。
- **定数・パラメータはデモの初期値に合わせる。** 掲載コードが描く絵と、デモの初期表示を一致させる（「面を外す」トグルの既定がオンなら、掲載コードも面を外した状態にする）。
- **やってはいけない改変** — 処理を `// 省略` で削る、実装には無いAPI・値に書き換える、そのままでは動かないコードにする。
- **行数の上限は設けない。** 短さのために、デモと同じ絵を出すのに要るコードを落とさない。`scene.ts` を「記事に載せやすい単位」で設計する責任は実装側に置く。
- 載せるのは、その記事の**主題が現れている部分**と、**そのコードだけで初期表示と同じ絵になるのに要る部分**（面の枠線、基準となる点や線など）。
- 既定では**載せない**もの（長いだけで主題が薄れる） — 頂点座標・インデックスなどのデータ定義、色などの定数、`update()`・`dispose()` の後処理。マテリアルの生成と `scene.add()` は載せる。
- **`three` の API を使わない処理も載せない。** 多角形を三角形へ分割するような純粋な配列操作は、`scene.ts` に置いたまま掲載コードから外す（記事に載せるのは three の API が現れている部分）。
- **どこまで載せるかは最終的に著者が決める。** 完了報告で何を載せ何を外したかを伝え、指示があればその形に直す。
- 当初は「`scene.ts` からの逐語抜粋に限る」としていたが、`cg/modeling/shape-model-overview`（さまざまな形状モデル）の実装時に、読者がそのまま書き下せる形を優先する方針へ変更した（2026-08-01）。「一度も実行されていないコードを載せない」という目的は変えていない。
- 当初は「1 デモにつき 40 行程度」という目安を置いていたが、`cg/camera/pinhole-camera`（ピンホールカメラ）の実装時に撤廃した（2026-08-01）。行数に収めるために投影面の枠線や基準となる点・線を落とすと、掲載コードだけを書き写した読者の手元とデモの絵が食い違うため。

### 見た目

既存の 3D デモ（`lib/demo/pccs/PCCSColorSolid3D.svelte`）の規約を踏襲する。

- canvas のラッパ: `width: 100%` ＋ `aspect-ratio` ＋ 枠線 ＋ `touch-action: none` ＋ `cursor: grab`
- **`aspect-ratio` はデモごとに変更可**（変換・投影のデモは横長のほうが見やすい場合がある）
- 枠線は `light-dark()` でライト／ダークに追従させる（枠はシーンではなくページ側の要素のため）
- ラッパに `role="img"` ＋ `aria-label`。**Tweakpane パネルはその外（兄弟要素）**に置く
- `{#if browser}` でクライアントのみマウントする

### 背景色

- **ライト／ダーク共通の固定色**とする。`_shared` にニュートラルな暗めグレーの既定を持ち、デモごとに上書き可能にする。
- 理由は 2 つ。
  - 軸ラベルや線の色を、両モードで可読な 1 色に決められる。
  - `scene.ts` にテーマの分岐が入らないため、**掲載コードの見え方が読者の手元と一致する**。

### Tweakpane

- **操作を用意するのは、記事の主題に関わるパラメータだけ。** 主題から外れるもの（形状モデルの記事における光の向きなど）は固定値にし、パネルに出さない。
- `devDependencies` に追加する（このリポジトリは `three`・`chroma-js` も `devDependencies` に置いている）。
- ロードは SvelteKit のコード分割任せ（デモを載せた記事のチャンクにだけ入る）。明示的な動的 import はしない。
- CSS 変数（`--tp-base-background-color` など）に `light-dark()` を指定し、**サイトのライト／ダークに追従**させる。
- パネルは **canvas の外（下）** に置く。狭い画面でオーバーレイすると図が隠れ、`touch-action: none` の領域と操作が混ざるため。

### アニメーション

- **自動アニメーションは作らない。** 操作したときだけ動くようにする。

## 色彩記事への適用

2026-08-09 に適用範囲を色彩記事（`color-theory`・`color-fields`）へ広げた。当初は「色彩記事の 3D は Threlte、CG記事は素の Three.js」の 2 系統で運用する方針だったが、**新規の 3D デモは色彩記事でも素の Three.js（このスキル）で作る**ことにした。既存の Threlte 製デモは据え置き、移植はしない。

### CG記事との差分

- **記事に Three.js のコードを載せない。** 色彩記事の読者に持ち帰ってもらうのは色の理論であって Three.js の書き方ではないため、狙いの 2 つ目（応用例を示す）を取らない。`:::Foldable` のコードブロックを付けず、「掲載コードの規約」も適用しない。
- **置き場所は `app/src/lib/demo/threejs/color/<デモ名>/`**（`scene.ts` と `<デモ名>Demo.svelte`）。CG記事のようにユニット・記事slugを挟まない。
  - 色彩記事のルートは `color-theory/<slug>`・`color-fields/<slug>` の 1 階層で、slug 衝突の心配が薄い。
  - デモは記事よりも題材（色立体・スペクトルなど）に紐づき、複数の記事から使われうる。既存の SVG 図解も `lib/demo/color/<題材>/` と題材で分かれている。
  - `<デモ名>` は記事slugではなくデモの内容から決める（kebab-case）。頭字語は既存の色彩デモに合わせて大文字のまま（`PCCSColorSolidDemo.svelte`）。
- **`scene.ts` の掲載前提の制約を外す。** 記事に載らないため、`_shared` の型 import（`ThreeSceneContext`）と、色データ・色計算モジュール（`$lib/data/pccs`・`$lib/color/**`・`chroma-js`）の import を許す。「記事に載せやすい単位で設計する」責任も負わない。色の値を `scene.ts` に手で書き写さず既存の出典から取る、という利点のほうが大きい。
- **デモの狙いは「内容の理解を助ける」の 1 点。** 3 次元・連続量・視点移動が効く題材に絞り、2 次元の図解で足りるものは `svg-diagram-component` に任せる（「向かない」と申告して止まる判断は CG記事より多くなる）。
- **提案フォーマットから「視点」「記事に載るコード」の 2 列を落とす。**
- **完了報告から「記事に載せたコード」を落とし**、色データの出典と、色を歪めない設定（マテリアル・ライト・背景色）を書く。

### 色を歪めないための約束

色そのものが記事の主題になるため、レンダリングで色が変わる要因を持ち込まない。

- 「その色を見せる」対象は `MeshBasicMaterial`（ライティングの影響を受けない）。既存の `PCCSColorSolid3D` も同じ。
- トーンマッピングは素の `WebGLRenderer` の既定（`NoToneMapping`）のまま。Threlte の `<Canvas>` は AgX が既定で高彩度の色が褪せるが、素の Three.js ではこれが起きない。
- 背景色は無彩色に保つ（背景の明度は明度対比で図の色の見えを変える）。既定の `DEMO_BACKGROUND` から変える場合も、無彩色かつライト／ダーク共通の固定色にする。

なお、背景色を固定色にする 2 つ目の理由（掲載コードの見え方が読者の手元と一致する）は色彩記事では消えるが、1 つ目の理由（両モードで可読な 1 色に決められる）が残るため、方針は変えない。

## 既存機能との関係・整合

- **`author-style-writer`** — 本文の執筆はこちらの担当。このスキルは執筆完了後に呼ばれ、地の文には手を入れない（デモ・デモ直前の `:::Action`・コードブロック・import・フロントマターのみ）。`:::Action` の文体（casual な意志形）は `writing-guides/stylistic-quirks.md`「本文とActionのレジスターの二層構造」に従い、`:Mark[]` は自分から書かない（`writing-guides/syntax-guide.md`）。
- **`svg-diagram-component`** — 静的な SVG 図解の担当。引数で図の内容を渡す／`visual: true` を付与する、といった流儀を踏襲する。**`:::Todo` は図版・デモ共用のプレースホルダなので、このスキルも `:::Todo` を依頼として読み、ブロックを差し込みで置き換える**（`svg-diagram-component` のパターンCと同じ扱い。→「`:::Todo` の扱い（パターンA-1）」）。静的な2次元の図で足りる `:::Todo` は、3D 案との対比を示したうえで `svg-diagram-component` へ回す（→「懸念・代替案」）。`:::Todo` が無いときだけ、挿入位置をデモ案の提案時に合意する。
- **`図解` タグ（`visual: true`）** — `lib/meta/guide-pages.ts` がフロントマターを集約し、`lib/components/m-directive/PageLink.svelte` が一覧リンクにタグを描画する。記事ページ上部（`page-meta`）には `visual` は表示されないため、デモの有無も一覧リンクにのみ現れる。
- **既存の Threlte 3D デモ** — `PCCSColorSolid3D.svelte`・`MunsellColorSolid3D.svelte` はそのまま据え置き、移植しない。新規の 3D デモは色彩記事でも素の Three.js で作るため、同じ記事に 2 系統が並びうる（→「色彩記事への適用」）。
- **`CanvasWrapper`** — 既存の 3D デモ埋め込みと同じく `<CanvasWrapper>` で包む。

## ドメインルール上の考慮

- PCCS の色相・トーンなど色彩ドメインのルールは、CG記事のデモには直接関わらない。**色彩記事のデモでは主題そのもの**で、色の値は既存の色データモジュール（`$lib/data/pccs` など）から取り、レンダリングで色を歪めない（→「色彩記事への適用」）。
- CG記事は `group: ["CG"]` / `["ImgP"]` を持ち、カリキュラム上の出典区分がタグとして表示される。デモの有無はこの区分とは別軸の情報で、`図解` タグが担う。

## データ・状態

- 永続化するデータは無い。デモのパラメータは Tweakpane が保持する実行時の状態のみで、リロードで初期値に戻る。
- 記事側に増えるのはフロントマターの `visual: true` と、本文中のコンポーネント使用箇所・`:::Action`・コードブロック。
- `guide-pages.ts` は `import.meta.glob` でビルド時にフロントマターを集約するため、`visual: true` を書けばタグ表示に反映される。追加の登録作業は不要。

## エッジケース・異常系

- **WebGL 非対応・コンテキストロスト** — メッセージを表示する。メッセージには**どういう環境なら動作するか**を明記する。
- **1 記事に複数デモ** — 複数の rAF ループと WebGL コンテキストが同一ページで同時に走りうるため、**画面外のデモはループを停止する**（`_shared` で必須）。
- **記事slugの解決失敗** — 0 件・複数ヒットは確認して止める。
- **デモに向かない記事** — 提案フェーズで「向かない」と申告して止まってよい。
- **`:::Todo` がデモに向かない内容** — 静的な2次元の図で足りると判断した場合も、その旨を伝えたうえで 3D・操作にするならどう見せられるかを代替案として示し、指示を待つ（→「懸念・代替案」）。静的な図で進めると決まったらブロックは残し、`/svg-diagram-component` を案内する。
- **`:::Todo` と `<デモの内容>` の両方がある** — 引数の指定を優先し、対応する `:::Todo` があればその位置に差し込んでブロックを置き換える。
- **記事が `draft: true` のまま** — 執筆直後に呼ばれる想定のため、下書き記事も対象とする。

## 非機能要件

- **アクセシビリティ** — 特別な配慮は要件としない。既存デモに倣い、ラッパに `role="img"` ＋ `aria-label` を付ける範囲に留める。
- **モバイル** — Tweakpane パネルは canvas の外（下）に置く。OrbitControls を使うため canvas 側は `touch-action: none`。
- **パフォーマンス** — DPR 上限 `min(devicePixelRatio, 2)`、画面外でのループ停止、自動アニメーションなし。
- **バンドル** — SvelteKit のコード分割任せ。`three` は既に色彩記事でも読み込まれている前例がある。

## 制約

- 静的サイト（`adapter-static`）で prerender されるため、Three.js・Tweakpane はクライアントのみで動かす（`{#if browser}` ガード）。
- ` ```lang:タイトル ` 形式のコードブロックは shiki のハイライトが効かない（`code-title.js` が remark 段階で `html` ノードに置き換えるため）。デモのコード掲載ではタイトルを付けない。
- 素の `WebGLRenderer` は既定が `NoToneMapping` のため、Threlte の `<Canvas>` で必要だったトーンマッピングの明示は不要。
- CG記事の実体は `cg/<ユニット>/<記事slug>` で、slug 単体ではパスが確定しない。色彩記事は `color-theory/<記事slug>`・`color-fields/<記事slug>` の 1 階層。slug の解決時にどちらで見つかったかで、コードを載せるかどうかとデモの置き場所が決まる。

## 受け入れ条件

- デモが意図どおり動く。**目視確認はユーザーが行う。**
- `npm run check` が通る。**実行はユーザーが行い、スキルは勝手に実行しない**（`svg-diagram-component` と同じ）。エラー・警告が報告されたら修正する。
- 記事の ` ```ts ` ブロックが `scene.ts` で実際に動いているコードから作られている（逐語一致は問わないが、処理の削除や書き換えは無い）。**色彩記事ではコードブロックが無いこと。**
- 記事のフロントマターに `visual: true` が付いている。
- 各デモの直前に `:::Action` が置かれ、操作と着眼点が対で書かれている。
- 記事本文（地の文）が変更されていない。
- `:::Todo` を元にした場合、そのブロックがデモの差し込みで置き換わり、記事に `TODO` の文字列が残っていない。
- 画面外に出たデモのループが停止する。

## 検討して却下した案

- **Threlte で実装し、本質部分を Three.js に翻訳して掲載** — 記事に載るコードが一度も実行されないコードになる。翻訳が必要になるのはカメラ・投影・ライティングといった**まさにCG記事の主題になりやすい箇所**で、そこに検証の穴が開く。加えて Threlte の `<Canvas>` が既定で行う設定（トーンマッピング等）の差により、デモの見え方と掲載コードの見え方がずれるという最も気づきにくい乖離が生まれる。一部のみ掲載と決めた時点で、定型を `_shared` に追い出せるため素の Three.js を選ぶコストが消えたことも理由。
- **`import src from "./scene.ts?raw"` による自動掲載** — 原理的に乖離ゼロだが、現状の shiki は mdsvex のビルド時ハイライトのため、`?raw` の文字列にはハイライトが効かない。ランタイムハイライタか専用プラグインが必要になる。
- **掲載コードの全文掲載** — renderer 生成からリサイズ・破棄まで含めると 1 デモで 100 行を超え、記事の主題よりボイラープレートが目立つ。
- **「Web」タグの新設** — フロントマターの新フラグ・タグコンポーネント・色トークンが必要になり、CG記事では `図解` `Web` `CG` `画像処理` の 4 タグが並んで狭い画面で折り返す。`図解` タグで代替する。
- **掲載コードと `scene.ts` の逐語一致を検証する vitest テスト** — 乖離が起きた瞬間に CI で落ちる利点はあるが、過剰。加えて逐語一致そのものを要件から外したため（→「掲載コードの規約」）、検証すべき対象がなくなった。規約の記述に留める。
- **デモ案の提示に `AskUserQuestion` を使う** — 選択肢が 2〜4 個に固定されるため、案の件数が記事ごとに変わるこの用途に合わない。
