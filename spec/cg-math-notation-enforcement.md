# CG記事の数式記法の強制化

## 目的・背景

`writing-guides/math-notation-guide.md` の記法（数式・インラインコード）を、CG記事（`app/src/routes/cg/**`）に対して機械的に強制する。あわせて、その整備を担う `format-math-notation` スキルを高速化する。

### 発端の課題

- 記法ルールは新しく書く記事から適用する方針で、導入時点で違反を含んでいた既存記事は `app/.textlintignore`（ベースライン）で対象外にしている。結果として、**既存記事の記法は誰も強制していない**。
- `/format-math-notation <slug>` の実行にかなりの時間がかかるため、何らかのタイミングで自動実行するなら、スキル自体の高速化が前提になる。

### 調査で判明した「遅さの正体」

**textlint は遅くない。** 全172記事・ベースライン無効での実行が **2.3秒**。ボトルネックはリンタではない。

| 指標 | 値 |
| --- | --- |
| 機械検出できる違反（全記事） | 665件 / 78記事 |
| うち `--fix` で自動修正できる | 644件（97%） |
| 真に判断が要るもの | 21件 |

過去の実行例（`0e88b9e6` パラメトリック曲線・曲面）の差分は **52件すべて textlint の自動修正**だった。そのコミットメッセージが記録している判断は次のとおり。

> インライン数式のままにした記号（x・y・z・t・u・v・m・n）は、KaTeX 必須記号を含まないが**ブロック数式の記号を説明する文の中にあり、同じ文の X(t)・P_i・C^n と揃っている**ため維持した

つまり**差分ゼロの読解作業に時間を使っている**。textlint が見ていない8ルールのうち、とくに「スコープを見て初めて決まる」3つ（ブロック数式の説明文・文単位の統一・記事全体の統一）を、記事を通読して人力で解いていた。

### 設計の核

このスコープルールを**素朴に機械化すると壊れる**。「KaTeX 必須記号を含まない `$$…$$`」で数えると、全記事857件中**478件**が「インラインコードに落とすべき」候補として挙がるが、上記の `$$t$$`・`$$C(t)$$` はまさにその478件に含まれ、**維持が正しい**。

逆に順序を入れ替えれば解ける。**ブロック数式の説明文 → 文単位の統一 → 記事全体の統一**を先に確定させれば、「インラインコードへ落とすべき `$$…$$`」はその残差として決まる。ガイドの「なるべくインラインコード」は、上位3ルールに拾われなかった記号だけに掛かる規則である。

実測でこれを確認した（CGスコープ）。

| 段階 | 件数 |
| --- | --- |
| 素朴判定による降格候補 | 432件 |
| ① ブロック数式の記号 → 維持 | −411件 |
| ② 同じ文に KaTeX 必須記号 → 維持 | −5件 |
| **残る真の降格候補** | **16件 / 7記事** |

さらにこの16件も、③記事全体の統一を減算し、KaTeX 判定の穴（`\;`・`\,` のようなバックスラッシュ＋非英字を必須記号と見ていなかった）を埋めれば数件に落ちる。

**したがって「強制化」と「高速化」は同じ工事である。** 強制するには機械判定が要る。機械判定ができればスキルの読解作業がそのまま消える。

## スコープ

### やること

- CG記事（`app/src/routes/cg/**`）を対象に、記法ルールを機械的に強制する。
- textlint のルールを増やし、現在スキルが人力で見ている判断を可能なかぎり機械側へ移す。
- 検査を2パスに分ける（ブロッキングの `syntax` と、非ブロッキングの `advisory`）。
- 記法整備の進捗を追うタスクリストを新設し、既存2枚と同じ仕組みで YAML に追随させる。
- `publish-article` の手順0に記法ゲートを追加し、違反があれば `format-math-notation` を**自動実行**する。
- `format-math-notation` を advisory 専門の薄いスキルに縮める。バッチ指定を受け付ける。
- 既存CG記事21件（ベースライン掲載分）の移行。

### やらないこと

- **色の理論・色の活用分野の記事（`color-theory` / `color-fields`）を強制化の対象にすること。** タスクリスト・公開時ゲート・ベースライン解消の目標はCG記事のみ。
- **textlint の検査対象を CG に狭めること。** 現在すべての記事が検査対象で、非CG記事はすべて緑である。新ルールを追加しても非CG記事で落ちるのは2件だけなので（後述）、検査対象は全記事のまま維持する。CG限定なのは「強制化の仕組み」の側だけ。
- 表記揺れ（`app/textlint/prh.yml`・`lint:svx:notation`）。別系統。
- `syntax-guide.md` 側の記法（ディレクティブの使い分け、見出しの分類タグ、ボールド体の禁止など）。
- 文章・構成・強調・図版・デモ。
- 編集直後（PostToolUse フック）・コミット前（Stop フック）・CI（GitHub Actions）でのゲート。今回の契機は公開時のみ。

## ユーザーストーリー・主要ユースケース

1. **新しいCG記事を公開する。** `draft: true` を外して `/commit-this` を実行すると、`publish-article` の手順0で記法ゲートが走る。違反があれば `format-math-notation` が自動実行され、`--fix` が収束するまで当たる。`commit-this` が「記法を整備」のコミットを独立して先に作り、コミットの許可プロンプトで差分を確認して承認する。
2. **既存の公開済みCG記事を整備する。** タスクリストの `[ ]` を見て、`/format-math-notation #transformation` のようにセクション単位でまとめて回す。
3. **advisory の指摘を片付ける。** `npm run lint:svx:advisory` で判断待ちの指摘を見て、必要なら `/format-math-notation <slug>` で対応する。公開はブロックされないので、任意のタイミングでよい。
4. **CG記事が新しく増える。** `node scripts/sync-tasklists.mjs --write` でタスクリストに自動で行が足され、対応漏れが構造的に起きない。

## 機能要件

### 1. 検査を2パスに分ける

**組織原則: 自動修正できない指摘は `syntax` パスに置かない。**

この原則があるからこそ、公開時ゲートからの自動実行が安全になる（`--fix` を収束させれば必ず0件にできる＝承認を挟まずに書き換えても、決定的な変換しか起きない）。

| スクリプト | 中身 | 性質 | ベースライン |
| --- | --- | --- | --- |
| `lint:svx:syntax` | `--fix` で必ず0件にできるルールだけ | **ブロッキング**（公開時ゲートが見る） | 効く |
| `lint:svx:advisory` | 判断が要るもの全部 | **非ブロッキング** | 効かない |
| `lint:svx:notation` | 表記揺れ（現状のまま） | 非ブロッキング扱い（現状のまま） | 効かない |

この原則の帰結として、**現行 `syntax` パスにある「報告のみ」の指摘は advisory へ移る**。

- `svx-number-in-code` の「英字に隣接する数字」（`3D`・`600nm` のように囲む範囲の判断が要るもの）
- `svx-math-function-in-code` の「引数が続く関数名」（`sin(x)` のように囲む範囲の判断が要るもの）

### 2. `--fix` を収束まで回す

**現状は1パスしか回しておらず、連鎖して生まれた違反が残る。これは実バグである。**

実測（全記事）:

| パス | 残り |
| --- | --- |
| fix 前 | 665件 |
| 1パス後 | 24件 |
| 2パス後 | **21件（収束）** |

再現例: `輝度 255 の白` → 数字ルールが `輝度 ` + "`255`" + ` の白` にする → 前後にスペースが生まれ `svx-no-space-around-code` の違反4件が**新たに発生**する → 2パス目で `輝度`255`の白` に収束。

`lint:svx:fix` を「変化が無くなるまで、上限回数つきで繰り返す」形に変更する。

### 3. 既存ルールの辞書強化

`svx-number-in-code` に**単位辞書**を持たせ、単位つきの数値を単位ごと囲む自動修正を可能にする（`600nm` → `` `600nm` ``）。ガイドが「単位つきの数値は、単位も含めてインラインコードにします」と明記しているため、判断の余地がない。

**単位以外は辞書に載せない。** 色記号（PCCSトーン `v2`、マンセル `5R`）・固有名詞（`3D`・`3DCG`・`3DS`）・BC記法（`BC2万年`）はトークンの列挙で例外化せず、advisory パスで判断待ちとして出す。

CGスコープでこれに該当するのは `3D`・`3DCG`・`3DS` の**3件のみ**（色記号とBC記法は `color-theory` 側でスコープ外）。

### 4. 新しい textlint ルール

#### 決定的なルール（自動修正・`syntax` パス）

| ルール | 内容 |
| --- | --- |
| `svx-inline-math-dfrac` | インライン数式の中の `\frac` → `\dfrac` |
| `svx-math-prime` | 数式の中のアポストロフィ `'` → `^{\prime}` |
| `svx-block-math-linebreak` | ブロック数式の行末を `\\\\`（4つ）に、`\frac` を含むブロックは `\\\\\\\\`（8つ）に |
| `svx-no-code-in-label` | `:Anki[]`・`:Mark[]` のラベルとリンクのテキストの中のインラインコードを外す |

これらは**ほぼ予防専用**である。実測での既存違反はリポジトリ全体で6件（CGベースライン2件・CGいま緑1件・非CGベースライン2件・非CGいま緑1件）。

#### `:::Action` のルール

| ルール | 内容 | 配置 |
| --- | --- | --- |
| `svx-action-no-inline-math` | `:::Action` 内のインライン数式を禁止 | Unicode で書ける記号（`θ`・`≡`・`×`）はインラインコードへ自動変換 → `syntax` |
| 同上（言い換えが必要な分） | 添字・分数・行列は日本語への言い換えが必要 | **`advisory`**（文章を書く判断のため） |

#### スコープ解析ルール（昇格は自動・`syntax` パス）

適用順序が意味を持つ。上から順に確定させる。

| # | ルール | 内容 |
| --- | --- | --- |
| ① | `svx-block-math-symbol-unify` | ブロック数式を説明する文では、その式の記号をインライン数式で書く |
| ② | `svx-sentence-math-unify` | インライン数式を含む文では、数式・変数・関数名をインライン数式に統一する |
| ③ | `svx-article-symbol-unify` | 同じ対象を表す記号は記事全体でどちらか一方に統一する |

- **昇格（インラインコード → インライン数式）のみ自動修正する。** ①②③はいずれも「数式側へ揃える」向きが一意に決まる。
- **降格（インライン数式 → インラインコード）は自動修正しない。** 降格の根拠は「①②③に拾われなかったこと」であり、スコープ検出の取りこぼしがそのまま誤修正になる。素朴な実装では478件（全記事）／432件（CG）の偽陽性が出る。
- **`:::Action` のテキストは①②③の対象外**（ガイドの明示）。
- **数字は②③の対象外**（ガイドの明示）。数字の判定は広く取る必要がある（後述）。

#### 残差ルール（検出のみ・`advisory` パス）

| ルール | 内容 |
| --- | --- |
| `svx-prefer-inline-code` | ①②③に拾われず、KaTeX 必須記号も含まない `$$…$$` を降格候補として報告する |

### 5. タスクリストの新設

既存2枚（`ogimage/OGP-TASKLIST.md`・`writing-guides/STYLE-ANALYSIS-TASKLIST.md`）と同一構造の3枚目を作り、`scripts/sync-tasklists.mjs` の `TASKLISTS` に追加する。

- CG記事のセクションだけを載せる（`cg/<yaml>.yaml #<id>` 単位）。
- **`[x]` は `app/.textlintignore` から導出する。** その記事の行がベースラインに載っていなければ `[x]`。
  - 既存2枚は「`[x]` は絶対に生成しないし、消さない」という不変条件を持つが、**3枚目だけはこの例外**とする。記法整備の完了状態は `.textlintignore` という機械可読な正典が既にあり、手記録を併置すると二重管理のドリフトが起きるため。
  - 帰結として、`[x]` の意味は「**`lint:svx:syntax` の検査対象に入っている**」になる。advisory の指摘が残っていても `[x]` になる（advisory は非ブロッキングなので）。
- `[draft]`・`[ページ未作成]` の扱いは既存2枚と同じ。
- `sync-tasklists.mjs` が新しいCG記事の行を自動で足すため、**新規記事の登録漏れが構造的に起きない**。

### 6. 公開時ゲート（`publish-article` 手順0）

既存の編集指示ディレクティブの残存チェックに、記法ゲートを追加する。

1. 対象記事に `lint:svx:syntax` を当てる（ベースラインは効かせる。ベースラインに載っている記事はそもそも対象外なので、ゲートを通過する）。
2. 違反があれば **`format-math-notation` を自動実行する**（案内して止めるのではない）。
3. `--fix` が収束するまで当てる。`syntax` パスは自動修正できるルールだけなので、必ず0件になる。
4. 作業ツリーに変更を残すだけで、**`publish-article` はコミットしない**（既存の分担を維持）。
5. advisory の残件は報告するが、公開を止めない。

既存のディレクティブゲート（`:::Todo` などが残っていたら案内して止まる）とは扱いが異なる。ディレクティブは図版・デモという創作作業を要求するのに対し、記法は決定的な変換で片付くためである。

### 7. コミット（`commit-this`）

`commit-this` が記法整備を**独立したコミットとして先に**作る。

```
commit-this
  ├─ publish-article --before-commit
  │    └─ 手順0: 記法ゲート
  │         └─ format-math-notation を自動実行（作業ツリーに変更を残すだけ）
  ├─ commit #1  記事タイトル：数式・インラインコードの記法を整備 [ai-draft]   ← 許可プロンプト
  ├─ commit #2  記事タイトル [ai-draft]                                  ← 許可プロンプト
  └─ publish-article --ogp → commit #3                                  ← 許可プロンプト
```

**承認は commit の許可プロンプトで担保する。** `.claude/settings.json` の `permissions.ask` に `Bash(git commit *)` があるため、自動実行で書き換えた差分は必ず人間の確認を経る。これにより「公開時ゲートから自動実行すると、手順4の承認が消える」という懸念が解消される。

コミットメッセージは過去の実績（`0e88b9e6` など）と揃える。

### 8. `format-math-notation` スキルの改修

#### 移管して消える手順

| 現行手順 | 移管先 |
| --- | --- |
| 手順2 機械的な違反の洗い出し | `lint:svx:syntax`（収束ループ化） |
| 手順3 grep＋通読で拾う8ルール | 新ルール群（決定的4件・`:::Action`・昇格3件） |
| 手順3 記号インベントリの作成 | ③記事全体の統一ルールが内部で持つ |
| 手順4 修正方針の表と承認 | 自動修正分は不要（決定的なので承認の意味がない）。コミットの許可プロンプトが確認点になる |
| 手順5 `--fix` 1回 | 収束ループ |
| 手順6 手作業 | 大半が自動修正に吸収される |

#### 残る役割（advisory 専門）

1. **advisory の指摘の判断** — 降格候補と、英字隣接の数字の囲む範囲（CGスコープで `3D`・`3DCG`・`3DS` の3件）。
2. **昇格の自動修正が踏み込めない箇所の手当て** — `` `C_fg` `` → `$$C_{fg}$$` のような添字の波括弧化（実測2件）。
3. **`:::Action` の添字・分数を日本語に言い換える** — ガイドが「日本語で言い換えます」と定めている創作作業。
4. **置き換えで文意が崩れる箇所の保留判断と報告** — 現行の「迷ったら直さない」を維持する。
5. **`app/.textlintignore` の行の削除** — `syntax` が0件になったら対象記事の行を外す。タスクリストは導出なので触らない。

#### 引数

```
/format-math-notation [<記事slug>|#<セクションid>|--auto] …
```

- **`#<セクションid>`** — タスクリストのセクション見出しに書かれた id（`#transformation` など）をそのまま渡せる。`author-style-analyzer` と同じ流儀。CG のセクション id はユニットをまたいで重複しうるので、指定時はユニット名も添える。
- **`--auto`** — 公開時ゲートからの自動実行モード。自動修正だけを当て、advisory は報告のみにする（判断を伴う書き換えをしない）。

#### 手順（改修後）

1. 対象を確定する。
2. `--fix` を収束まで回す。
3. advisory の指摘を表で提示して承認を得る（`--auto` のときは報告のみで止める）。
4. 手当てを当てる。
5. `syntax` が0件なら `.textlintignore` の行を外す。
6. 報告する。コミットはしない。

| 既存 | 関係 |
| --- | --- |
| `app/.textlintignore` | 引き続きベースラインの正典。タスクリストの `[x]` はここから導出する |
| `app/textlint/README.md` | 2パス構成・新ルール・辞書の方針を追記する（検査の仕組みの正典） |
| `scripts/sync-tasklists.mjs` | `TASKLISTS` に3枚目を追加。`[x]` の導出ロジックを新設（既存2枚の不変条件は変えない） |
| `publish-article` | 手順0に記法ゲートを追加。「コミットしない」「ゲートに引っかかったものを自分の判断で対応しない」の原則のうち、**記法だけは自動実行する例外**になる |

| `writing-guides/math-notation-guide.md` | ルールの正典。変更しない（機械化するだけ） |
| `lint:svx:notation`（表記揺れ） | 別系統。触らない |

### 現在の状態（CGスコープ）

| 項目 | 値 |
| --- | --- |
| CG記事 | 68件 |
| ベースライン掲載 | 21件（`draft: true` 4件 / 公開済み 17件） |
| 検査対象（いま緑） | 47件 |
| 現行4ルールの違反 | 251件 / 21記事 → `--fix` 2パスで収束、残差3件 |

### 新ルールが既存の緑を壊さないこと

新しい決定的ルールを全記事に効かせても、落ちるのは**2件だけ**（CG 1件・非CG 1件、いずれもブロック数式の行末改行）。昇格ルール（②文単位）は**非CG記事に1件も発火しない**。

したがって textlint の検査対象を CG に狭める必要はなく、狭めるべきでもない（非CG記事89件の現在の検査が失われる）。

## ドメインルール上の考慮

- **色記号の慣習表記** — PCCSトーン記号（`v2`）・マンセル記号（`5R`・`5YR`）・色光の角括弧表記（`$$[R]$$`）。CGスコープではPCCSトーンとマンセルは出現しないが、`$$[R]$$` 形式は KaTeX 必須記号として扱う（降格しない）。
- **`:::Action` の例外** — ギリシャ文字も含めてインラインコードで書く。記事全体・文単位の統一より優先する。地の文で `$$\theta$$` と書いている記事でも `:::Action` の中だけ `` `θ` `` になるのは混在ではない。
- **数字の統一対象外** — ②③では数字を対象外にする。この判定を狭く取ると偽陽性になる。実測で `` `-1` ``（負号）と `` `(1, 0, 0)` ``（数字のタプル）を変数と誤認し、**整備済みの記事2件を違反と誤検出した**。負号・小数・タプル・範囲・単位つきをすべて数字と見る必要がある。
- **KaTeX 必須記号の判定** — バックスラッシュ＋英字（`\theta`）だけでなく、**バックスラッシュ＋非英字**（`\;`・`\,`）も必須記号に含める。実測で `$$(0 \; 0 \; 1)$$` を降格候補と誤検出した。
- **複合語の中の変数記号も昇格する** — `` `x`軸 ``・`` `x`方向 `` はガイドの文言どおり `$$x$$ 軸`・`$$x$$ 方向` に昇格させる（数字の「単語中でも囲む」と揃える）。昇格候補30トークンのうち約8件がこの形。

## データ・状態

- **記事本文** — `app/src/routes/cg/**/+page.svx`。書き換え対象。
- **ベースライン** — `app/.textlintignore`。記法整備の完了状態の正典。
- **タスクリスト** — CG記事の記法整備の進捗の人間向けビュー。`[x]` はベースラインから導出するので、それ自体は状態を持たない。
- **永続化・スキーマ変更** — なし。アプリの実行時データには一切触らない。

## エッジケース・異常系

| ケース | 挙動 |
| --- | --- |
| ベースラインに載っている記事を公開する | ゲートは通過する（ベースラインが効くため）。整備は移行の担当 |
| 公開済みCG記事を編集して違反が入る | **検出する契機が無い**。ベースラインから外れているので `lint:svx` の対象ではあるが、それを走らせる契機が公開時しかなく、公開は済んでいる。既知の穴（下記） |
| `--fix` が収束しない（振動する） | 上限回数で打ち切り、収束しなかった旨を報告して止める |
| `--fix` がコードブロック・ディレクティブ属性・リンクURLに及ぶ | その箇所だけ戻し、マスクの取りこぼしとして報告する（ルール実装の修正はスキルの仕事ではない） |
| 対象記事に未コミットの差分がある | 差分が混ざる旨を伝えて続行可否を確認する（自分でコミットも退避もしない） |
| タスクリストと `.textlintignore` の不整合 | 導出なので原理的に起きない |
| CG以外の記事に `format-math-notation` を手動で渡す | 受け付ける（スキルの適用範囲は3ルートのまま）。ただしタスクリストとゲートの対象外 |
| 新ルール追加で非CGの緑が落ちる（2件） | 直して緑に戻す。ベースラインに追加はしない |

### 既知の穴

**公開後の後退を検出する契機が無い。** 公開時ゲートは `draft: true` が外れる瞬間に一度だけ発火するため、公開済み記事をあとから編集して違反が入っても誰も検出しない。`commit-this` に `lint:svx:syntax`（2秒・トークン0）を足せば埋まるが、今回の契機は公開時のみと決めたため、意図的に空けている。

## 非機能要件

- **パフォーマンス** — `lint:svx:syntax` は全172記事で2.3秒。CG記事68件なら1秒未満。収束のため2〜3パス回しても数秒。公開時ゲートに入れても体感に影響しない。
- **トークン消費** — 自動実行される部分（`--fix` の収束）はシェル実行のみで、LLM の読解を伴わない。現行スキルの通読・インベントリ作成が消えるぶん、大幅に減る。
- **アクセシビリティ・モバイル・SEO** — 該当なし（記事本文の記法のみで、レンダリング結果の意味は変わらない）。
- **可読性の担保** — 自動修正の差分はコミットの許可プロンプトで人間が確認する。

## 制約

- **ルールの正典は `writing-guides/math-notation-guide.md`。** ルールを増やすときはガイドを先に直す。textlint 側にガイドに無いルールを持ち込まない。
- **`.svx` と `.textlintignore` の変更だけなので `npm run check` は実行しない**（CLAUDE.md「品質チェック」）。ただし `scripts/sync-tasklists.mjs` と `textlint/rules/*.js` を変更したときは、それぞれの動作確認を行う。
- **`npm run lint:svx:fix` は全記事に及ぶ。** スキルから当てるときは対象記事のパスを明示する。
- **ベースラインを無効にする `--ignore-path /dev/null` を、対象記事だけの検査で忘れない。**
- **textlint のフィクサは1パスでは収束しない。** ルール間の連鎖を前提に設計する。
- **`scripts/` の依存（`yaml`）は `scripts/package.json` にある。** 未インストールなら `scripts/` で `npm install`。

## 受け入れ条件

1. `npm run lint:svx:syntax` に含まれるすべてのルールが、`--fix` を収束させれば0件になる（「自動修正できない指摘は syntax パスに置かない」原則が守られている）。
2. `npm run lint:svx:fix` が収束するまで繰り返し、実行後に `lint:svx:syntax` が0件になる。
3. 新ルールを全記事に効かせた状態で、`lint:svx:syntax` が緑になる（現在緑の非CG記事2件・CG記事1件を直したうえで）。
4. 昇格ルールが、整備済みCG記事10件（`.textlintignore` から既に外した記事）に対して**1件も誤検出しない**。
5. 降格ルールが advisory パスに出る件数が、CGスコープで一桁に収まる（素朴実装の432件から減っていること）。
6. `node scripts/sync-tasklists.mjs --check` が3枚のタスクリストすべてで差分なしになる。
7. タスクリストの `[x]` が `app/.textlintignore` の内容と常に一致する。
8. CG記事を新規作成して `sync-tasklists.mjs --write` を回すと、タスクリストに行が自動で足される。
9. `draft: true` を外したCG記事に対して `/commit-this` を実行すると、記法ゲートが発火し、`format-math-notation` が自動実行され、記法整備のコミットが公開コミットより前に作られ、それぞれ許可プロンプトが出る。
10. 移行完了時点で、CG記事の `.textlintignore` 掲載が0件になり、タスクリストのCGセクションが全て `[x]` になる。
