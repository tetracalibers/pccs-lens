# スタイルガイドのコンパクト化

## 目的・背景

`author-style-writer` が執筆時に読むスタイルガイドが4ファイル計 **313,714字（242ルール）** に達し、コンテキストを圧迫している。日本語は概ね1文字≈1トークン前後なので、ガイドだけで20万トークン級となり、コンテキスト窓に匹敵する。

内訳を測ると、**実行可能な指示（ルール＋適用条件）は全体の16%**で、**分析メタデータが66%**を占める。

| 項目 | 文字数 | 比率 |
| --- | ---: | ---: |
| 根拠 | 82,442 | 27.1% |
| 確度 | 57,321 | 18.9% |
| 関連ルール | 34,237 | 11.3% |
| 反例・例外 | 26,073 | 8.6% |
| ルール（本体） | 24,370 | 8.0% |
| 適用する／しない状況 | 24,465 | 8.1% |
| その他（対象・記事タイプ・ファイル固有項目・見出し等） | 54,806 | 18.0% |

ファイル別の内訳:

| ファイル | 文字数 | ルール数 |
| --- | ---: | ---: |
| `writing-style.md` | 94,478 | 78 |
| `stylistic-quirks.md` | 80,359 | 72 |
| `thinking-flow.md` | 69,121 | 58 |
| `refine-style.md` | 59,752 | 34 |

### 原因

`author-style-analyzer` の差分更新手順が「確度・根拠に追記する」形になっているため、両欄が**分析回ごとに追記される追記専用（append-only）の台帳**になっている。

例（`writing-style.md`「総括・まとめの節を設けない」の確度欄は単一で3,201字）:

> 配色技法シリーズ10本すべてが…／混色シリーズ6本も…／デジタル画像シリーズ5本も…／CG・幾何変換シリーズ5本も…／色彩史の通史も…／色の活用分野でも…（以下、分析回ごとに追記が続く）

執筆側にとってこれは「強い傾向」の一語で足りる。

### 放置した場合の見通し

`writing-style.md` の行数は20回の分析ラウンドを通じて線形に増え、最終ラウンドでもなお `+59/−22` 行。分析済み85記事に対し **未作成436記事** が控えているため、執筆側の量が記事数に比例する現構造のままでは、一度掃除しても元に戻る。

**目標とする構造：執筆側の量はルール数に比例し、記事数に比例しない。**

## スコープ

### やること

1. **確度・根拠の分離** — 分析時にしか使わない情報を執筆側のファイルから除去する
2. **埋もれた制約の昇格** — 根拠・確度の散文に埋もれている実行可能な制約を、ルール欄・適用条件欄へ引き上げる
3. **記事→ルールの逆引きインデックス導入** — 根拠を正規化し、記事単位の再分析を可能にする
4. **モード別の読み分け** — `author-style-writer` が、モードに応じて必要なガイドだけ読む
5. **両スキルの契約改訂** — `author-style-analyzer` の出力契約と `author-style-writer` の参照指示を更新

### やらないこと

- **ルールの統合・削減**（242ルールの本数は変えない）。統合判断の材料は、圧縮後のガイドで実際に何本か書いてみないと得られない。根拠を捨てた後では統合ミスを検証できなくなるため、今回は本数に手を付けない
- **記事タイプ別のファイル分割**。`writing-style.md` 78ルールのうち72件（92%）が「概念解説」を含み、記事タイプの値は78ルールに対して41種類の自由記述であるため、機械的に振り分けられない
- **確度によるファイル分割**。確度は「著者固有性の強さ」の指標で「使用頻度」の指標ではないため、実用上おかしな結果になる（`refine-style.md` の核が3ルールしか残らず、編集モードの主力である「箇条書き→散文」「指示語・主語の明示化」が条件付き側へ落ちる。`writing-style.md` では全記事で使う「導入：本題の前に位置づけを提示する」が条件付き側へ落ちる）
- **進行的開示の高度化**（索引を読ませて writer に選ばせる方式）。スタイルガイドは「まとめ節を置かない」のような*不在*の制約が多く、存在を知らない制約は索引から引けない。生成モードでは全ガイドを読ませ、品質を優先する
- **既存ルールの内容変更**（昇格を除く）。文体の判断そのものは変えない

## ユーザーストーリー・主要ユースケース

- 著者が新規記事を書かせるとき、writer は4ガイド全部を読む（品質優先。約132,000字）
- 著者が公開済み記事に修正を依頼するとき、writer は `refine-style.md` と `stylistic-quirks.md` だけ読む（約60,000字）。局所的な言い回しの修正なら `refine-style.md` のみ（約32,000字）
- 著者が analyzer で新記事を分析するとき、analyzer はルールファイルと `evidence/<観点>.md` を読み、両方を更新する
- **（新規）著者が既に分析済みの記事を改稿したあと、その記事だけ再分析できる** — `evidence/<観点>.md` の当該記事ブロックを消して書き直すことで、古い根拠の撤回が原子的に行える

### 再分析が必要な理由（実例）

`/color-fields/landscape-color-approach`（景観色彩の考え方）は 2026-07-19 08:53 に分析され、2026-07-28 06:55 に本文が改稿されている（「依頼に基づき景観法の記述を独立ページへのリンクに変更」）。現在ガイドに載っている同記事由来の根拠は、すでに現物と一致していない。

`author-style-writer` には編集モードがあり、CLAUDE.md は公開後の人手修正のコミット規約まで定めているため、記事の改稿は定常的に発生する。

### 現構造では再分析ができない

再分析は「足す」だけでなく**「撤回する」**操作を含む。記事 X がルール R を支持していて、改稿で R が成り立たなくなったら、R の根拠から X を取り除いて確度を再評価する必要がある。

現在の設計では根拠がルール側に散文で分散しているため、X を撤回するには242ルールの散文を横断して X の記述だけを外科手術的に取り除く必要がある。しかも「配色技法シリーズ10本すべてが〜」のような集約表現は1本分だけ減らせない。**根拠を別ファイルへ移すだけでは解決しない**（台帳が依然としてルール単位で組まれているため）。

解決するには、根拠を**記事単位**に持ち替える（正規化する）必要がある。

## 機能要件

### ファイル構成

```
writing-guides/
├── syntax-guide.md        約10,000字         ★全モード必須（変更しない）
├── thinking-flow.md        31,644字 58ルール   生成モードのみ
├── writing-style.md        40,909字 78ルール   生成・推敲
├── stylistic-quirks.md     27,987字 72ルール   生成・推敲・編集
├── refine-style.md         21,691字 34ルール   生成・推敲・編集
├── evidence/              約35,000字          analyzer専用（writerは読まない）
│   ├── thinking-flow.md
│   ├── writing-style.md
│   ├── stylistic-quirks.md
│   └── refine-style.md
└── pending/               現状どおり           analyzer専用（現状も読まない）
```

### ルールの記述形式（改訂後）

執筆側に残す項目:

- 対象 / ルール / 適用する状況 / 適用しない状況 / 記事タイプ / 配置位置 / 構成上の効果
- 表現 / 使用目的 / 使用されやすい文脈 / 過剰使用への注意（`stylistic-quirks.md`）
- 認識する問題 / 選択する説明戦略 / 読者に起こそうとする理解の変化 / 次の判断へ進む条件（`thinking-flow.md`）
- 修正前の特徴 / 修正後の傾向 / 修正操作 / 修正の目的 / 差分の種類（`refine-style.md`）
- **確度：ラベルの3語のみ**（`強い傾向` / `条件付きの傾向` / `弱い傾向`）
- **反例・例外：一般化できるものは「適用しない状況」へ吸収する。記事固有の反例は執筆側に残さない**
- **関連ルール：裸の参照のみ**（`→ thinking-flow.md「◯◯」`）。`pending/` への参照は削除する

執筆側から除去する項目:

- **根拠：全部**（→ `evidence/<観点>.md`）
- **確度の判定理由：全部**（→ `evidence/<観点>.md`）

`pending/` 参照を削除する理由は、`author-style-writer` の SKILL.md が既に「たどって読む必要はない」と明言しており、執筆側には純粋なノイズであるため。

### 確度をラベルとして残す理由

`references/output-contract-analysis.md` に「弱い傾向は、生成時に積極的に適用するルールとして扱わない」とある。執筆側は「このルールをどのくらい強く当てるか」を知る必要があるため、ラベルは残す。一方「なぜその確度なのか」は、次の分析ラウンドで確度を上げ下げするときにしか使わないため除去する。

### 変換の実例

現状（`stylistic-quirks.md` の実物、1,893字）:

```markdown
### ヘッジ文末：主観・一般則を和らげる

- 表現：「〜傾向があります」「〜こともあります」「〜かもしれません」「〜でしょう」。
- ルール：一般則や主観的な色の印象を述べるときは断定せず、これらのヘッジ文末で和らげる。
  一方で、定義そのもの・表色系のルール・手順の指示は「〜です」「〜します」で断定する。
- 使用目的：例外や個人差のある事柄で言い切りを避けつつ、確定した定義とは register を分ける。
- 使用されやすい文脈：例外・個人差のある一般則、主観的な印象。
- 適用しない状況：定義・表色系のルール・手順の指示は断定する。
- 確度：強い傾向（直接確認できる事実）。色の理論5記事以上で多数確認でき…    ← 221字
- 根拠：「異なる傾向があります」「大まかに明度を表すこともあります」／CG基礎
  「生じることがあります」…照明・光源シリーズでも…色のはたらき方シリーズでも
  …色覚シリーズは…一方インテリア・照明の分野解説シリーズは3記事とも0件で…  ← 1,307字
- 過剰使用への注意：ヘッジ自体は一般技法。…
```

改訂後（約440字、77%削減）:

```markdown
### ヘッジ文末：主観・一般則を和らげる

- 確度：強い傾向
- 表現：「〜傾向があります」「〜こともあります」「〜かもしれません」「〜でしょう」。
- ルール：一般則・主観的な印象・例外や付随ケースを述べるときは断定せず、
  これらのヘッジ文末で和らげる。
- 適用しない状況：定義・分類・表色系のルール・手順の指示・装置や処理の機能説明は
  「〜です」「〜します」で断定する。確定した割合や分類も言い切る。
- 使用量：1段落に2回以上重ねない。
- 変種：著者自身の推測を述べる場面がない記事タイプでは、助動詞ヘッジ
  （でしょう／かもしれません）を使わず、量化・程度限定の語で和らげる。
- 過剰使用への注意：ヘッジ自体は一般技法。語尾の列挙ではなく
  「何を和らげ、何を断定するか」の使い分けとして運用する。
```

「使用量」「変種」、および「適用しない状況」への追記は、**現状は根拠1,307字の中に埋もれていて、ルール欄・適用条件欄には書かれていなかった**もの。これが「昇格」の実体である。

同様の例として `stylistic-quirks.md`「双方向の括弧グロス」の根拠3,349字には、次の実行可能な制約が埋もれている。

- 括弧の中身は名詞句か短い述部に抑え、句点を打たない
- 1文に括弧注を2つ以上入れるのは対句のときだけ
- 文相当の長さの補足は `:::Note` / TermCard へ逃がす
- 用語カードで定義する語・内部リンクで委ねる語には付けない

**根拠欄をスクリプトで機械的に切り落とすと、これらが一緒に失われる。**

### `evidence/<観点>.md` の形式

観点ごとに1ファイルとし、記事 slug をキーにする（`evidence/stylistic-quirks.md` の例）:

```markdown
## /color-theory/color-vision-types
- ヘッジ文末：主観・一般則を和らげる
- 双方向の括弧グロス

## /color-fields/interior-design-basics
- 双方向の括弧グロス
  ※ ヘッジ文末は反例（助動詞ヘッジ0件）
```

- キーは記事 slug（記事名ではない）
- 値はその観点の支持ルール名リスト。反例は `※` で注記する
- **確度は導出値**：ルールを支持する記事数・記事タイプの幅は、これを数えて算出する
- 記事を再分析するときは、各ファイルの当該記事ブロックを丸ごと消して書き直す（他の記事のエントリに触らない）

#### 単一ファイルにしない理由

記事 slug をキーにするため、1ファイルにまとめると移行時に**毎フェーズで既存インデックス全体を読んでから追記する**必要が生じ、後半のフェーズほど重くなる（最終的に約35,000字）。観点ごとに分ければ、各フェーズは自分の1ファイルだけを書けばよく、マージが発生しない。

代償として、記事1本の再分析で4ファイルを触ることになるが、analyzer はもともと4ガイドを並行更新する設計なので対称的である。

### 移行手順

根拠を捨てる前にしか記事名を抽出できないため、順序に制約がある。

1. **抽出と昇格を1パスで行う** — 各ルールの根拠・確度を読み、(a) 記事名を `evidence/<観点>.md` へ登録し、(b) 埋もれた制約をルール欄・適用条件欄へ昇格させる
2. **根拠・確度の散文を削除**し、確度をラベルのみに置換する
3. **反例・関連ルールを圧縮**する（一般化できる反例は「適用しない状況」へ吸収、関連ルールは裸の参照へ、`pending/` 参照は削除）
4. **`author-style-analyzer` の契約を改訂**する
5. **`author-style-writer` の参照指示を改訂**する

手順1〜3は242ルールを1件ずつ読む必要があるため、`##` セクション単位でチャンク分割して進める。

### スキル改訂の内容

`author-style-analyzer`:

- `references/output-contract.md`「根拠の記載方法」を、ルール欄への記述から `evidence/<観点>.md` への登録に変更する
- 同「ルールの基本形式」から `根拠` 欄を削除し、`確度` はラベルのみと規定する
- 同「既存ファイルの更新規則」に**再分析（記事単位の撤回）**の手順を追加する
- 同「最終検証」の根拠・確度の項を、インデックス側を検証する形に改める
- `SKILL.md` の出力先に `writing-guides/evidence/<観点>.md`（4ファイル）を追加する

`author-style-writer`:

- 「参照するスタイルガイド」をモード別の表に置き換える
- `evidence/` を読まないことを、`pending/` と同じ強さで明記する
- 各ワークフローステップの参照先を、モード別の読み込み範囲と整合させる

## 既存機能との関係・整合

- **`pending/` の仕組みは変更しない。** 保留プールは「主要ルールに採用していない観察」を置く場所で、今回の `evidence/` は「採用済みルールの根拠」を置く場所。役割が異なる
- **`STYLE-ANALYSIS-TASKLIST.md` は変更しない。** 記事単位の分析済み判定は現状どおり。再分析が必要な記事の検出は、改稿時に `[x]` を外す運用で足りる（今回のスコープ外だが、将来の入口として整合させておく）
- **確度によるファイル移動は発生しない。** 確度で割らないため、`条件付き→強い傾向` の昇格でルールがファイル間を移動することはない
- **`syntax-guide.md` は変更しない。** 記法・書式の必須ルールであり、文体ガイドとは性質が異なる

## ドメインルール上の考慮

`references/output-contract.md` および `output-contract-analysis.md` が定める分析の原則と矛盾しないこと。

- **「根拠と反例を追跡できるか」（最終検証）** — 追跡先をルール欄から `evidence/<観点>.md` へ移す。追跡可能性は失わない
- **「同一シリーズへの偏り」の判定** — インデックスから記事 slug の分布を数えることで判定できる
- **「同じルールを複数箇所へ記載しない」** — 核と条件付きに分割しないため、この原則に触れない
- **「成果物は『どの記事を分析したか』の記録ではなく再利用可能なスタイルガイドとする」（SKILL.md 注意事項）** — 現状はこの原則が「ガイドの目的」節だけを守っており、根拠・確度欄へ分析対象の記録が流れ込んでいた。今回の分離はこの原則をルール欄にも及ぼすもの
- **誤読の巻き戻し** — 移行前の根拠散文は git 履歴に残る。各分析ラウンドは1コミットで、コミットメッセージに記事名が入っているため、`git log -S "ルール名" -- writing-guides/` で辿れる

## データ・状態

- 永続化するのは Markdown ファイルのみ。アプリのコードには一切触れない
- `evidence/` 配下の4ファイルは analyzer が読み書きする唯一の可変状態。writer は読まない
- 確度ラベルはルールファイルに保持するが、判定理由は保持しない（インデックスから再導出する）
- 根拠の件数・記事タイプの幅はルールファイルに書かない（導出値であり、書くと再び追記対象になる）

## エッジケース・異常系

- **記事名から slug が引けない場合** — 現状の根拠には「配色技法シリーズ10本すべて」のような集約表現があり、個別記事へ展開できない。この場合はシリーズ名のままの暫定エントリを置き、当該記事を再分析した時点で正しい slug へ置き換える。**移行時のインデックスは不完全でよい**（再分析時にどうせ上書きするため、不完全な初期値で困らない）
- **記事が削除された場合** — インデックスから当該ブロックを削除する。確度は導出値なので自動的に追随する
- **記事タイプの値が自由記述で統制されていない** — 今回は正規化しない（41種のまま残す）。記事タイプでの分割をしないため実害がない
- **writer が `evidence/` を誤って読む** — `pending/` と同じ強さの禁止を SKILL.md に明記する
- **弱い傾向10件の扱い** — 執筆側のルールファイルに**残す**（`確度：弱い傾向` ラベル付き）。外す削減効果は約3,000字にとどまる一方、`pending/` とも異なる第3のプールが生まれて運用が複雑になるため
- **昇格した制約が既存の適用条件と矛盾する場合** — 矛盾を勝手に解消せず、著者に提示して判断を仰ぐ

## 非機能要件

読み込み量の目標:

| モード | 読むファイル | 目標 | 現状比 |
| --- | --- | ---: | ---: |
| 生成 | syntax + 4ガイド | 132,000字以下 | 42% |
| 推敲 | syntax + writing-style + stylistic-quirks + refine-style | 101,000字以下 | 32% |
| 編集 | syntax + refine-style + stylistic-quirks | 60,000字以下 | 19% |
| 編集・最小 | syntax + refine-style | 32,000字以下 | 10% |

現状はどのモードでも 313,714字を読み込んでいる。

将来の増加率: 執筆側の量が**ルール数に比例し、記事数に比例しない**こと。436記事を分析しても執筆側は増えない構造にする。

## 制約

- **根拠を捨てる前にしか記事名を抽出できない** — 移行手順1と2の順序は入れ替えられない
- **昇格はスクリプトで自動化できない** — 根拠の散文から実行可能な制約を見分けるのは意味の判断であり、242ルールを1件ずつ読む必要がある。ここが作業量の本体
- Markdown ファイルのみの変更のため、`npm run check` は実行しない（CLAUDE.md の品質チェック基準に従う）
- コミットは `[skip ci]` の対象（ドキュメント・スキルのみの変更）。ただし未 push のコミットにアプリの実行・ビルドに関わる変更が同居する場合は付けない

## 受け入れ条件

1. 4ガイドの合計が **132,231字以下**であり、各ルールに `根拠` 欄が存在せず、`確度` 欄がラベル3語のみである
2. `evidence/` 配下に観点ごとの4ファイルが存在し、記事 slug をキーとして支持ルールを列挙している
3. `author-style-writer` の SKILL.md にモード別の読み込み範囲が明記され、`evidence/` を読まない旨が `pending/` と同じ強さで書かれている
4. `author-style-analyzer` の出力契約に、記事単位の再分析（撤回）手順が記述されている
5. **昇格の検証** — 移行の各チャンクで、根拠から昇格させた制約を差分として提示し、著者が確認する
6. **品質の検証** — 圧縮後のガイドで記事を1〜2本書かせ、著者が文体の再現度を判断する。劣化が認められた場合、どのルールの情報が失われたかを特定して補う
