# author-style-analyzer の実行コスト削減

## 目的・背景

`author-style-analyzer` スキルの1回の実行が、実行時間・トークン使用量ともに過大になっている。あわせて Workflow のエージェント数に関する警告が出る。

ただし `/config` の Dynamic workflow size は確認の結果デフォルト（15体未満）であり、**現行の13体はガイドラインの内側**だった。したがってエージェント数の削減は警告を消すための対策ではなく、実行時間とトークン使用量を削った結果として得られるものと位置づける。警告の出どころは特定できていない（未確定・保留事項を参照）。

### 現状のコスト構造（実測）

Workflow スクリプト `references/analysis-workflow.js` は3ステージ・計13エージェントを起動する。

| ステージ | エージェント数 | モデル・effort |
| --- | ---: | --- |
| Stage1 独立分析（4観点） | 4 | 継承 / high |
| Stage2 反証（4）＋境界レビュー（1） | 5 | sonnet / medium・high |
| Stage3 統合（4観点） | 4 | 継承 / high |

トークンの大半は Stage3 に集中している。統合エージェントは自分の観点の「ガイド本体・根拠インデックス・保留プール」の3ファイルを全文 Read するため、4体合計で次の量を読む。

| 種別 | 字数 | 内訳 |
| --- | ---: | --- |
| ガイド本体 4ファイル | 160,345 | writing-style 54,824 / thinking-flow 41,120 / stylistic-quirks 38,129 / refine-style 26,272 |
| `evidence/` 4ファイル | 174,970 | writing-style 54,192 / stylistic-quirks 44,848 / thinking-flow 41,858 / refine-style 34,072 |
| `pending/` 4ファイル | 146,537 | stylistic-quirks 39,751 / thinking-flow 39,307 / writing-style 38,717 / refine-style 28,762 |
| 合計 | **481,852** | |

これに `output-contract.md`（約1.5万字）を4体が全文 Read し、Stage1・Stage2 の構造化出力（4観点分の特徴 JSON・反証判定・境界判定）が4体すべてのプロンプトへ埋め込まれる。日本語は概ね1文字≈1トークンのため、Stage3 だけで入力50万トークン級になる。

**エージェント数も読み込み量も分析対象の記事数に比例しない。** 記事1本を分析する回でも13体が起動し、同じ量を読む。

### 構造上の問題

#### 1. `pending/` が追記専用の倉庫になっている

`pending/` は4ファイル計510項目・146,537字。採用済みルール251件の2倍の「保留」が溜まっている。Git 履歴を見ると直近8ラウンドすべてで挙動が同じで、1ラウンドあたり70〜90行が追加され、削除は0〜8行にとどまる。

```
608508c3  +16/-2   +16/-3   +23/-1   +15/-0     ← pending 4ファイルの 追加/削除 行数
e28a149c  +16/-2   +16/-1   +24/-0   +13/-0
b6922f13  +18/-8   +19/-4   +16/-2   +18/-3
d98ef1cd  +11/-5   +24/-5   +30/-3   +17/-2
```

SKILL.md は「①昇格②追記③棄却の対象とする」と規定しているが、実態は①③がほぼ動いていない。原因は形式にある。1項目が200〜400字の散文で、昇格の鍵になる支持記事数が文中に溶けているため、判定するには全文を読むしかない。

`spec/writing-guides-compaction.md` がガイド本体から追い出した追記専用台帳が、`pending/` で再発している状態である。

#### 2. ルール名がキーとして機能していない

SKILL.md は「ルール名は本体の `###` 見出しと一字一句一致させます（揺れると追跡できません）」と規定しているが、実際には短縮形で書かれている。

```
本体の見出し   ### 推奨・評価の文末「効果的です／効果を発揮します」
evidence の行  - 推奨・評価の文末（「特に、高彩度のトーンを使うと…効果的です」）
```

ルール名で機械的に照合すると stylistic-quirks の76ルール中22件が「支持0件」と出る。現状は統合エージェントが全文を読んで人間的に照合しているため破綻が表面化していないが、**支持記事数を機械集計する設計はこのキーの上に乗る**ため、先に解決が必要になる。

#### 3. 確度ラベルが支持記事数と相関していない

```
=== writing-style : ルール79 / evidenceブロック86 ===
  強い傾向: 12件        支持記事数 min=2  中央値=8  max=59
  条件付きの傾向: 59件  支持記事数 min=1  中央値=4  max=29
  弱い傾向: 8件         支持記事数 min=1  中央値=2  max=6
```

全ルールの約7割が「条件付きの傾向」に入り、その中に支持1記事のものと29記事のものが同居している。「条件付き」は件数ではなく**記事タイプが限定される**という別軸を表しているため、件数だけの閾値で機械導出するとラベルが大量に動く。なお記事タイプは `evidence/` に記録されていない（`分析時点` の SHA のみ）ため、現状では第2軸を機械集計できない。

#### 4. 分析の目的が2種類あるのに手順が1つしかない

文体解析タスクリストは88記事が `[x]`、未分析は4記事。この段階では「新しく書いた記事が既存ルールを支持するか記録する」ことと「溜まった根拠からガイドを見直す」ことは別の作業だが、いまはどちらも同じフルパイプラインを通る。

## スコープ

### やること

- `evidence/` を記事単位のファイルへ分割する
- ルールへ安定 ID を導入する
- `pending/` を1項目1行の構造に変える
- 確度の降格のみを機械化する
- 実行を「根拠モード」「発見モード」の2つに分ける
- 根拠モードの `evidence/` 生成をスクリプト化する
- Workflow の進行制御をパイプライン化し、境界レビューを後段へ移す
- 上記に伴う既存データの移行

### やらないこと

- ガイド本体の内容そのものの見直し・再圧縮（`spec/writing-guides-compaction.md` の残タスクは本仕様の対象外）
- `author-style-writer` の読み込み範囲の変更（本体4ファイルを読む方式は維持する）
- 分析の観点を4つから増減すること
- 記事本文の読み込みを4観点で共有すること（独立分析の原則を優先し、重複読み込みは許容する）
- 確度の昇格の機械化

## ユーザーストーリー・主要ユースケース

1. **記事を1〜数本公開した直後**：`/author-style-analyzer <slug>` を実行し、その記事が既存ルールのどれを支持するかを記録する。ガイド本体は変わらない。軽く速い。
2. **カテゴリ・セクション単位でまとめて分析するとき**：`/author-style-analyzer #cg-basics --discover` を実行し、記事から特徴を抽出したうえで、保留の昇格・新規ルールの採用・確度の見直しまで行う。
3. **記事を追加せずガイドを整理したいとき**：`/author-style-analyzer --discover` を実行し、溜まった保留と支持記事数の集計だけを材料に棚卸しする。
4. **公開後に改稿した記事を追いかけるとき**：`evidence/` に記録された `分析時点` と現在のコミットを比べ、変わっている記事を再分析する（既存手順を維持）。

## 機能要件

### 1. 2つのモード

| | 根拠モード（既定） | 発見モード（`--discover`） |
| --- | --- | --- |
| 目的 | 記事が既存ルールを支持するかを記録する | ガイドそのものを見直す |
| 書き込み権限 | `evidence/` のみ | 本体・`evidence/`・`pending/` の3層 |
| 新しい特徴 | `pending/` へ1行で積む | 昇格・採用を判断する |
| ガイド本体 | 触らない（確度の降格を除く） | 更新する |
| 境界レビュー | 実行しない | 実行する |
| 記事指定なしの実行 | 不可 | 可（棚卸しのみ） |
| エージェント数 | 8体（Git 履歴なしなら6体） | 10〜13体 |

呼び出し形式：

```
/author-style-analyzer #cg-basics              → 根拠モード（既定）
/author-style-analyzer #cg-basics --discover   → 発見モード
/author-style-analyzer --discover              → 棚卸しのみ（記事を読まない）
```

**根拠モードでも発見は起きる。** 変わるのは「見つけた特徴をその場で本体に入れるかどうか」だけで、根拠モードでは `pending/` に積み、採用の判断を発見モードへまとめる。発見の機会を捨てる設計ではない。

### 2. 根拠モードの手順

1. **前処理（メインセッション）**：スコープを解決し、ガイド本体4ファイルから `### [ID] ルール名` を抽出してルールID一覧（251行・約1万字）を作る。各記事の `分析時点` SHA を `git log -1 --format=%h` で確定する。
2. **判定（観点ごと4体・Git 履歴が無い回は refine-style を起動しない）**：ルールID一覧と記事本文を渡し、「この記事がどのルールIDを支持するか／反例か／該当しないか」を構造化出力で返させる。**ガイド本体・`evidence/`・`pending/` は読ませない。**
3. **反証（観点ごと4体）**：過剰な当てはめを弾く。独立したエージェントとして残す。
4. **記帳（スクリプト）**：判定の構造化出力から `evidence/<観点>/<slug>.md` を機械生成する。統合エージェントは起動しない。
5. **確度の降格（スクリプト＋メインセッション）**：支持が2記事以下に落ちたルールを検出し、該当ルールの `確度` 欄のみ「弱い傾向」へ更新する。該当が無ければ本体は一切変更しない。
6. **新特徴の記録**：判定で挙がった既存ルールに当てはまらない特徴を、`pending/` へ1行で追記する。
7. **後処理**：タスクリストの更新、報告。報告には**昇格候補の件数と未処理の保留件数**を必ず含め、閾値を超えていれば発見モードの実行を推奨する。

### 3. 発見モードの手順

1. **前処理**：根拠モードと同じスコープ解決に加え、`grep -rl "<ID>" evidence/<観点>/` でルールごとの支持記事数を集計し、`pending/` から昇格候補（支持が閾値以上の保留）を抽出する。
2. **分析（観点ごと4体）**：現行 Stage1 と同じ深さで特徴を抽出する。
3. **反証（観点ごと4体）**：現行 Stage2 の Evidence Reviewer と同じ。
4. **統合（観点ごと4体）**：ガイド本体・`evidence/`・`pending/` を更新する。渡すのは**自観点の特徴 JSON のみ**（他観点の特徴は渡さない）。
5. **境界レビュー（1体・後段）**：書き上がった4ファイルを読み、重複・配置の誤りを検出して報告する。
6. **後処理**：タスクリストの更新、報告。

2〜4は観点ごとのパイプラインとして流す（バリアを張らない）。

### 4. 進行制御

- 現行の「4分析が全部終わる→反証が全部終わる→統合」の3段バリアをやめ、観点ごとに `分析→反証→統合` を独立して流す。
- 4観点を揃える必要があるのは境界レビューだけなので、これを統合の後段へ移す。重複・配置誤りの解決は「書く前の事前回避」から「書いた後の事後検出」に変わる。検出結果は報告し、修正は次のラウンドまたは個別の指示で行う。
- `gitAnalyzable` が空の回は Revision Diff Analyst の系列（分析・反証・統合）を起動しない。現行スクリプトは Git 履歴が1本も無くても起動し、「確認できないと明記する」だけの仕事をさせている。`evidence/refine-style` のブロック数は45で、他観点の86〜90に対して半分の記事にしか Git 差分の根拠がない。

### 5. `output-contract.md` の分割

統合エージェント4体が全文（約1.5万字）を Read している。観点別に必要な節へ分割し、各エージェントには自分の観点分＋共通規約だけを渡す。Stage1 で `ANALYSIS_CRITERIA` として実施済みの手法を統合側へ広げる。

## 既存機能との関係・整合

### `author-style-writer`

- 本体4ファイルを読む方式は変えない。見出しに `[WS-012]` の ID が付くが、writer は無視して読めばよい。
- SKILL.md の「読まないファイル（分析専用）」節に `evidence/thinking-flow.md` などのファイル名が列挙されているため、ディレクトリ形式（`evidence/<観点>/`）へ更新する。
- 本体内の `関連ルール` 参照は名前のまま残す（`→ writing-style.md「◯◯」`）。writer が読むファイルであり、ID だけでは人間が辿れないため。

### `spec/writing-guides-compaction.md`

- 本体からの根拠の分離という方針を引き継ぐ。本仕様はその続きとして、`pending/` と `evidence/` に同じ原則を適用する。
- 残タスク（4ガイド合計 132,231字以下の確認、圧縮後ガイドでの再現度検証）は本仕様の対象外だが、ID 付与作業と同時に本体を触るため、実施順序の調整が必要になる。

### `writing-guides/STYLE-ANALYSIS-TASKLIST.md`

- タスクリストの更新はスキル層（メインセッションの後処理）の責務という現行の切り分けを維持する。
- 根拠モードでも `[x]` を付ける（記事の分析は完了しているため）。

### `scripts/`

- `evidence/` 生成スクリプト・支持記事数の集計スクリプト・移行スクリプトは `scripts/` 配下に置く（`sync-tasklists.mjs` と同じ場所）。

## ドメインルール上の考慮

- 確度ラベル3語（強い傾向／条件付きの傾向／弱い傾向）の定義は変えない。機械化するのは「支持が2記事以下に落ちたルールを弱い傾向へ降格する」判定のみで、昇格と「条件付き」の判定は引き続きエージェントが行う。
- 4ガイドの責務分担（思考／構成／表現／修正）は変えない。
- 「ガイド本体の量はルール数に比例させ、記事数に比例させない」という原則を維持する。ID の付与は1ルールあたり10字程度の増加にとどまる。

## データ・状態

### `evidence/`（記事単位に分割）

```
writing-guides/evidence/
  writing-style/
    _README.md                          ← 凡例・根拠の性質に関する注意
    cg/basics/anti-aliasing.md
    color-theory/pccs-basics.md
    ...
  thinking-flow/
  stylistic-quirks/
  refine-style/
```

1記事のファイル：

```markdown
分析時点: `d8bd3563`
記事タイプ: 概念解説

- WS-012（末尾を結果要約「なめらかに見えるようになります」で閉じる）
- WS-034（前提記事へリンクし前回の欠落を述べてから問いへ）
  ※ WS-041：スーパーサンプリングは前手法の限界提示を伴わず、限界駆動が弱い
```

- 支持記事数は `grep -rl "WS-012" writing-guides/evidence/writing-style/ | wc -l` で求める。この値を確度の正とする。
- 記事タイプを記録する（現状は記録されていない）。将来2軸での確度導出へ戻す余地を残すため。
- 新規記事は Write のみ、再分析は該当1ファイルのみを読み書きする。

### ルールID

- 形式：観点略号2文字＋連番3桁。`TF`（thinking-flow）／`WS`（writing-style）／`SQ`（stylistic-quirks）／`RS`（refine-style）。
- 本体の見出し：`### [WS-012] 原理・自然現象を先頭節に置く総論先行構成`
- ルールを廃止したら欠番にする（採番の再利用はしない）。
- ルール名を改名しても ID は変えない。

### `pending/`（1項目1行）

```markdown
- SQ-P045｜支持2記事のみ・媒体機能への依存が大きい｜支持: /color-theory/color-area-proportion, /color-theory/hue-tone-difference
```

- 保留にも ID を振る（本体ルールと区別できる接尾辞を付ける）。昇格時に本体の ID へ置き換える。
- 昇格候補の抽出はメインセッションが行い、エージェントには候補だけを渡す。全文は読ませない。

## エッジケース・異常系

- **記事に Git 履歴（AI草稿コミット）が無い**：Revision Diff Analyst の系列を起動しない。報告に「refine-style は対象外」と明記する。
- **ルールID一覧と `evidence/` の ID が食い違う**（本体から削除されたルールの ID が `evidence/` に残っている）：集計スクリプトが検出して報告する。自動削除はしない。
- **確度の降格対象が0件**：ガイド本体を一切変更しない（根拠モードの通常ケース）。
- **再分析で支持記事が0になったルール**：降格ではなく廃止候補として報告する。自動削除はしない。
- **`--discover` に記事指定が無い**：記事を読まず、`pending/` の昇格候補と支持記事数の集計だけで棚卸しする。分析・反証のエージェントは起動しない。
- **判定エージェントが失敗した観点がある**：その観点の `evidence/` は生成せず、失敗を報告する。他観点は続行する（現行のフィルタ方針を維持）。
- **移行前のデータ形式が残っている**：ID を持たない本体・分割前の `evidence/` を検出したら、移行が未完了である旨を報告して停止する。

## 非機能要件

- **エージェント数**：根拠モードで8体以下、発見モードで13体以下（Workflow のガイドラインである15体未満を維持する）。根拠モードの8体は統合ステージをスクリプト化した結果であり、体数そのものを目標に設計を歪めない。
- **トークン**：根拠モードのファイル読み込みを1万字程度（ルールID一覧）＋記事本文に抑える。発見モードのファイル読み込みを現状の48.2万字から約20万字へ削減する。
- **実行時間**：観点ごとのパイプライン化により、壁時計を「各段の最遅の合計」から「最も遅い観点の合計」へ短縮する。
- **可観測性**：根拠モードの完了報告に、昇格候補の件数・未処理の保留件数を必ず含める。

## 制約

- `Edit` ツールは同一会話で Read 済みのファイルしか編集できない。「渡すだけで読ませない」は、書き込みが新規 Write または機械生成である場合にのみ成立する。`evidence/` の記事単位分割はこの制約への対処でもある。
- ガイド本体は差分更新のため Read が必要で、発見モードでは16万字の読み込みが残る。これを削るには本体自体の圧縮が必要で、本仕様の対象外とする。
- Workflow スクリプトでは `Date.now()` / `Math.random()` / 引数なしの `new Date()` が使えない。SHA・タイムスタンプはメインセッションが前処理で確定して渡す。
- 記事本文は4観点が独立して読むため、重複読み込みは削減しない（独立分析の原則を優先する）。

## 受け入れ条件

1. 根拠モードで記事1本を分析したとき、起動するエージェントが8体以下であること。
2. 根拠モードの実行で、ガイド本体4ファイルがエージェントに Read されないこと（確度の降格が発生した場合を除く）。
3. 根拠モードの実行で、`evidence/<観点>/<slug>.md` が4観点分（Git 履歴が無い記事は3観点分）生成され、`分析時点` の SHA が4ファイルで一致すること。
4. 発見モードの実行で、ガイド本体・`evidence/`・`pending/` の3層が更新され、境界レビューの結果が報告されること。
5. `grep -rl "<ID>" writing-guides/evidence/<観点>/ | wc -l` で求めた支持記事数が、全ルールについて0件でないこと（表記ゆれによる照合漏れが解消していること）。
