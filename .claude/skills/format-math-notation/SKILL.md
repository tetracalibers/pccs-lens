# 記事の数式・インラインコード記法の整備スキル (format-math-notation)

既存記事の本文を `writing-guides/math-notation-guide.md` の記法に沿った形に整える。

**ルールの正典はガイド側**で、このスキルが持つのは適用の手順（洗い出し → 判断 → 書き換え → 確認 → ベースラインの解除）だけである。作業前に `writing-guides/math-notation-guide.md` を必ず全文読む。**このファイルにルールを書き写して増やさない**（食い違ったらガイドを正とする）。

**直すのは記法だけで、文章には手を入れない。** 語順・言い回し・説明の順序・段落構成・見出し・`:Anki[]` / `:Mark[]` は変えない（それは `/author-style-writer` の編集モードの仕事）。表記の置き換えで文が読めなくなる場合は、直さずに報告する。

## 適用範囲

| 記事の種類 | パス |
| --- | --- |
| CG・画像処理 | `app/src/routes/cg/<ユニット>/<slug>/+page.svx` |
| 色の理論 | `app/src/routes/color-theory/<slug>/+page.svx` |
| 色の活用分野 | `app/src/routes/color-fields/<slug>/+page.svx` |

扱うのは `math-notation-guide.md` のルールだけ。次は対象外で、**ついでに直さない**（依頼されていない変更になる）。

- **`syntax-guide.md` 側の記法** — ディレクティブの使い分け、`:Anki[]` を付ける／外す、見出しの分類タグ、ボールド体の禁止、リンク、擬似コード。ただし**`:Anki[]` の中にインラインコードが書かれている場合**だけは、数字のルールの一部として直す（→ ガイド「数字は必ずインラインコードにする」）。
- **表記揺れ**（`app/textlint/prh.yml`・`npm run lint:svx:notation`） — 別の系統。指摘が出ていても、このスキルでは直さず件数を報告するだけにする。
- **文章・構成・強調・図版・デモ**。

## 引数

```
/format-math-notation <記事slug>[,<記事slug>…]
```

- **`<記事slug>`** — 対象記事の slug（例: `color-matching-and-grassmanns-law`・`basic-transformations`）。カンマ・空白区切りで複数渡せる。
- **複数渡された場合も、1記事ずつ手順2〜7を回す。** 記事ごとに方針の承認を取り、記事ごとに報告する（まとめて一気に書き換えない。差分が混ざるとレビューできない）。
- **引数なし** — セッションの文脈から対象を特定する。特定できなければ、ベースライン（`app/.textlintignore`）に残っている記事の一覧を提示して尋ねる。推測でどれかに決めない。

### 記事slugの解決

```bash
find app/src/routes/cg -maxdepth 2 -type d -name "<記事slug>"
find app/src/routes/color-theory app/src/routes/color-fields -maxdepth 1 -type d -name "<記事slug>"
```

- **0件なら該当ページが無い旨を伝えて中止する。複数件なら候補パスを提示して確認する。** 重複する slug は `transformation/basic-transformations` のようにユニット込みで渡してもらう。

## 前提（検査の仕組み）

`app/textlint/README.md` が正典。押さえておく点は次のとおり。

- **記法パス（`lint:svx:syntax`）はベースライン `app/.textlintignore` が効く。** ルール導入時点で違反を含んでいた既存記事は対象外になっているので、`npm run lint:svx` を回しても対象記事は緑に見える。**このスキルでは `--ignore-path /dev/null` でベースラインを無効にし、対象記事だけを検査する**（手順2）。
- **`npm run lint:svx:fix` は使わない。** 全記事に `--fix` が及ぶ。必ず対象記事のパスを明示して当てる（手順5）。
- 検査対象から外れる領域は `app/textlint/lib/svx.js` のマスクで決まる（コードブロック・インラインコードの中身・フロントマター・HTML/Svelte・見出し・ディレクティブ名／ラベル／属性・数式の中・リンクのURL）。**マスクされた場所の違反は textlint では出ないので、手順3で自分で見る。**

### textlint が見る4ルール

| ルール | 内容 | 自動修正 |
| --- | --- | --- |
| `svx-number-in-code` | 数字は必ずインラインコードにする | ○（英字に隣接する数字は報告のみ） |
| `svx-math-function-in-code` | 数学で定義されている関数名もインラインコードにする | ○（引数が続く形は報告のみ） |
| `svx-no-space-around-code` | インラインコードの前後には空白を置かない | ○ |
| `svx-inline-math-spacing` | インライン数式の前後には半角スペースを置く | ○ |

**出力の `✓` が付いた指摘だけが `--fix` で直る。** `✓` の無い指摘（`600nm`・`3DCG` のように英字へ隣接する数字、`sin(x)` のように引数が続く関数名）は、囲む範囲の判断が要るため手作業になる。

### textlint が見ないルール（手作業で拾う）

| ガイドの節 | 何を見るか |
| --- | --- |
| インライン数式はなるべく使わず、インラインコードで書く | KaTeX でしか書けない記号（ギリシャ文字・上下付き・`\equiv`・`\times`・`[R]` のような色記号）を含まない `$$…$$` |
| 同じ対象を表す記号は、インライン数式とインラインコードを混在させない | 記事全体での記号ごとの表記の揺れ |
| インライン数式を含む文では、数式・変数・関数名をインライン数式に統一する | 1文の中の `$$…$$` と `` `…` `` の混在（数字は対象外） |
| ブロック数式を説明する文では、その式の記号をインライン数式で書く | ブロック数式の前後で、その式の記号を指している文 |
| インライン数式の分数は `\dfrac` で書く | `$$…\frac…$$`・`$$…/…$$` |
| プライム記号は `^{\prime}` で書く | 数式の中のアポストロフィ `'` |
| ブロック数式の改行 | `\\`（2つ）のままの行末、`\frac` を含むブロックの `\\\\`（4つ） |
| `:Anki[]` の中では数字を囲まない | `:Anki[…`…`…]` |

## 手順

### 1. 対象を確定し、作業前の状態を確認する

- slug を解決してファイルパスを確定する（→「記事slugの解決」）。
- **対象記事に未コミットの差分が無いか確認する。**

  ```bash
  git status --porcelain -- app/src/routes/<...>/+page.svx
  ```

  差分があれば、このスキルの修正が混ざってレビューしにくくなる旨を伝え、続けてよいかを確認する（自分でコミットも退避もしない）。
- ベースラインに載っているかを見る（手順7でこの行を外す）。

  ```bash
  grep -n "<slug>/+page.svx" app/.textlintignore
  ```

- 記事を通読する。**この時点でどこを直すかを決めない**（手順2・3の洗い出しを踏まえて手順4でまとめて判断する）。

### 2. 機械的な違反を洗い出す（ベースライン無効）

```bash
cd app
npx textlint --rulesdir textlint/rules --ignore-path /dev/null src/routes/<...>/+page.svx
```

ルール別の件数と、`--fix` で直らない指摘を分けて数える。

```bash
# ルール別の件数
npx textlint --rulesdir textlint/rules --ignore-path /dev/null src/routes/<...>/+page.svx 2>&1 \
  | grep -oE 'svx-[a-z-]+' | sort | uniq -c

# --fix で直らない指摘（`✓` が付いていないもの）
npx textlint --rulesdir textlint/rules --ignore-path /dev/null src/routes/<...>/+page.svx 2>&1 \
  | grep error | grep -v '✓'
```

0件でも手順3へ進む（textlint が見ているのは4ルールだけなので、**エラー0件は記法ルールを満たした証明にはならない**）。

### 3. textlint が見ないルールの違反を洗い出す

grep で候補を機械的に集めてから、記事を読んで判断する。

```bash
cd app
F=src/routes/<...>/+page.svx

# インライン数式の一覧（KaTeX 必須記号を含まないものはインラインコードへ）
grep -noE '\$\$[^$]+\$\$' $F

# 数式の中のアポストロフィ（プライム記号）
grep -n "\$\$[^\$]*'" $F

# ブロック数式の行末の改行（`\\`2つのままの行、`\frac` を含むブロック）
grep -n '\\\\' $F
grep -n 'frac' $F

# `:Anki[]` の中のインラインコード
grep -noE ':Anki\[[^]]*`[^]]*\]' $F

# インラインコードの一覧（同じ対象の表記が混在していないかを見る）
grep -noE '`[^`]+`' $F | sed 's/^[0-9]*://' | sort | uniq -c | sort -rn
```

- **記号のインベントリを作る。** 記事に出てくる数学的対象（変数・行列・関数名・色記号）ごとに、インライン数式で書かれた箇所とインラインコードで書かれた箇所を数え、**どちらに寄せるか**を記事全体で1つ決める（→ ガイド「同じ対象を表す記号は…」）。
- **ブロック数式ごとに、その式を説明している文を探す。** その文の中の記号がインラインコードなら、インライン数式へ寄せる候補になる（数字は除く）。
- **文単位で混在を見る。** インライン数式を含む文にインラインコードの変数・関数名が残っていないか（数字は対象外）。

### 4. 修正方針を表で提示して承認を得る

**本文を書き換える前に、必ずここで止まる。**

| # | 行 | 現在 | 直した後 | 根拠（ガイドの節） | 区分 |
| - | -- | ---- | -------- | ------------------ | ---- |
| 1 | 34 | `画素値$$i$$を` | `画素値 $$i$$ を` | インライン数式の前後には半角スペースを置く | 自動修正 |
| 2 | 78 | `` `T` `` と `$$T^{-1}$$` の混在 | 両方インライン数式 | 同じ対象を表す記号は混在させない | 手作業 |

- 区分は**自動修正**（手順5の `--fix`）と**手作業**（手順6）に分ける。件数が多い自動修正は1行ずつ並べず、ルール別の件数でまとめてよい。手作業は1件ずつ挙げる。
- **判断が分かれるものは候補を併記して確認する。** 記事全体でどちらの表記に寄せるか、その `$$…$$` が KaTeX 必須記号を含むと見るか、`600nm` をどこまで囲むか、などは勝手に決めない。
- **迷ったら直さない。** すでに記事内で一貫している表記を好みで反対側へ寄せない。判断がつかない箇所は「保留」として表に残し、手順8で報告する。

### 5. 自動修正を当てる

```bash
cd app
npx textlint --rulesdir textlint/rules --ignore-path /dev/null --fix src/routes/<...>/+page.svx
```

- 直後に差分を確認する。

  ```bash
  git diff -- app/src/routes/<...>/+page.svx
  ```

- **コードブロック・ディレクティブの属性・リンクのURL・`:Anki[]` の中に修正が及んでいないか**を見る。及んでいたらその箇所だけ戻し、マスクの取りこぼしとして報告する（ルールの実装を直すのはこのスキルの仕事ではない）。
- `--fix` 後も残る指摘（`✓` の無かったもの）は手順6で手作業として扱う。

### 6. 手作業の修正を当てる

承認された表のとおりに、1ルールずつ直す。**置き換えに連鎖するルールを忘れない。**

- インラインコード → インライン数式にしたら、**前後に半角スペースを1つ入れる**（約物に接する側と行頭・行末は入れない）。
- インライン数式 → インラインコードにしたら、**前後のスペースを詰める**。
- インライン数式の中の分数は `\dfrac`、プライムは `^{\prime}`。
- 文単位の統一では**数字だけを対象外**にする（数字はインラインコードのまま）。
- `:Anki[]` の中の数字はバッククォートを外す。
- ブロック数式の行末は `\\\\`（4つ）、`\frac` を含むブロックは `\\\\\\\\`（8つ）。

**文章そのものは変えない。** 助詞の調整・言い換え・語順の入れ替えはしない。表記を置き換えると文意が崩れる箇所は、直さずに保留して報告する。

### 7. 検査して、ベースラインから外す

```bash
cd app
npx textlint --rulesdir textlint/rules --ignore-path /dev/null src/routes/<...>/+page.svx
```

- **0件になり、手順4の手作業分も片付いた場合だけ**、`app/.textlintignore` からその記事の行を削除する（`.textlintignore` 自身が「既存記事の記法を直したら行を削除する」と定めている運用）。削除するのは**対象記事の1行だけ**で、他の行に触らない。
- 削除したら、ベースラインを効かせた通しの検査で緑になることを確認する。

  ```bash
  npm run lint:svx:syntax
  ```

- **保留した箇所が残っている場合は行を外さない。** 外さない理由を手順8で報告する（取り繕って外さない）。
- 表記揺れは別系統なので、対象記事の件数だけ確認して報告に添える（直さない）。

  ```bash
  npx textlint --config .textlintrc.notation.json --ignore-path /dev/null src/routes/<...>/+page.svx
  ```

### 8. 報告する

- ルール別の修正件数（自動修正／手作業）と、記事全体で寄せた表記の統一先。
- 判断を確認した点とその結論。
- **保留した箇所と理由**（直さなかったものを黙って落とさない）。
- `app/.textlintignore` の行を外したか、外さなかった場合はその理由。
- 表記揺れの残件（件数のみ。このスキルでは直していないこと）。
- `git diff --stat` の結果。
- **コミットはしない。** 変更内容を報告して指示を待つ（コミットは `/commit-this`）。`.svx` と `.textlintignore` の変更だけなので `npm run check` は実行しない（CLAUDE.md「品質チェック」）。

## 注意事項

- **正典は `writing-guides/math-notation-guide.md`。** 作業前に全文を読み、判断はガイドの文言に照らす。ガイドに無いルールを「整えるついで」に持ち込まない。
- **記法だけを直す。** 文章・構成・強調・図版・デモには触らない。`:Anki[]` / `:Mark[]` は外さず、付け足しもしない。
- **本文の書き換えは手順4の承認を得てから。** 自動修正も承認の対象に含める（`--fix` は一括で本文を書き換えるため）。
- **`npm run lint:svx:fix` を使わない。** 全記事に及ぶ。対象記事のパスを明示して当てる。
- **ベースライン（`.textlintignore`）を無効にする `--ignore-path /dev/null` を忘れない。** 忘れると既存記事は緑に見え、違反を1件も拾えない。
- **エラー0件を根拠にしない。** textlint が見るのは4ルールだけで、インライン数式とインラインコードの選択・記事全体の統一・`\dfrac`・プライム記号・ブロック数式の改行は手作業で見る。
- **過剰修正しない。** 「なるべくインラインコード」を根拠に、KaTeX でしか書けない記号を含む数式をインラインコードへ落とさない。
- **1回の実行で複数記事を扱うときも、記事ごとに承認と報告を挟む。** 差分が混ざるとレビューできず、コミットも分けられない。
- ベースラインから行を外せた記事は、以降 `npm run lint:svx` で常に検査される。**外したあとに違反を残さない**（手順7の確認を飛ばさない）。
