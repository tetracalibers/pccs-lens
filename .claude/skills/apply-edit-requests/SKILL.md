# 記事の編集指示の一括対応スキル (apply-edit-requests)

記事本文に書き残した編集指示（`:::Add`・`:::Delete`・`:::Fix`）を、1回の実行でまとめて片付ける。

指示を書いたのは著者で、このスキルはそれを解釈して実行する側に立つ。**指示の中身を評価し直したり、書かれていない改善を持ち込んだりはしない。**

## 適用範囲

記事ページに残っている `:::Add` / `:::Delete` / `:::Fix` の一括処理。

| 記事の種類 | パス |
| --- | --- |
| CG・画像処理 | `app/src/routes/cg/<ユニット>/<slug>/+page.svx` |
| 色の理論 | `app/src/routes/color-theory/<slug>/+page.svx` |
| 色の活用分野 | `app/src/routes/color-fields/<slug>/+page.svx` |

対象外:

- **`:::Todo`** — 図版・デモが欲しい箇所の**新規**プレースホルダ。作成には配置先の相談やデモ案の提案が入るため、`/svg-diagram-component`・`/add-threejs-demo` を個別に呼ぶ。**このスキルは読み飛ばし、残っていても消さない**
- **`:::Pending`** — 採否を検討中の文章。中身は指示ではなく**候補の本文そのもの**で、採用・不採用を決めるのは著者。**このスキルは読み飛ばし、残っていても消さない**（採否が決まっていれば、著者が採用＝ブロックだけ外す／不採用＝囲んだ記述ごと削除する）
- **`::ComingSoon`** — 節そのものの未執筆マーカー。本文を書き起こす作業なので `/author-style-writer` の担当
- **1回の実行で扱うのは1記事だけ。** 複数記事の横断・リポジトリ全体の走査はしない

## 扱う編集指示

| ブロック | 中身 | 担当 | 対応後 |
| --- | --- | --- | --- |
| `:::Add` | 加筆の**指示** | `author-style-writer` | ブロックを、書いた文章に置き換える |
| `:::Delete` | 消す予定の**本文そのもの** | `author-style-writer` | 囲まれた記述ごとブロックを削除する |
| `:::Fix`（`target="text"`・既定） | 既存の文章への修正**指示** | `author-style-writer` | 指示を本文に反映し、ブロックを削除する |
| `:::Fix{target="svg"}` | 既存のSVG図解への修正**指示** | `svg-diagram-component` | コンポーネントを修正し、ブロックを削除する |
| `:::Fix{target="demo"}` | 既存のThree.jsデモへの修正**指示** | `add-threejs-demo` | デモを修正し、ブロックを削除する |

定義は `writing-guides/syntax-guide.md` ルール4が正典。作業前にこの節を読む。

**`:::Delete` だけは中身が指示ではなく、削除対象の記述そのもの**である点に注意する。中身を「消し方の指示」と読み違えて、記述を残したままブロックだけ外してはならない。

## 引数

```
/apply-edit-requests [<記事slug>]
```

- **`<記事slug>`（省略可）** — 対象記事の slug（例: `hidden-surface-removal-methods`・`pccs-color-system`）。省略時はセッションの文脈から特定し、特定できなければユーザーに尋ねる

### 記事slugの解決

3ルートを横断して探す。

```bash
find app/src/routes/cg -maxdepth 2 -type d -name "<記事slug>"
find app/src/routes/color-theory app/src/routes/color-fields -maxdepth 1 -type d -name "<記事slug>"
```

- **0件なら該当ページが無い旨を伝えて中止する。複数件なら候補パスを提示して確認する。** 推測でどれかに決めない
- パスから記事の種類（CG／色の理論／色の活用分野）を判別する。担当スキル側の分岐（デモのコード掲載の有無など）で使う
- **`draft: true` の記事も対象**（公開前の手直しで呼ばれる想定）。`draft` は外さない

## 手順

### 1. 編集指示ブロックを洗い出す

```bash
grep -nE '^:{3,}(Add|Delete|Fix)' <対象ファイル>
```

- ディレクティブは**入れ子のとき外側のコロンが増える**（`::::Delete` で `:::Note` を囲むなど）。`:{3,}` で拾い、**閉じは開始行と同じコロン数の `:` だけの行**とみなしてブロックの範囲を確定する
- `:::Fix` の修正対象は `target` 属性で決まり、**省略時は `text`**（`app/src/lib/components/m-directive/Fix.svelte` の既定値）
- コードフェンス（` ``` `）の中の例示はディレクティブではない。記法自体を説明している記事では除外する
- **1件も無ければ、対応する指示が無いことを報告して終わる。** 他のディレクティブを代わりに処理しない

### 2. 各ブロックの対応方針を組み立てる

ブロックごとに次を決める。**この時点ではファイルを1文字も書き換えない。**

- 担当（→「扱う編集指示」）
- **指示が及ぶ範囲** — `:::Add` はブロックが置かれた位置、`:::Fix{target="text"}` は指示が指している段落・節、`:::Delete` は囲まれた記述
- 対応の方針（何をどう書くか・どう直すか）を1〜2行で

近接するブロックの読み方:

- **`:::Delete` の直前・直後に代替の記述が既に書かれている**ときは、置き換えが済んでいて残りは削除だけ、という意味になる。**新しい文章を書き足さない**
- **`:::Add` と `:::Delete` が隣り合う**ときは差し替えの指示。1件にまとめ、削除と加筆を別々にやるのではなく置き換えとして文章を作る
- `:::Fix{target="svg"}` / `{target="demo"}` は、指示が指しているコンポーネントを、本文の `<SVGWrapper>` / `<CanvasWrapper>` の使用箇所と `<script>` の `import` から特定する。**1つに絞れなければ手順3で確認する**
- **`:::Add` の中身が図版・デモの新設を求めている**ときは、文章として書き起こさない。手順3で確認し、合意のうえ `:::Todo` に置き換える（図版・デモの新規作成はこのスキルの担当外）

### 3. 一覧を提示して承認を得る

検出した全ブロックを表で提示する。

| # | 種別 | 位置 | 指示 | 担当 | 対応方針 |
| --- | --- | --- | --- | --- | --- |
| 1 | `Delete` | L12（導入） | 「隠面消去では〜」の段落 | 文章 | 直前に代替の記述があるため削除のみ |
| 2 | `Fix{demo}` | L88（バックフェースカリング） | 「投射線を表示」を既定でoffに | デモ | `BackfaceCullingDemo` の初期値を変更。掲載コードも合わせる |
| 3 | `Add` | L120（まとめ） | 視錐台との対応を1段落 | 文章 | **要確認**（どの記事の視錐台か。`projection-calculation` と解釈） |

- 位置は行番号と、その箇所が属する節（見出し）で示す。指示は要約せず読み取れる形で載せる
- 要確認の行は **要確認** と印を付け、**推測した解釈も併記する**（何も決めずに投げ返さない）
- 要確認があれば、同じ応答の中で `AskUserQuestion` にまとめて出す。**1回に4問までなので、影響の大きい順に4問を出し、残りは表の方針欄に解釈を明記して承認で兼ねる**
- 質問する／しないの基準は `author-style-writer` の編集モード（E2）と同じ。**方向性が `writing-guides/syntax-guide.md` の規約で定まる内容（導入文のテイストなど）は質問せず規約に従う。** 対象箇所が読み取れない・解釈で結果が変わる・対象コンポーネントが絞れない・指示が既存の記述と矛盾する場合だけ聞く
- 回答で方針が変わった行は、更新後の方針を短く示してから実行に入る

**承認を得るまで本文・コンポーネントを書き換えない。**

### 4. 実行する

処理する順序:

1. **文章系（`:::Add` / `:::Delete` / `:::Fix{target="text"}`）を、ファイルの上から順に。** 文体ガイドの読み込みが1回で済み、前後の流れも上から見ていける
2. 次に `:::Fix{target="svg"}`、最後に `:::Fix{target="demo"}`。どちらも作業の主体は `app/src/lib/demo/` 配下のコンポーネントで、本文への差分はブロックの削除だけになる

- **対応と除去を1件ずつ対にする。** 1件直したらそのブロックを取り除く（→「ブロックの除去」）。まとめて最後に消すと取りこぼす
- **承認された方針から外れる必要が出てきたら、その場で手を止めて確認する。** 黙って別の対応に切り替えない
- **一括処理をサブエージェントに分散しない。** 同じ `+page.svx` を複数のエージェントが書き換えると衝突するうえ、文章の一貫性はセッション側で担保する

### 5. 品質チェック

- **文章系だけの対応（`.svx` のみの変更）なら `npm run check` は実行しない**（`CLAUDE.md`「品質チェック」の基準）
- `.svelte` / `.ts` を変更した場合も、**`npm run check` はユーザー側で実行する。勝手に実行しない**（`svg-diagram-component`・`add-threejs-demo` と同じ規約）。ユーザーがエラーや警告を報告したら、その内容に従って修正する
- **図版・デモの見た目の確認はユーザーが行う。** ブラウザを立ち上げて確認しようとしない
- 最後に、対応済みのブロックが残っていないか確かめる（`:::Todo`・`:::Pending` は対象外なので残っていてよい）

  ```bash
  grep -nE '^:{3,}(Add|Delete|Fix)' <対象ファイル>
  ```

### 6. 報告する

- **対応した指示の一覧**（種別・箇所・何をしたか）。文章系は書いた／直した内容が分かるように書く
- 指示の直接対象**以外**で、流れを整えるために触った箇所
- **残したブロック**（見送り・保留）とその理由
- 変更したファイル（`+page.svx` と `app/src/lib/demo/` 配下）
- デモを直した場合は、`add-threejs-demo`「完了報告」の項目（書き換えた `:::Action` の文面など）を添える
- **コミットはこのスキルではしない。** `/commit-this` に渡す。著者の指示に基づく修正なので、記事のコミットは `[ai-draft]` を付けない「依頼された修正」の扱いになる（→ `CLAUDE.md` Git規約）。**どんな指示だったかがコミットメッセージ本文に残るよう、指示の要約を報告に含める**

## 担当別の進め方

### 文章（`:::Add` / `:::Delete` / `:::Fix{target="text"}`）

- **`author-style-writer` を読み込み、「記事ページを編集する場合（編集モード）」の E3 以降に従う。** 対象ファイルの特定（E1）と編集指示の確定（E2）は手順1〜3で済んでいるので繰り返さない
- 読むガイドは編集モードの範囲（`syntax-guide.md`＋`math-notation-guide.md`＋`refine-style.md`＋`stylistic-quirks.md`。構成に及ぶ指示なら `writing-style.md`、新しい説明を書き足す指示なら `thinking-flow.md` も）。**指示の集合全体で必要な範囲を判断し、最初に1回だけ読む。** ブロックごとに読み直さない
- **指示の直接対象だけでなく、前後の文章・節の流れも整える**（接続の唐突さや重複を残さない）。ただし調整は接続と重複の解消までにとどめ、指示の無い箇所を書き換えない
- `:::Delete` で記述が消えた跡は、前後がつながるように整える。消した記述が担っていた説明を、指示なく別の場所に書き足さない

### SVG図版（`:::Fix{target="svg"}`）

- **`svg-diagram-component` を読み込み、「コンポーネント仕様」以降（描画方法・定数の宣言・矢印マーカー・スタイル・グラフの軸／曲線など）に従って既存コンポーネントを修正する。** 新規作成の手順（パターンA〜Cの判定、配置先ディレクトリの4案提示）は使わない
- 修正対象は既にページに差し込まれているので、`import`・`visual: true`・使用箇所は原則そのまま。**コンポーネントを作り直してファイル名が変わるときだけ**、`import` と使用箇所を直す
- `SVGWrapper` の `maxW` は書き換えない（表示倍率は著者が決める）

### Three.jsデモ（`:::Fix{target="demo"}`）

- **`add-threejs-demo` を読み込み、`scene.ts` の書き方・`_shared` の API・見た目・Tweakpane・アニメーションの規約に従って既存デモを修正する。** 新規デモの手順（`:::Todo` の実装〈パターンA-1〉、デモ案の提案〈パターンA-2〉）は使わない
- **CG記事では、記事に載せている ts コードブロックも合わせて直す。** 掲載コードは実際に動いている `scene.ts` から作り、定数・パラメータはデモの初期値に一致させる規約のため、初期値やUIラベルを変えたらコードブロック側も追随させる（色彩記事にはコードブロックが無い）
- デモの変更（Tweakpane のラベル・初期値・操作パラメータ）で直前の `:::Action` が合わなくなったら、**`:::Action` の側を書き換える**（本文に合わせるのではなく Action を合わせるのが規約）。**書き換えたら `:::Action{fixme}` にする**（AIが手を入れた Action は要編集の印を付ける規約。既に `{fixme}` が付いていればそのまま。→ `writing-guides/syntax-guide.md` ルール4）。書き換えた文面は報告に載せる
- **地の文のデモへの言及が合わなくなった場合は、報告に挙げて著者の判断を仰ぐ。** `:::Fix{target="text"}` の指示が無い限り本文は直さない

## ブロックの除去

- `:::Add` → **ブロック全体（開始行から閉じの `:::` まで）を、書いた文章に置き換える。** 指示文が本文に残らないようにする
- `:::Delete` → **囲まれた記述ごとブロック全体を削除する。** 中身を残さない
- `:::Fix` → **ブロック全体を削除する。** 修正は指示された対象（本文・コンポーネント）に入れる
- 除去のあと、前後の空行を整える（空行が2つ以上続かない、見出しや段落が空行なしでくっつかない）
- **対応を見送ったブロックは消さずに残す。** 報告に理由を書く

## やってはいけないこと

- 手順3の承認を得る前に本文・コンポーネントを書き換える
- 対応していないブロックを消す（見送ったものは残して報告する）
- `:::Todo`・`:::Pending`・`::ComingSoon` を処理する・消す
- `:::Delete` の中身を指示と読み違えて、書かれている記述を残したままブロックだけ外す
- 指示が指していない箇所まで書き換える（`:::Fix` は指示の範囲に限る）
- 曖昧な指示を推測で埋めて黙って進める（手順3でまとめて確認する）
- 既存の `:Anki[]` / `:Mark[]` を、指示が明示的に求めていないのに外す・入れ替える
- 見出し構成（テキスト・順序・分類タグ）を、指示が求めていないのに変える
- `draft: true` を外す（公開の判断は著者）
- フロントマターの `layout` / `title` を変える
- ブロックを消した跡に空行の乱れを残す
- 一括処理をサブエージェントに分散する
- 指示に無い改善（言い回しの整え直し、節の並べ替えなど）をついでに入れる

## 完了条件

- 承認された全ブロックに対応が入り、そのブロックが本文から消えている
- 見送ったブロックだけが本文に残り、報告に理由が載っている
- 記法・書式が `writing-guides/syntax-guide.md`・`writing-guides/math-notation-guide.md` に従っている
- 文章系の修正が、指示の範囲と前後の流れの調整にとどまっている
- 図版・デモの修正が、担当スキルのコンポーネント規約に従っている
- CG記事でデモを直した場合、記事の ts コードブロックがデモの実装と一致している
