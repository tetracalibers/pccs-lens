# コミット作成スキル (commit-this)

**現在のセッションで変更したファイルだけ**を対象に、CLAUDE.md の「Git 規約」「品質チェック」に沿ったコミットを 1 つ（必要なら複数）作るためのスキルです。

このスキルがやること・やらないことを最初に確認する。

- **やること**: **`main` にいるならブランチを切る** → コミット対象の確定（**引数でパスが指定されていればそれだけ**、無ければセッションで触ったファイル） → **記事の公開（`draft` 削除）の検出と `publish-article` の呼び出し**（公開時タスクの実行はそちらの担当。このスキルは結果をコミットに反映する） → **コンテンツ YAML の変更を見たタスクリストの整合チェック** → **公開済み記事へのデモ追加の検出と `draft` フラグの書き戻し** → **非 draft 記事の本文変更を見た記法整備タスクリストの `[x]` 解除** → コミット対象の分類 → 未 push コミットを見た `[skip ci]` 判断 → 日本語コミットメッセージの組み立て → 明示パス指定でのコミット → **コミット完了後の件名の報告**。
- **やらないこと**: `push` はしない。`git add -A` / `git add .` / `git commit -a` は使わない。**セッション外（ユーザーや別セッションが加えた）未コミット変更を巻き込まない。** 公開時タスクの手順を自前で持たない（正典は `publish-article`）。**デモ追加のための OGP 画像の生成・再生成をこのスキルで行わない**（`draft` を戻して再公開時の公開時タスクに委ねる。→ 手順 1.7）。**`draft: true` を外すことはしない**（公開の判断は著者）。`publish-article` がディレクティブの残存でゲートを閉じた場合、**その場でディレクティブに対応してしまわない**（案内を報告に載せてコミットは通常どおり進める。→ 手順 1.5 a）。

## 入力

- **ファイルパス（任意・複数可）**: 引数にパスらしき語（`/` を含む、既知の拡張子で終わる、または実在するパスと一致する）が渡されたら、**そのパスだけをコミット対象にする**。パス以外の語はメッセージのヒント（下の「補足」）として扱う。
- **補足（任意）**: コミットメッセージのヒント、対象を絞る指示（「◯◯だけ」）、依頼の意図など。無くても動く。

### ファイルパスを指定されたときの具体例

| 引数 | コミット対象 |
| --- | --- |
| `/commit-this README.md` | `README.md` **だけ**。同じくセッションで触った他のファイルが dirty でも含めない |
| `/commit-this app/src/routes/color-theory/blackbody-radiation/+page.svx` | その記事 1 ファイルだけ（`.svx` なので手順 1.5 の公開判定・手順 4 の件名規約の対象になる） |
| `/commit-this README.md .claude/skills/commit-this/SKILL.md` | 指定した 2 ファイルだけ（空白区切りで複数指定） |
| `/commit-this app/src/lib/demo/illusion/` | ディレクトリ指定。その配下で dirty なファイルすべて（`git status --porcelain -- <dir>` で展開する） |
| `/commit-this README.md 公開手順の追記だけ先にコミット` | 対象は `README.md`。残りの語はメッセージのヒントとして使う |

指定時の扱い:

- **明示指定は「セッションで変更したファイルだけ」の制限より優先する。** ユーザーが名指ししたパスは、セッション外で変更されたファイルでも対象にしてよい（勝手に巻き込むわけではないため）。ただし手順 6 の報告で、**セッションで触っていないファイルである**旨と差分の要点（`git diff HEAD -- <path>` で確認）を明示する。
- 指定パスに差分が無い（`git status --porcelain -- <path>` が空）ときは、コミットせずその旨を報告する。
- 指定パスの一部だけが dirty なときは、dirty なものだけを対象にし、差分の無いパスは報告で触れる。
- 指定が無い場合のみ、手順 1 のとおり「セッション変更リスト」から対象を決める。

## 手順

### 0. ブランチを確認する（`main` にいるなら切る）

**`main` に直接コミットしない。** 何よりも先に現在のブランチを確認する。

```sh
git branch --show-current
```

- **`main` 以外** → そのブランチのままコミットする。何もせず手順 1 へ進む。
- **`main`** → **新しいブランチを切ってから**コミットする。ブランチ名は下の方針で決め、**事前承認は求めずそのまま作成し、手順 6 で報告する**（コミットメッセージと同じ扱い）。

```sh
git switch -c <ブランチ名>
```

ブランチ名の決め方:

- 引数の補足にブランチ名の指定・ヒントがあればそれに従う。
- 無ければ、コミット対象の変更内容から英小文字ケバブケースのスラッグを作り、`feature/<スラッグ>`（バグ修正なら `fix/<スラッグ>`）にする。既存ブランチの慣例に合わせる（`git branch --sort=-committerdate | head` で確認できる）。
- 記事の執筆・公開が主眼なら、記事のルートのスラッグを流用してよい（例: `feature/cg-vanishing-points-and-n-point-perspective`）。

注意点:

- **未コミットの変更はそのまま新しいブランチへ引き継がれる**ので、ここで切っても手順 1 以降の対象判定・ファイル書き換えには影響しない。
- 同名のブランチが既にあって `git switch -c` が `already exists` で失敗したときは、スラッグを見直して別名にする。**既存ブランチに乗せ換える（`git switch <既存>`）のは勝手に決めず**ユーザーに確認する。
- **`main` に未 push のコミットが残っていた場合**（手順 3 の `git log HEAD --not --remotes` で分かる）、新ブランチはそれを含んだ状態から始まり、ローカルの `main` も同じコミットを指したままになる。`main` を `origin/main` に戻すかどうかは**自動でやらない**（履歴を動かす操作のため）。手順 6 で状況を報告し、指示を仰ぐ。

### 1. 現在のセッションで変更したファイルを特定する

> **引数でファイルパスが指定されている場合はこの手順を飛ばし、そのパス（ディレクトリなら配下の dirty なファイル）だけを対象にする**（「入力」の具体例を参照）。差分の有無だけ `git status --porcelain -- <path>` で確認し、手順 1.5 へ進む。

コミット対象は、**このセッションであなた（アシスタント）が作成・編集したファイル**に限る。

1. **セッションでの変更を思い出す。** このセッション中に Write / Edit / NotebookEdit で作成・編集したファイル、および Bash で動かした（`mv`・リネーム・フォーマッタ・生成物など）ファイルを列挙し、これを「セッション変更リスト」とする。これが対象判定の一次情報。
2. **`git status` と突き合わせる。**

   ```sh
   git status --porcelain
   ```

   - セッション変更リストのうち、実際に差分がある（`M` / `A` / `??` / ステージ済み）ものだけを残す。差分が無いものは編集後に元へ戻った等なので除外する。
   - **git 上は dirty だが、セッション変更リストに無いファイル**は、セッション開始時点で既に存在した変更（ユーザーや別セッション由来）とみなし、**コミットに含めない**。存在は手順 6 で報告する。
3. **巻き込みのエッジケースを確認する。** セッションで触ったファイルが、セッション開始時点で**既に別の未コミット変更を持っていた**場合（環境のセッション開始時 `git status` スナップショットに載っていたファイルなど）、そのファイルをステージするとセッション外の差分も一緒にコミットされる。該当があれば、その旨をユーザーに伝えて含めてよいか確認する。
4. **セッションの記録が無いとき**（別セッションで加えた変更を後からコミットする等で、自分が編集した記憶が無い場合）は推測しない。`git status` を提示し、どのファイルを対象にするかユーザーに確認する。

> `git add -A` / `git add .` / `git commit -a` は使わない。必ず**パスを明示**してステージする（手順 5）。

### 1.5. 記事の公開（`draft` 削除）を検出し、`publish-article` に渡す

コミット対象に `.svx`（記事ページ）が含まれる場合、**その差分で `draft: true` 行が削除されているか**を調べる。削除されていれば「この作業で記事を公開した」とみなし、**公開時タスクは `publish-article` スキルに任せる**。手順の正典はそちらで、このスキルが担うのは**呼び出しと、その結果をコミットへ反映すること**だけ。

```sh
# 対象 svx ごとに、HEAD からの差分（ステージ済み・未ステージの両方）を見る
git diff HEAD -- <対象の .svx パス> | grep -E '^[-+]draft: *true'
```

- `-draft: true` があり `+draft: true` が無い → **公開**。以下 a を実行する。
- どちらも出ない／両方出る → 公開ではない。そのまま手順 2 へ進む。
- **新規追加ファイルで最初から `draft: true` が無い**場合は、実質的な新規公開ページだが「draft を外した」わけではないので、公開時タスクを実行してよいか**ユーザーに確認**してから進む（このリポジトリでは新規ページを `draft: true` で作るのが通常なので稀）。

#### a. コミット前のフェーズを呼び出す

公開した記事のルート（`app/src/routes/` を除いたパス）を渡して、Skill ツールで `publish-article` を実行する。複数記事を公開した場合はまとめて渡してよい。

```
/publish-article /<route> --before-commit
```

`--before-commit` で走るのは、**ディレクティブの残存チェック（ゲート）・記法ゲート（`lint:svx:syntax` と `format-math-notation --auto` の自動実行）と、`visual` フラグの追加・文体解析タスクリストの `[draft]` 解除**まで。OGP 画像は記事本文と別コミットにするため、記事をコミットしたあとの手順 5.5 に回る。

- **ゲートを通った場合** → `publish-article` が書き換えたファイル（記事の `.svx`・`writing-guides/STYLE-ANALYSIS-TASKLIST.md`）を、**手順 5 のステージ対象に加える**。コミット本文でもその旨に触れる（例: `公開に伴い visual フラグを追加し、文体解析タスクリストの draft 注釈を外した。`）。
- **記法ゲートが記事を書き換えた場合** → その差分だけを**独立したコミットとして、公開のコミットより先に**作る（→ 手順 1.55）。
- **ゲートで止まった場合**（`:::Todo` / `:::Add` / `:::Delete` / `:::Edit` / `:::Modify` / `:::Pending` や `{fixme}` 付きの `:::Action` が本文に残っていた） → **公開時タスクは実行されない。**
  - **コミットは通常どおり進める**（対象・メッセージの組み立ては変わらない）。ただし**手順 5.5 の OGP 生成は飛ばす**。
  - `publish-article` が組み立てた案内（コピペで実行できるスキル呼び出し）を、**そのまま手順 6 の報告に載せる**。文面を要約したり作り直したりしない。
  - `visual` フラグとタスクリストの書き換えはこのコミットに入らないので、**ディレクティブに対応したあとに `/publish-article <slug>` を実行し、その変更を別コミットにする**必要がある。報告でその旨も伝える。
  - **このスキルの中でディレクティブに対応しない。** 案内されたスキルを走らせるかどうかはユーザーが決める。

> `visual` のように**コミット対象の `.svx` 自身が書き換わる**ので、この呼び出しはステージ（手順 5）より前に済ませる。

#### b. 自動実行しないもの

**文体スタイルガイドの更新（`author-style-analyzer`）と PR 説明文の更新（`update-pr-description`）は、`publish-article` も自動実行しない**（→ `publish-article` 手順4）。手順 6 で未実施として案内する。

### 1.55. 記法の整備を独立したコミットにする

`publish-article` の記法ゲート（手順 0.5）が記事を書き換えた場合、**その差分だけを先に、独立したコミットにする。**

```
commit-this
  ├─ publish-article --before-commit
  │    └─ 手順0.5: 記法ゲート → format-math-notation --auto（作業ツリーに変更を残すだけ）
  ├─ commit #1  <記事タイトル>：数式・インラインコードの記法を整備 [ai-draft]   ← 許可プロンプト
  ├─ commit #2  <記事タイトル> [ai-draft]                                    ← 許可プロンプト
  └─ publish-article --ogp → commit #3                                      ← 許可プロンプト
```

- **記法の差分と本文の差分を1つのコミットに混ぜない。** 記法整備は機械的な変換なので、混ぜると本文の変更がレビューできなくなる。
- **順序は「記法 → 公開」。** 記法整備だけを先に切り出すには、公開の差分がまだステージされていない状態でコミットする必要がある。
- **記法だけを切り出せない場合**（同じ行に本文の変更と記法の変換が混在している、など）は、分割せず1つのコミットにまとめ、**本文にその旨を書く**。取り繕って分けない。
- 件名は過去の実績（`0e88b9e6` など）と揃える。

  ```
  <記事タイトル>：数式・インラインコードの記法を整備 [ai-draft]
  ```

  本文には、当てたルールと件数（`lint:svx:syntax` の出力から）と、advisory に残した指摘があればその件数を書く。**`format-math-notation --auto` による自動修正なので `[ai-draft]` を付ける**（`author-style-writer` の編集モードで依頼された修正ではない）。
- **この自動実行が人間の確認を飛ばさない根拠は、コミットの許可プロンプト**である（`.claude/settings.json` の `permissions.ask` に `Bash(git commit *)` があるため、差分は必ず人間の目を通る）。
- ステージは記事の `.svx` **1ファイルだけ**にする（`git add -- <path>`）。記法ゲートは他のファイルを触らない。

### 1.6. タスクリストとコンテンツ YAML の整合をとる

`ogimage/OGP-TASKLIST.md` と `writing-guides/STYLE-ANALYSIS-TASKLIST.md` は、コンテンツ YAML（`app/src/lib/content-pages/**/*.yaml`）の並び順をそのまま写したもの。**YAML の並べ替え・改名・`DraftLink`→`PageLink` や、記事の新規追加・削除があるとタスクリストが黙ってずれる。** 原因の変更と同じコミットに追随を載せる。

コミット対象に次のいずれかが含まれるときに実行する。

- `app/src/lib/content-pages/**/*.yaml`
- `app/src/routes/**/+page.svx` の**新規追加・削除**、または frontmatter（`title` / `draft`）の変更

```sh
node scripts/sync-tasklists.mjs --check
```

> `Cannot find package 'yaml'` で落ちたら依存が未インストール。`npm --prefix scripts install` を実行してからやり直す（`scripts/` は app とは独立した小さな Node パッケージ）。

- **差分なし（exit 0）** → 何もせず手順 2 へ。
- **差分あり（exit 1）** → 出力された変更点を**そのままユーザーに提示**し、`--write` で反映してよいか確認する。承認を得たら次を実行し、書き換わった2ファイルを**手順 5 のステージ対象に加える**。

  ```sh
  node scripts/sync-tasklists.mjs --write
  ```

- **エラー終了** → 1 行も書き込まれない。メッセージ（多くは YAML の想定外の記述）を報告し、**タスクリストを手で書き換えて取り繕わない**。記事側のコミットは通常どおり進めてよい。

スクリプトが触るのは構造（並び順・行の追加削除・`[ページ未作成]`↔``[draft] `/route` `` の変換）だけで、**`[x]`（生成済み・分析済み）を作ることも消すこともしない**。`draft: true` なのに `[x]` のような矛盾は警告として出るだけなので、出たら報告する。

> `[draft]` → `[ ]` の書き換えはこのスクリプトでも解消できるが、公開時タスクの一部として `publish-article`（手順2）で先に済んでいる（公開時タスクの実行結果として報告するため）。両方走っても結果は同じ。

> **手順 1.7 で `draft` を戻した場合は、そのあとにこのチェックを再実行する**（frontmatter の `draft` が変わり、ここでの結果が古くなるため。→ 手順 1.7 b）。

### 1.7. 公開済み記事へのデモ追加を検出し、`draft` を戻す

コミット対象に `.svx`（記事ページ）が含まれる場合、**すでに公開されている（`draft: true` が無い）記事にデモが追加されたか**を調べる。追加されていれば、frontmatter に **`draft: true` を書き戻す**（いったん下書きに戻す）。

こうする理由: OGP 画像はデモの画面写真を図版として埋め込むので、公開後にデモが増える・入れ替わると**画像が記事の中身と合わなくなる**。`draft` に戻しておけば、著者が改めて `draft` を外したときに**手順 1.5 の公開検出に乗り**、`publish-article` の公開時タスク（ディレクティブの残存チェック・`visual` フラグ・OGP 画像の生成）がまとめて回る。デモを何本か入れ終えてから一度だけ図版を作り直せる。

判定は次の2つを**両方**満たすかで行う。

```sh
# ① 記事が現時点で非 draft か（作業ツリーの内容を見る）
grep -qE '^draft: *true' <対象の .svx> && echo draft || echo published

# ② この差分でデモが追加されたか（$lib/demo/ の import 行が増えたか）
git diff HEAD -- <対象の .svx> | grep -E '^\+.*\$lib/demo/'
```

- **① が `draft`** → 対象外。すでに下書きなので何もしない。
- **手順 1.5 で「公開」と判定した記事も対象外。** 著者がこの作業で公開したものを、同じコミットで下書きへ戻さない。
- **② が空** → 対象外。デモコンポーネント側（`app/src/lib/demo/**`）を新規追加しただけで記事の import 行が変わっていない場合も、記事に載る図版は変わっていないので対象外。
- **既存デモの差し替え**（import 行が1本減って別の1本が増えた）は対象に含める。図版が古くなるのは同じ。
- **`visual: true` は触らない。** 付けるのは公開時タスク（`publish-article` 手順1）の担当で、再公開のときに付く。

#### a. `draft: true` を書き戻す

frontmatter の**末尾**（閉じる `---` の直前）に、**直前に空行を1行入れて** `draft: true` を置く。このリポジトリの下書きページはすべてこの形（公開時は `draft: true` と直前の空行をまとめて削除する）。

```yaml
---
layout: guide-content
title: ベジェ曲線の数学的性質 # CG 3-4-3, 3-4-4

group: ["CG"]
visual: true

draft: true
---
```

- 書き換えるのは**コミット対象の `.svx` 自身**なので、ステージ（手順 5）より前のここで済ませる（同じコミットに載る）。
- **コミット本文でその旨に触れる**（例: `デモの追加に伴い draft を戻した。再公開時に OGP 画像を生成し直すため。`）。
- **`draft` を戻すと記事は一時的に非公開になる。** 手順 6 で必ず報告し、再公開の手順（`draft: true` と直前の空行を外して `/commit-this`）を添える。
- 対象が複数記事あれば、すべてに同じ処理を行う。
- **すでに `draft: true` がある記事に二重で足さない**（① で除外済み）。

#### b. タスクリストの整合を取り直す

`draft` は frontmatter の値なので、書き戻すと手順 1.6 の判定材料が変わる（公開状態を写しているタスクリストの `[ ]` が `[draft]` に戻る）。**手順 1.6 の `--check` をここでもう一度実行する。**

```sh
node scripts/sync-tasklists.mjs --check
```

- 差分が出たら手順 1.6 と同じ扱い（出力をそのまま提示して `--write` の承認を得て、書き換わった2ファイルを手順 5 のステージ対象に加える）。
- `[x]`（OGP 生成済み・分析済み）は付け替えられず**警告として出るだけ**なので、出たら報告に載せる。**手で書き換えない。**

### 1.8. 非 draft 記事の本文が変わったら、タスクリストの記録を戻す

コミット対象に `.svx`（記事ページ）が含まれる場合、**公開されている（`draft: true` が無い）記事の本文が変わったか**を調べる。変わっていれば、2枚のタスクリストの記録を戻す。

- `writing-guides/NOTATION-TASKLIST.md` の該当行を **`[x]` → `[ ]`**（→ a）
- `writing-guides/STYLE-ANALYSIS-TASKLIST.md` の該当行を **`[x]` → `[~]`**（→ b）

こうする理由: どちらの `[x]` も**そのときの本文に対する記録**である。記法整備（`[x]` ＝ `format-math-notation` を実行して advisory の判断まで済んだ）は、本文が書き換われば記事全体・文単位・ブロック数式の説明文の統一が崩れうる。文体分析（`[x]` ＝ 4観点の根拠を `evidence/` へ記録済み）も、`分析時点` に記録した SHA の本文に対する結果でしかない。記録を戻しておけば、あとから `/format-math-notation #<セクションid>` や `/author-style-analyzer <slug>` を回したときに**もう一度対象として拾われる**。

**文体解析タスクリストは `[ ]` に落とさず `[~]` にする。** `[ ]` は「一度も分析していない」を意味し、`author-style-analyzer` は `[x]` / `[~]` の記事に対してだけ「再分析するか」を確認して `evidence/` の `分析時点` と `git diff` を突き合わせる（メタデータのみの変更なら再分析不要と判断できる）。`[ ]` に落とすとその分岐に入らず、確認なしの再分析になり、未分析の残件数も濁る。記法整備タスクリストの `[x]` は本文に対する記録がリスト以外に無いため、こちらは `[ ]` で構わない。

判定は次の**すべて**を満たすかで行う（①②は2枚に共通、③はリストごと）。

```sh
# ① 記事が現時点で非 draft か（作業ツリーの内容を見る）
grep -qE '^draft: *true' <対象の .svx> && echo draft || echo published

# ② frontmatter より後ろ（本文）に変更があるか
FM_END=$(awk 'NR>1 && /^---$/{print NR; exit}' <対象の .svx>)
git diff -U0 HEAD -- <対象の .svx> \
  | awk -v fm="$FM_END" '/^@@/{split($3,a,","); sub(/^\+/,"",a[1]); if (a[1]+0 > fm) found=1} END{exit !found}' \
  && echo body-changed || echo frontmatter-only

# ③ タスクリストで現在 [x] か（リストごとに見る）
grep -n -- '^- \[x\] `/cg/<ユニット>/<slug>`$' writing-guides/NOTATION-TASKLIST.md
grep -n -- '^- \[x\] `/<route>`$' writing-guides/STYLE-ANALYSIS-TASKLIST.md
```

- **① が `draft`** → 対象外。下書きの記事は執筆中で本文が動き続けるため、編集ごとに外しても意味がない（`[draft]` のまま、あるいは下書き段階で回した `[x]` のまま残す）。
- **② が `frontmatter-only`** → 対象外。`visual` フラグの追加や `draft` の付け外しだけでは記法は変わらない。
- **③ に該当行が無い** → そのリストは対象外。`[ ]`・`[draft]`・`[~]` なら戻すものが無い。記法整備タスクリストにはCG記事しか載らないので、色記事は文体解析タスクリストだけが対象になる。
- **このコミットで `[x]` を付けたばかりの記事は対象外。** `format-math-notation` を回したコミットは、記法の整備そのものが本文を書き換えるので、そのまま外すと記録が残らない。`author-style-analyzer` を回したコミットも同じ（新しい本文を分析した結果なので戻す理由が無い）。タスクリストの差分で当該行が `[x]` になっているかで判定する。

  ```sh
  git diff HEAD -- writing-guides/NOTATION-TASKLIST.md | grep -E '^\+- \[x\] `/cg/'
  git diff HEAD -- writing-guides/STYLE-ANALYSIS-TASKLIST.md | grep -E '^\+- \[x\] `/'
  ```

- **記法整備だけの書き換えは文体解析タスクリストの対象外**（記法整備タスクリストは上のとおりそもそも対象外）。手順 1.55 の独立コミットや `/format-math-notation` の実行コミットは `$...$` の付け替えなど機械的な変換しか含まず、文体の根拠は動かない。本文の差分が記法整備によるものだけなら `[~]` は付けない。判定は同じコミットに `writing-guides/NOTATION-TASKLIST.md` の `[x]` 追加が含まれるか、または差分が `lint:svx:fix` の自動修正だけかで行う。

- 手順 1.7 で `draft` を戻した記事も対象外（① で `draft` になるため自然に外れる）。

#### a. 記法整備タスクリストの `[x]` を `[ ]` に戻す

該当行の状態マーカーだけを書き換える。**行の位置・スラッグ・他の行には触らない。**

```
- [x] `/cg/basics/shape-rasterization`
→
- [ ] `/cg/basics/shape-rasterization`
```

- 書き換えた `writing-guides/NOTATION-TASKLIST.md` を**手順 5 のステージ対象に加える**（本文の変更と同じコミットに載せる）。
- **コミット本文でその旨に触れる**（例: `本文を書き換えたため、記法整備タスクリストのチェックを外した。`）。
- 対象が複数記事あれば、すべての行を書き換える。
- **`[ ]` に戻したことは手順 6 で必ず報告する。** 記法の整備が未実施に戻る（あとから `/format-math-notation <slug>` を回す必要がある）ので、黙って済ませない。
- `sync-tasklists.mjs` は `[x]` を作りも消しもしないので、**この書き換えはスクリプトでは代替できない**（手で行うのが正しい）。`--check` の結果には影響しない。

#### b. 文体解析タスクリストの `[x]` を `[~]` にする

同じく該当行の状態マーカーだけを書き換える。**`[ ]` にはしない**（→ 手順 1.8 冒頭の理由）。

```
- [x] `/color-theory/light-scattering`
→
- [~] `/color-theory/light-scattering`
```

- 書き換えた `writing-guides/STYLE-ANALYSIS-TASKLIST.md` を**手順 5 のステージ対象に加える**（本文の変更と同じコミットに載せる）。
- **コミット本文でその旨に触れる**（例: `本文を書き換えたため、文体解析タスクリストを再分析待ち（[~]）にした。`）。
- 対象が複数記事あれば、すべての行を書き換える。記法整備タスクリストと違いCG記事に限らないので、色の理論・色の活用分野の記事も対象になる。
- **`[~]` にしたことは手順 6 で必ず報告する。** 再分析の候補が増える（あとから `/author-style-analyzer <slug>` を回す必要がある）ので、黙って済ませない。再分析するかどうかの判断は analyzer 側で `evidence/` の `分析時点` と本文の差分を見て行うため、**このスキルで再分析の要否まで決めない**。
- `[x]` を `[~]` に戻すのはこのスキルだけで、`[~]` から `[x]` へ戻すのは `author-style-analyzer`（再分析の完了時、または再分析不要と判断してユーザーの承諾を得たとき）。`sync-tasklists.mjs` はどちらのマーカーも作らず消さない。

### 2. コミット対象を分類する（app・ビルド系 / ドキュメント・スキル系）

`[skip ci]` の判断（手順 3）とメッセージ規約（手順 4）のため、対象ファイルを次の 2 種に分類する。

- **app・ビルド系（CI 対象）**: `app/**`（`.svx`・`.css` を含む）、ルートの `package.json`・lockfile・`*.config.*`・CI 設定など、**アプリの実行・ビルドに関わる**ファイル。
- **ドキュメント・スキル系（CI 非対象）**: `docs/**`、`spec/**`、`.claude/skills/**`、ルートの `*.md`（`CLAUDE.md` / `README` など）、その他アプリの実行に関わらない Markdown。

> **注意**: `.svx` は `app/` 配下の記事ページでビルド対象なので、**app・ビルド系**として扱う（`[skip ci]` の対象外）。「Markdown だから CI 非対象」と早合点しない。

> **例外（OGP 生成物）**: `app/static/ogp/**`・`ogimage/data/**`・`app/src/lib/meta/og-manifest.json`・`ogimage/OGP-TASKLIST.md` は `app/` 配下を含むが、アプリのロジックではなくメタデータ・静的アセットなので **CI 非対象扱い**（CLAUDE.md の Git 規約に明記）。これらだけのコミットは `[skip ci]` の候補になる（ただし手順 3 の未 push 判定が優先）。

### 3. `[skip ci]` を付けるか判断する

CLAUDE.md の規約をそのまま適用する。判断材料として**未 push コミット**を確認する。

```sh
# 未 push コミット一覧（upstream 未設定でも動く：リモートに存在しないコミットを列挙）
git log --oneline HEAD --not --remotes

# 未 push コミットが触れているファイル一覧
git log HEAD --not --remotes --name-only --pretty=format: | sort -u | sed '/^$/d'
```

判断ルール:

- `[skip ci]` を付けてよいのは、**今回のコミット対象が丸ごとドキュメント・スキル系のみ**（app・ビルド系を 1 つも含まない）の場合だけ。
- **さらに、既存の未 push コミットに app・ビルド系の変更が 1 つでも含まれる場合は、たとえ今回のコミットがドキュメント・スキルのみでも `[skip ci]` を付けない。** 先頭コミットの `[skip ci]` は push 全体の CI をスキップしうるため。この場合は、**コミット本文にその理由を 1 行残す**（下の例）。
- 上記以外（今回のコミットが app・ビルド系を含む、または混在）→ `[skip ci]` は付けない。

まとめると、**「今回の対象に app・ビルド系が無い」かつ「既存の未 push コミットにも app・ビルド系が無い」→ 付ける。どちらかに app・ビルド系があれば付けない。**

> **付けないと判断したら、件名にも本文にも `[skip ci]` という文字列を書かない。** CI のスキップ判定はコミットメッセージ全体（本文を含む）を対象とするため、「`[skip ci]` は付けない」と打ち消しで書いても、その記述自体でスキップが有効になってしまう。理由を残すときは角括弧つきの表記を避ける。

`[skip ci]` を抑止した場合の本文注記の例:

```
未 push コミットに app 配下の変更が含まれるため、規約に従い CI スキップ指示は付けない。
```

### 4. コミットメッセージを作る（日本語・CLAUDE.md Git 規約）

- **件名は必ず日本語。** 変更を端的に表す。
- **本文（依頼に基づく変更の場合）**: 何を変えたかだけでなく、**どんな依頼で・なぜそう変えたか（意図・背景）**を日本語で数行残す。件名だけで意図が伝わるなら本文は省いてよい。
- `[skip ci]` を付ける場合は**件名の末尾**に置く（例: `景観色彩ガイドの用語を統一 [skip ci]`）。付けない場合は、**本文にも `[skip ci]` という文字列を書かない**（手順 3 の注記を参照）。

#### `.svx`（記事ページ）の件名規約

対象に `.svx` が含まれる場合、frontmatter の `title:` から記事タイトルを取り、次のいずれかにする。

- **AI 初稿**（このセッションで雛形→本文を新規に書き起こした場合）: `記事タイトル [ai-draft]`
- **初稿ではないが AI の修正のみ**: `記事タイトル：修正内容 [ai-draft]`
- **人間が依頼した修正 / `author-style-writer` の編集モードで指示された修正**: `記事タイトル：依頼された修正内容`（`[ai-draft]` は付けない。依頼であることが分かるように書き、本文に依頼・意図を残す）
  - 例: `景観色彩の考え方：依頼に基づき導入文を追記`

初稿かどうかは、そのコミット前まで `draft` の雛形で本文が無く、今セッションで本文を書き起こしたなら「初稿」と判断する。

> 記事とそれ以外（コンポーネント・YAML 等）を 1 回の作業で触った場合、記事の公開・執筆が主眼なら記事タイトル基準の件名にし、本文でその他の変更に触れる。分けた方が履歴が読みやすいなら**コミットを分割**してよい（記事＝`.svx` と、それ以外を別コミットにする等）。分割時は各コミットで手順 2〜4 を個別に適用する。

#### 末尾のトレーラ

このリポジトリの慣例に従い、コミットメッセージの末尾に `Co-Authored-By:` の 1 行を付ける（本文がある場合は 1 行空けてから）。

```
Co-Authored-By: Claude <モデル名> <noreply@anthropic.com>
```

**モデル名はここに固定で書かない。** 実行するモデルは変わっていくため、次の優先順で解決する。

1. **システム側（環境・`CLAUDE.md`）から指示されているトレーラがあれば、それをそのまま使う。** 実行中のモデル名を含んだ形で与えられるので、これが最も確実。
2. 指示が無い場合は、**そのセッションで実行しているモデルの表示名**（`Opus 5`・`Sonnet 5` など）を使う。
3. 判断がつかないときは、直近のコミットで実際に使われている形に合わせる。

```sh
# 直近のコミットのトレーラを確認する
git log -5 --format='%b' | grep -i 'co-authored-by' | sort -u
```

1 と 3 が食い違う場合（モデルが新しくなった直後など）は 1 を優先し、**過去のコミットの古いモデル名に引きずられない**。逆に、自分が使うつもりの名前が慣例と大きく違う場合は、コミット前にユーザーへ一言確認する。

### 5. コミットする

1. **品質チェック（必要な場合）**: 対象に型チェックが有効なファイル（`.ts` / `.js` / `.svelte`。ただし `.svelte` の CSS のみ変更は除く）が含まれ、このセッションでまだ `npm run check` を通していない場合は、コミット前に `app` ディレクトリで実行し、エラー・警告を解消する。`css` / `svx` / `md` のみのコミットなら不要。
2. **明示パスでステージ**する。手順 1.5 a でゲートを通った場合は、`publish-article` が書き換えたファイル（記事の `.svx`・`writing-guides/STYLE-ANALYSIS-TASKLIST.md`）もこのパス一覧に含める。

   ```sh
   git add -- <path1> <path2> ...
   ```

3. **コミット**する。**メッセージの事前承認は求めず、手順 4 で組み立てたものをそのままコミットする。** 本文・改行・日本語を保つため、ヒアドキュメントで標準入力から渡す（コマンド自体にメッセージが見える形にする）。**scratchpad などの一時ファイルには書き出さない。**

   ```sh
   git commit -F - <<'EOF'
   <件名>

   <本文>
   EOF
   ```

   件名だけで本文が無い場合は `-m "<件名>"` でよい。
4. **コミットできたら件名を報告する**（手順 6）。全文の再掲は不要。
5. `push` はしない。

### 5.5. 公開記事の OGP 画像を生成し、別コミットにする

手順 1.5 a で**ゲートを通った**公開記事がある場合のみ実行する（公開が無い／ゲートで止まった場合は飛ばす）。

> 公開済み記事にデモを追加したケースは**ここでは扱わない。** 手順 1.7 で `draft` を戻してあるので、著者が改めて公開したときに手順 1.5 経由でこの手順に入る。

1. **生成する。** 控えておいたルートを引数に、`publish-article` の OGP フェーズを呼ぶ（Skill ツール。複数記事なら 1 ルートずつ実行する）。

   ```
   /publish-article /<route> --ogp
   ```

   - タイトルの改行位置・図版の要否・白背景の透過は、**`publish-article` → `generate-ogp-image` の手順に従って対話で確認する**（勝手に決めない）。
   - `ogimage/` の依存・フォントが未整備などで生成に失敗した場合は、**記事のコミットはそのままに**、OGP を未実施として手順 6 で報告し、手動で実行するコマンドを案内する。ここで詰まっても記事コミットは巻き戻さない。

2. **生成物を別コミットにする。** 更新されるのは次の4種（`publish-article` の報告に出る）。

   - `app/static/ogp/<route>.png`
   - `ogimage/data/<route>.json`（図版があれば `ogimage/data/assets/<route>/` も）
   - `app/src/lib/meta/og-manifest.json`
   - `ogimage/OGP-TASKLIST.md`

3. **件名**は `<記事タイトル>のOGP画像を生成`（複数記事なら `<A>・<B>のOGP画像を生成`）。`[skip ci]` は手順 3 のルールで判断する。**直前の記事コミット（`app/**` の `.svx`）が未 push で残るため、通常はここで `[skip ci]` を付けられない**。付けないと判断したら、件名・本文のどこにも `[skip ci]` という文字列を書かない。
4. 手順 5 と同様に、**事前の承認は求めずコミットし、完了後に件名を報告する**。

### 6. 報告する

事前に承認を取らないぶん、**ユーザーが何をコミットしたか知るのはこの報告が最初**になる。件名は必ず示す。

- **新しく切ったブランチ**（手順 0 で `main` にいた場合）とその名前。`main` のままだったなら触れなくてよい。`main` に未 push のコミットが残っている場合は、その状況（ローカルの `main` がまだそれを指していること）も添える。
- **コミットした件名**（複数コミットならそれぞれの件名）とコミットハッシュ。`git log -1 --stat` で確認結果を示す。本文まで含めた全文の再掲は不要。
- コミット対象のファイル一覧（app・ビルド系 / ドキュメント・スキル系の分類つき）。
- `[skip ci]` を付けたか／付けなかったかと、その理由（未 push コミットの状況）。
- **コミットに含めなかった dirty ファイル**があれば列挙し、「セッション外の変更のため対象外にした」旨を添える。

公開済み記事にデモを追加した場合（手順 1.7 で検出）は、あわせて次を報告する。

- **検出した記事とデモ**（記事タイトル・ルート・追加された（差し替わった）コンポーネント名）。
- **`draft: true` を戻したこと**と、**その記事が一時的に非公開になる**こと。ここは黙って済ませない。
- **再公開の手順**: `draft: true`（と直前の空行）を外して `/commit-this` を実行すれば、手順 1.5 が公開を検出して `publish-article` が回り、OGP 画像もそこで生成し直される。デモを続けて足す予定なら、入れ終えてから外せばよいことも添える。
- **タスクリストの追随**（手順 1.7 b）: 再実行した `--check` の結果と、`--write` したなら書き換えたファイル。`[x]` / `[~]` の矛盾警告（draft に戻した記事が手記録のマーカーを持っている）が出たときはその内容。

非 draft 記事の本文を変更した場合（手順 1.8 で検出）は、あわせて次を報告する。

- **記法整備タスクリストで `[x]` を `[ ]` に戻した記事**（記事タイトル・ルート）。戻さなかった記事があるなら、その理由（下書きのまま・frontmatter のみの変更・このコミットで `[x]` を付けたばかり）。
- **記法の整備が未実施に戻ること**と、あとから `/format-math-notation <slug>`（複数記事はカンマ区切り）で回し直せること。
- **文体解析タスクリストで `[x]` を `[~]`（再分析待ち）にした記事**（記事タイトル・ルート）と、あとから `/author-style-analyzer <slug>`（複数記事はカンマ区切り）で再分析できること。**再分析が必要かどうかは analyzer が本文の差分を見て判断するので、ここで要否を決めない。**

記事を公開した場合（手順 1.5 で検出）は、あわせて次を報告する。**内容は `publish-article` の報告を引き継ぐ**（自分で数え直したり、言い換えたりしない）。

- **ディレクティブの残存チェックの結果**（`publish-article` 手順0）。残存が無ければ「残存なし」の一言でよい。
- **記法ゲートの結果**（`publish-article` 手順0.5）: `lint:svx:syntax` が0件だったか、`format-math-notation --auto` を回して0件にしたか。書き換えた場合は**記法整備のコミットの件名**も示す。**advisory の残件**は件数と、`/format-math-notation <slug>` で片付けられることを添える。
- **ゲートで止まった場合**は、残っていたディレクティブと、**コピペで実行できる案内のコマンドをそのまま載せる**（要約・作り直しをしない）。あわせて次の2点を伝える。
  - 公開時タスク（`visual` フラグ・文体解析タスクリスト・OGP 画像）は**未実行**であること。
  - ディレクティブに対応したあと `/publish-article <slug>` を実行し、その変更を**別コミットにする**必要があること。
- **公開時タスクの実行結果**: `visual` フラグ（追加した／図解が無いので不要／すでにあった）、文体解析タスクリスト（`[draft]` を外した／該当行が無く未更新）、OGP 画像（生成したルートと PNG のパス／未実施ならその理由）。
- **残っている公開後タスク**: 文体スタイルガイドの更新（`/author-style-analyzer <slug>`。複数記事はカンマ区切りでまとめて実行できる）と、**push したうえで**の PR 説明文の更新（`/update-pr-description`）。この2つは自動実行しないので、コマンドを添えて促す。
- **未分析記事の残件**: `publish-article` が出した件数とスラッグの一覧をそのまま載せる（**「ほか N 件」と省略しない**）。次にどこまで `/author-style-analyzer` にかけるかの判断材料になる。

## 注意事項

- **`main` に直接コミットしない**（手順 0）。`main` にいたら `git switch -c` で新しいブランチを切ってからコミットする。ブランチ名は事前承認を求めず決めてよいが、報告で必ず伝える。
- **push しない。** push は別途ユーザーの明示指示があってから。
- **コミットメッセージの事前承認は求めない。** 組み立てたらそのままコミットし、**完了後に件名を報告する**（手順 6）。メッセージは一時ファイルに書き出さず、ヒアドキュメントで直接渡す。
- `git add -A` / `git add .` / `git commit -a` は禁止。常にパス明示。
- **セッション外の未コミット変更を勝手にコミットしない。** 迷ったら対象リストをユーザーに確認する。ただし**引数でパスを明示指定された場合はそのパスが対象**（「入力」参照）。報告時にセッション外の変更である旨を伝える。
- `[skip ci]` の判断は必ず**未 push コミット全体**（`git log HEAD --not --remotes`）を見て行う。今回のコミットがドキュメント・スキルのみでも、未 push に app 変更があれば付けない。
- 付けないと判断したコミットでは、**件名・本文のどこにも `[skip ci]` という文字列を残さない**。打ち消しの説明として書いた場合でも CI がスキップされる。
- コミットの分割が読みやすさに資する場合（記事の公開と無関係な雑多な変更が混ざる等）は分割を提案・実施してよい。
- **公開時タスクの手順を本スキルに書き戻さない。** 正典は `publish-article`（`visual` フラグ・文体解析タスクリストの `[draft]` 解除・OGP 画像の3つを実行し、`author-style-analyzer` と `update-pr-description` は自動実行しない）。構成が変わったときは README「記事の公開（draft を外したとき）」と `publish-article` を更新する。
- **記法ゲートが記事を書き換えたら、公開コミットより先に独立したコミットにする**（手順 1.55）。記法の機械的な変換と本文の変更を混ぜない。分けられない場合は無理に分けず、本文でその旨に触れる。
- **公開を検出したら、フェーズを分けて2回呼ぶ**（`--before-commit` はコミット前、`--ogp` はコミット後。手順 1.5 a・手順 5.5）。順序を入れ替えると、`visual` フラグやタスクリストが記事コミットに乗らない／OGP 生成物が記事本文と同じコミットに混ざる。
- **ディレクティブの残存でゲートが閉じたら、公開時タスクと OGP は飛ばすがコミットは通常どおり進める**（手順 1.5 a）。案内された対応をこのスキルの中で実行しない。ユーザーが対応したあと `/publish-article <slug>` を別コミットで反映する。
- **タスクリストと YAML の照合を手作業でやらない**（手順 1.6）。`scripts/sync-tasklists.mjs` が正典。目視で突き合わせると、節をまたぐ移動や片方のリストだけの欠落を確実に取りこぼす。逆に、スクリプトが出した差分を**確認なしに `--write` しない**。
- OGP 生成で対話が必要になっても**勝手に決めない**（改行位置・図版の要否・白背景の透過）。`generate-ogp-image` の手順に従って確認する。
- **公開済み（非 draft）の記事にデモを追加したら、frontmatter に `draft: true` を戻す**（手順 1.7）。OGP 画像はデモの画面写真を図版にしているため、**再公開のタイミングで公開時タスクに作り直させる**のがこのリポジトリの流れ。**デモ追加のために OGP 画像をこのスキルで生成・再生成しない。**
- **`draft` を戻すのは記事を一時的に非公開にする操作。** 手順 6 で必ず報告し、再公開の手順を添える。逆に、**このスキルが `draft: true` を外すことはしない**（公開の判断は著者）。
- **`draft` を戻したらタスクリストの整合を取り直す**（手順 1.7 b）。frontmatter の `draft` が変わるので、手順 1.6 で得た結果は古くなる。
- **非 draft 記事の本文を変えたら、記法整備タスクリストの `[x]` を外し、文体解析タスクリストを `[~]` にする**（手順 1.8）。どちらの `[x]` も当時の本文に対する記録なので、本文が動けば無効になる。**下書き（`draft: true`）の記事と、frontmatter だけの変更では触らない。** また、`format-math-notation` や `author-style-analyzer` を回して `[x]` を付けたコミット自身では戻さない（記録が残らなくなる）。記法整備だけの書き換えでは文体解析タスクリストを触らない。
- **文体解析タスクリストは `[ ]` に落とさない**（手順 1.8 b）。`[ ]` は「一度も分析していない」を意味し、`author-style-analyzer` の再分析確認（`分析時点` の SHA と本文差分の突き合わせ）を迂回してしまう。再分析待ちは `[~]` で表す。
- **`[x]` の解除を `sync-tasklists.mjs` に期待しない。** スクリプトは `[x]` も `[~]` も作りも消しもしないので、手順 1.8 の書き換えは手で行うのが正しい。
