# コミット作成スキル (commit-this)

**現在のセッションで変更したファイルだけ**を対象に、CLAUDE.md の「Git 規約」「品質チェック」に沿ったコミットを 1 つ（必要なら複数）作るためのスキルです。

このスキルがやること・やらないことを最初に確認する。

- **やること**: コミット対象の確定（**引数でパスが指定されていればそれだけ**、無ければセッションで触ったファイル） → **記事の公開（`draft` 削除）の検出と公開時タスクの自動実行** → コミット対象の分類 → 未 push コミットを見た `[skip ci]` 判断 → 日本語コミットメッセージの組み立て → 明示パス指定でのコミット。
- **やらないこと**: `push` はしない。`git add -A` / `git add .` / `git commit -a` は使わない。**セッション外（ユーザーや別セッションが加えた）未コミット変更を巻き込まない。** 公開時タスクのうち**文体スタイルガイドの更新（`author-style-analyzer`）と PR 説明文の更新は自動実行しない**（手順 1.5 c）。

## 入力

- **ファイルパス（任意・複数可）**: 引数にパスらしき語（`/` を含む、既知の拡張子で終わる、または実在するパスと一致する）が渡されたら、**そのパスだけをコミット対象にする**。パス以外の語はメッセージのヒント（下の「補足」）として扱う。
- **補足（任意）**: コミットメッセージのヒント、対象を絞る指示（「◯◯だけ」）、依頼の意図など。無くても動く。

### ファイルパスを指定されたときの具体例

| 引数 | コミット対象 |
| --- | --- |
| `/commit-this README.md` | `README.md` **だけ**。同じくセッションで触った他のファイルが dirty でも含めない |
| `/commit-this app/src/routes/color-theory/blackbody-radiation/+page.svx` | その記事 1 ファイルだけ（`.svx` なので手順 1.5 の公開判定・手順 4 の件名規約の対象になる） |
| `/commit-this README.md .claude/skills/commit-this/SKILL.md` | 指定した 2 ファイルだけ（空白区切りで複数指定） |
| `/commit-this app/src/lib/demo/illusion/` | ディレクトリ指定。その配下で dirty なファイルすべて（`git status --porcelain -- <dir>` で展開する） |
| `/commit-this README.md 公開手順の追記だけ先にコミット` | 対象は `README.md`。残りの語はメッセージのヒントとして使う |

指定時の扱い:

- **明示指定は「セッションで変更したファイルだけ」の制限より優先する。** ユーザーが名指ししたパスは、セッション外で変更されたファイルでも対象にしてよい（勝手に巻き込むわけではないため）。ただし手順 5 の承認時に、**セッションで触っていないファイルである**旨と差分の要点（`git diff HEAD -- <path>` で確認）を明示する。
- 指定パスに差分が無い（`git status --porcelain -- <path>` が空）ときは、コミットせずその旨を報告する。
- 指定パスの一部だけが dirty なときは、dirty なものだけを対象にし、差分の無いパスは報告で触れる。
- 指定が無い場合のみ、手順 1 のとおり「セッション変更リスト」から対象を決める。

## 手順

### 1. 現在のセッションで変更したファイルを特定する

> **引数でファイルパスが指定されている場合はこの手順を飛ばし、そのパス（ディレクトリなら配下の dirty なファイル）だけを対象にする**（「入力」の具体例を参照）。差分の有無だけ `git status --porcelain -- <path>` で確認し、手順 1.5 へ進む。

コミット対象は、**このセッションであなた（アシスタント）が作成・編集したファイル**に限る。

1. **セッションでの変更を思い出す。** このセッション中に Write / Edit / NotebookEdit で作成・編集したファイル、および Bash で動かした（`mv`・リネーム・フォーマッタ・生成物など）ファイルを列挙し、これを「セッション変更リスト」とする。これが対象判定の一次情報。
2. **`git status` と突き合わせる。**

   ```sh
   git status --porcelain
   ```

   - セッション変更リストのうち、実際に差分がある（`M` / `A` / `??` / ステージ済み）ものだけを残す。差分が無いものは編集後に元へ戻った等なので除外する。
   - **git 上は dirty だが、セッション変更リストに無いファイル**は、セッション開始時点で既に存在した変更（ユーザーや別セッション由来）とみなし、**コミットに含めない**。存在は手順 6 で報告する。
3. **巻き込みのエッジケースを確認する。** セッションで触ったファイルが、セッション開始時点で**既に別の未コミット変更を持っていた**場合（環境のセッション開始時 `git status` スナップショットに載っていたファイルなど）、そのファイルをステージするとセッション外の差分も一緒にコミットされる。該当があれば、その旨をユーザーに伝えて含めてよいか確認する。
4. **セッションの記録が無いとき**（別セッションで加えた変更を後からコミットする等で、自分が編集した記憶が無い場合）は推測しない。`git status` を提示し、どのファイルを対象にするかユーザーに確認する。

> `git add -A` / `git add .` / `git commit -a` は使わない。必ず**パスを明示**してステージする（手順 5）。

### 1.5. 記事の公開（`draft` 削除）を検出し、公開時タスクを実行する

コミット対象に `.svx`（記事ページ）が含まれる場合、**その差分で `draft: true` 行が削除されているか**を調べる。削除されていれば「この作業で記事を公開した」とみなし、README「記事の公開（draft を外したとき）」の公開時タスクのうち、**`visual` フラグの追加と OGP 画像の生成をこのスキルの中で自動的に実行する**。

```sh
# 対象 svx ごとに、HEAD からの差分（ステージ済み・未ステージの両方）を見る
git diff HEAD -- <対象の .svx パス> | grep -E '^[-+]draft: *true'
```

- `-draft: true` があり `+draft: true` が無い → **公開**。以下 a・b を実行する。
- どちらも出ない／両方出る → 公開ではない。そのまま手順 2 へ進む。
- **新規追加ファイルで最初から `draft: true` が無い**場合は、実質的な新規公開ページだが「draft を外した」わけではないので、公開時タスクを実行してよいか**ユーザーに確認**してから進む（このリポジトリでは新規ページを `draft: true` で作るのが通常なので稀）。

#### a. `visual` フラグを追加する（コミット前）

`visual` はコミット対象の `.svx` 自身を書き換えるので、**ステージ前**に済ませて同じコミットに載せる。

```sh
grep -q '\$lib/demo/' <file>        # 図解コンポーネントを使っているか
grep -qE '^visual: *true' <file>    # すでにフラグがあるか
```

- **図解あり かつ フラグ無し** → frontmatter に `visual: true` を追加する。位置は `grades:` 行の直後（`grades:` が無いページは `group:` 行の直後、どちらも無ければ frontmatter を閉じる `---` の直前）。追加したらコミット本文でその旨に触れる。
- **図解なし** → 何もしない。判定に使うのは `$lib/demo/` の import だけで、**Mermaid 図だけのページにはフラグを付けない**運用。
- **すでにフラグがある** → 何もしない。

#### b. OGP 画像は記事コミットの後に生成する

OGP の生成物は記事本文と別コミットにするのがこのリポジトリの慣例なので、**先に記事をコミットしてから**手順 5.5 で生成する。ここでは対象ルート（`app/src/routes/` を除いたパス）を控えておくだけでよい。

#### c. 自動実行しないもの

- **文体スタイルガイドの更新（`author-style-analyzer`）は自動実行しない。** 実行コストが大きく、分析範囲の指定という判断を伴うため。手順 6 で未実施として案内するにとどめる。
- **PR 説明文の更新（`update-pr-description`）も自動実行しない。** push 後でないと差分がリモートに反映されず、このスキルは push しないため。手順 6 で push 後の作業として案内する。

### 2. コミット対象を分類する（app・ビルド系 / ドキュメント・スキル系）

`[skip ci]` の判断（手順 3）とメッセージ規約（手順 4）のため、対象ファイルを次の 2 種に分類する。

- **app・ビルド系（CI 対象）**: `app/**`（`.svx`・`.css` を含む）、ルートの `package.json`・lockfile・`*.config.*`・CI 設定など、**アプリの実行・ビルドに関わる**ファイル。
- **ドキュメント・スキル系（CI 非対象）**: `docs/**`、`spec/**`、`.claude/skills/**`、ルートの `*.md`（`CLAUDE.md` / `README` など）、その他アプリの実行に関わらない Markdown。

> **注意**: `.svx` は `app/` 配下の記事ページでビルド対象なので、**app・ビルド系**として扱う（`[skip ci]` の対象外）。「Markdown だから CI 非対象」と早合点しない。

> **例外（OGP 生成物）**: `app/static/ogp/**`・`ogimage/data/**`・`app/src/lib/meta/og-manifest.json`・`ogimage/OGP-TASKLIST.md` は `app/` 配下を含むが、アプリのロジックではなくメタデータ・静的アセットなので **CI 非対象扱い**（CLAUDE.md の Git 規約に明記）。これらだけのコミットは `[skip ci]` の候補になる（ただし手順 3 の未 push 判定が優先）。

### 3. `[skip ci]` を付けるか判断する

CLAUDE.md の規約をそのまま適用する。判断材料として**未 push コミット**を確認する。

```sh
# 未 push コミット一覧（upstream 未設定でも動く：リモートに存在しないコミットを列挙）
git log --oneline HEAD --not --remotes

# 未 push コミットが触れているファイル一覧
git log HEAD --not --remotes --name-only --pretty=format: | sort -u | sed '/^$/d'
```

判断ルール:

- `[skip ci]` を付けてよいのは、**今回のコミット対象が丸ごとドキュメント・スキル系のみ**（app・ビルド系を 1 つも含まない）の場合だけ。
- **さらに、既存の未 push コミットに app・ビルド系の変更が 1 つでも含まれる場合は、たとえ今回のコミットがドキュメント・スキルのみでも `[skip ci]` を付けない。** 先頭コミットの `[skip ci]` は push 全体の CI をスキップしうるため。この場合は、**コミット本文にその理由を 1 行残す**（下の例）。
- 上記以外（今回のコミットが app・ビルド系を含む、または混在）→ `[skip ci]` は付けない。

まとめると、**「今回の対象に app・ビルド系が無い」かつ「既存の未 push コミットにも app・ビルド系が無い」→ 付ける。どちらかに app・ビルド系があれば付けない。**

> **付けないと判断したら、件名にも本文にも `[skip ci]` という文字列を書かない。** CI のスキップ判定はコミットメッセージ全体（本文を含む）を対象とするため、「`[skip ci]` は付けない」と打ち消しで書いても、その記述自体でスキップが有効になってしまう。理由を残すときは角括弧つきの表記を避ける。

`[skip ci]` を抑止した場合の本文注記の例:

```
未 push コミットに app 配下の変更が含まれるため、規約に従い CI スキップ指示は付けない。
```

### 4. コミットメッセージを作る（日本語・CLAUDE.md Git 規約）

- **件名は必ず日本語。** 変更を端的に表す。
- **本文（依頼に基づく変更の場合）**: 何を変えたかだけでなく、**どんな依頼で・なぜそう変えたか（意図・背景）**を日本語で数行残す。件名だけで意図が伝わるなら本文は省いてよい。
- `[skip ci]` を付ける場合は**件名の末尾**に置く（例: `景観色彩ガイドの用語を統一 [skip ci]`）。付けない場合は、**本文にも `[skip ci]` という文字列を書かない**（手順 3 の注記を参照）。

#### `.svx`（記事ページ）の件名規約

対象に `.svx` が含まれる場合、frontmatter の `title:` から記事タイトルを取り、次のいずれかにする。

- **AI 初稿**（このセッションで雛形→本文を新規に書き起こした場合）: `記事タイトル [ai-draft]`
- **初稿ではないが AI の修正のみ**: `記事タイトル：修正内容 [ai-draft]`
- **人間が依頼した修正 / `author-style-writer` の編集モードで指示された修正**: `記事タイトル：依頼された修正内容`（`[ai-draft]` は付けない。依頼であることが分かるように書き、本文に依頼・意図を残す）
  - 例: `景観色彩の考え方：依頼に基づき導入文を追記`

初稿かどうかは、そのコミット前まで `draft` の雛形で本文が無く、今セッションで本文を書き起こしたなら「初稿」と判断する。

> 記事とそれ以外（コンポーネント・YAML 等）を 1 回の作業で触った場合、記事の公開・執筆が主眼なら記事タイトル基準の件名にし、本文でその他の変更に触れる。分けた方が履歴が読みやすいなら**コミットを分割**してよい（記事＝`.svx` と、それ以外を別コミットにする等）。分割時は各コミットで手順 2〜4 を個別に適用する。

#### 末尾のトレーラ

このリポジトリの慣例に従い、コミットメッセージの末尾に次の 1 行を付ける（本文がある場合は 1 行空けてから）。

```
Co-Authored-By: Claude Opus 4.8 <noreply@anthropic.com>
```

### 5. コミットする

1. **品質チェック（必要な場合）**: 対象に型チェックが有効なファイル（`.ts` / `.js` / `.svelte`。ただし `.svelte` の CSS のみ変更は除く）が含まれ、このセッションでまだ `npm run check` を通していない場合は、コミット前に `app` ディレクトリで実行し、エラー・警告を解消する。`css` / `svx` / `md` のみのコミットなら不要。
2. **メッセージを提示して承認を待つ。** 手順 4 で組み立てた件名・本文・トレーラを、そのままの形でチャット上に提示する。**scratchpad などの一時ファイルに書き出して黙ってコミットしない。** ユーザーの承認を得てから次へ進み、修正指示があれば反映して再提示する。
3. **明示パスでステージ**する。

   ```sh
   git add -- <path1> <path2> ...
   ```

4. **コミット**する。本文・改行・日本語を保つため、ヒアドキュメントで標準入力から渡す（コマンド自体にメッセージが見える形にする）。

   ```sh
   git commit -F - <<'EOF'
   <件名>

   <本文>
   EOF
   ```

   件名だけで本文が無い場合は `-m "<件名>"` でよい。
5. `push` はしない。

### 5.5. 公開記事の OGP 画像を生成し、別コミットにする

手順 1.5 で公開を検出した記事がある場合のみ実行する（無ければ飛ばす）。

1. **生成する。** 控えておいたルートを引数に `generate-ogp-image` スキルを実行する（Skill ツール。複数記事なら 1 ルートずつ実行する）。

   ```
   /generate-ogp-image /<route>
   ```

   - タイトルの改行位置・図版の要否・白背景の透過は、**そのスキルの手順に従って対話で確認する**（勝手に決めない）。
   - `ogimage/` の依存・フォントが未整備などで生成に失敗した場合は、**記事のコミットはそのままに**、OGP を未実施として手順 6 で報告し、手動で実行するコマンドを案内する。ここで詰まっても記事コミットは巻き戻さない。

2. **生成物を別コミットにする。** `generate-ogp-image` が更新するのは次の4種。

   - `app/static/ogp/<route>.png`
   - `ogimage/data/<route>.json`（図版があれば `ogimage/data/assets/<route>/` も）
   - `app/src/lib/meta/og-manifest.json`
   - `ogimage/OGP-TASKLIST.md`

3. **件名**は `<記事タイトル>のOGP画像を生成`（複数記事なら `<A>・<B>のOGP画像を生成`）。`[skip ci]` は手順 3 のルールで判断する。**直前の記事コミット（`app/**` の `.svx`）が未 push で残るため、通常はここで `[skip ci]` を付けられない**。付けないと判断したら、件名・本文のどこにも `[skip ci]` という文字列を書かない。
4. 手順 5 と同様に、**メッセージを提示して承認を得てから**コミットする。

### 6. 報告する

- コミット対象のファイル一覧（app・ビルド系 / ドキュメント・スキル系の分類つき）。
- `[skip ci]` を付けたか／付けなかったかと、その理由（未 push コミットの状況）。
- コミットメッセージ（件名）とコミットハッシュ。`git log -1 --stat` で確認結果を示す。
- **コミットに含めなかった dirty ファイル**があれば列挙し、「セッション外の変更のため対象外にした」旨を添える。

記事を公開した場合（手順 1.5 で検出）は、あわせて次を報告する。

- **公開時タスクの実行結果**: `visual` フラグ（追加した／図解が無いので不要／すでにあった）と、OGP 画像（生成したルートと PNG のパス／未実施ならその理由）。
- **残っている公開後タスク**: 文体スタイルガイドの更新（`/author-style-analyzer <slug>`。複数記事はカンマ区切りでまとめて実行できる）と、**push したうえで**の PR 説明文の更新（`/update-pr-description`）。この2つは自動実行しないので、コマンドを添えて促す。

## 注意事項

- **push しない。** push は別途ユーザーの明示指示があってから。
- **コミットメッセージは提示 → 承認 → コミットの順。** 一時ファイルに書いて無断でコミットしない。
- `git add -A` / `git add .` / `git commit -a` は禁止。常にパス明示。
- **セッション外の未コミット変更を勝手にコミットしない。** 迷ったら対象リストをユーザーに確認する。ただし**引数でパスを明示指定された場合はそのパスが対象**（「入力」参照）。承認時にセッション外の変更である旨を伝える。
- `[skip ci]` の判断は必ず**未 push コミット全体**（`git log HEAD --not --remotes`）を見て行う。今回のコミットがドキュメント・スキルのみでも、未 push に app 変更があれば付けない。
- 付けないと判断したコミットでは、**件名・本文のどこにも `[skip ci]` という文字列を残さない**。打ち消しの説明として書いた場合でも CI がスキップされる。
- コミットの分割が読みやすさに資する場合（記事の公開と無関係な雑多な変更が混ざる等）は分割を提案・実施してよい。
- **自動実行する公開時タスクは `visual` フラグと OGP 画像の2つだけ。** `author-style-analyzer` と `update-pr-description` は自動実行しない（手順 1.5 c）。公開時タスクの構成が変わったときは README「記事の公開（draft を外したとき）」と本スキルの両方を更新する。
- **`visual` の追加はコミット前、OGP の生成はコミット後**（手順 1.5 a・手順 5.5）。順序を入れ替えると、フラグが記事コミットに乗らない／OGP 生成物が記事本文と同じコミットに混ざる。
- OGP 生成で対話が必要になっても**勝手に決めない**（改行位置・図版の要否・白背景の透過）。`generate-ogp-image` の手順に従って確認する。
