# Author Style Writer

分析済みのスタイルガイドを参照し、著者らしい文章を生成、レビュー、推敲する。

このSkillはスタイル分析を行うためのものではない。既存ガイドに根拠がない特徴を、新たな著者の癖として推測して追加しない。

## 入力とモード

依頼内容と引数から、次のモードを判断して動く。読み込むスタイルガイドはモードごとに変わる（→「参照するスタイルガイド」）。

- **生成モード**（既定）: 白紙・雛形・書きかけのファイルに、著者らしい本文を新しく書く（→「基本ワークフロー」「既存コンテンツの扱い」）。
- **推敲モード**: すでにある文章を、依頼された範囲で見直す（→「既存文章を推敲する場合」）。
- **編集モード**: すでに本文のある記事ページに、指示された編集を加える（→「記事ページを編集する場合」）。局所的な言い回しの修正だけなら「編集・最小」として扱う。

引数（いずれも省略可）:

- **slug**: 対象記事ページのスラッグ（＝ディレクトリ名）。セッションの文脈で対象が明確なら省略してよい。
- **edit_instruction**: 編集指示（どこを・どう変えたいか）。これが渡された、またはすでに本文のある記事の編集を依頼された場合は、編集モードで動く。
- **keywords**: 本文に含めたいキーワード（カンマ区切り）。主に生成モードで使い、渡されたキーワードはすべて本文中で必ず取り上げる。編集モードでも加筆系の指示であれば加味してよい。

例: `/author-style-writer camera-capture-and-cg 「ピンホールカメラ」の節に焦点距離の説明を加筆して`

## 参照するスタイルガイド

### 必須の記法・書式ルール

本文を書く前に、リポジトリ直下の `writing-guides/syntax-guide.md` と `writing-guides/math-notation-guide.md` を必ず読み、そのすべてのルールに従う。これらは記事本文の記法・書式（独自ディレクティブ、`:Anki[]`、数式、コード、禁止事項など）を定めた必須ガイドで、著者の文体に関わらず常に適用する。**数式（KaTeX）の記法と、その表記に関わるインラインコードの規約（数字のインラインコード化・前後の空白）は `math-notation-guide.md`、それ以外の記法は `syntax-guide.md` が持つ。** 文体上の癖よりも、この記法・書式ルールを優先する。

**強調は `:Anki[]` に一本化し、`:Mark[]` は自分から使わない。** `:Mark[]` は暗記モードで隠れない強調で、どの語をそれにするかは著者（人間）が判断する領域なので、このスキルの側から選ばない。既存の `:Mark[]` は `:Anki[]` に変えずそのまま残す（→ `syntax-guide.md` ルール1）。

記法ルールのうち機械的に判定できるものは textlint で検査できる。**本文を書き終えたら、モードにかかわらず `npm run lint:svx` を通す**（→「記法・表記チェック」）。

### 著者の文体を再現するガイド

そのうえで、著者らしい文章にするために `writing-guides/` 配下の次の4ガイドを使う。どれを読むかはモードで決まる（→「モード別の読み込み範囲」）。

- `writing-guides/thinking-flow.md`
  - 何をどの順番で考え、どの地点で説明を補うか
- `writing-guides/writing-style.md`
  - 記事、セクション、段落、文をどう構成するか
- `writing-guides/stylistic-quirks.md`
  - 語り口、頻出表現、文末、接続表現、表記上の癖
- `writing-guides/refine-style.md`
  - AI生成文に対して著者が行いやすい修正

`writing-guides/` に見つからない場合は、リポジトリ内を検索して保存場所を特定する。

### モード別の読み込み範囲

4ガイドは合計で大きいため、**モードに応じて必要なガイドだけを読む。** `syntax-guide.md` と `math-notation-guide.md` は全モードで必須。

| モード | 読むガイド（`syntax-guide.md`・`math-notation-guide.md` に加えて） | 読まないガイド |
| --- | --- | --- |
| 生成 | `thinking-flow.md`・`writing-style.md`・`stylistic-quirks.md`・`refine-style.md`（全部） | — |
| 推敲 | `writing-style.md`・`stylistic-quirks.md`・`refine-style.md` | `thinking-flow.md` |
| 編集 | `refine-style.md`・`stylistic-quirks.md` | `thinking-flow.md`・`writing-style.md` |
| 編集・最小 | `refine-style.md` | 他の3ガイド |

- **生成モードでは4ガイド全部を読む。** 記事を新しく書き起こす作業では、何を説明するかの判断（`thinking-flow.md`）から表現（`stylistic-quirks.md`）まで全層が必要で、読み込み量を削るより品質を優先する。
- **推敲モードで `thinking-flow.md` を読まない**のは、説明する内容そのものを設計し直さないため。ただし依頼が「構成から見直す」「必要な説明が足りていないか見る」に及ぶ場合は生成モードと同じ範囲へ広げる。
- **編集モードの既定は `refine-style.md`＋`stylistic-quirks.md`。** 指示された箇所を直す作業の主力は修正傾向と言い回しである。
- **編集・最小**（語句の言い換え、文末の調整、表記の統一など、構成に触らない局所的な修正）は `refine-style.md` だけでよい。
- **範囲は途中で広げてよい。** 節の追加・並べ替え・見出し構成の変更が必要になったら `writing-style.md` を、新しい説明を書き足す必要が出てきたら `thinking-flow.md` を、その時点で読む。**足りないまま推測で補わない。**

### 読まないファイル（分析専用）

次は分析専用の補助記録であり、**読み込まない**。文章生成・推敲・レビューの根拠には使わない。

- `writing-guides/pending/` 配下（`pending/thinking-flow.md` などの4ファイル）… 根拠不足・単一記事偏りなどで主要ルールに採用していない「保留」観察。`author-style-analyzer` が昇格判断のために読む。
- `writing-guides/evidence/` 配下の**ディレクトリごと**（`evidence/thinking-flow/`・`evidence/writing-style/`・`evidence/stylistic-quirks/`・`evidence/refine-style/`）… 記事1本につき1ファイルで、その記事が支持するルールIDと該当箇所・分析時点のコミットを記録した索引。`author-style-analyzer` が確度の算出と記事単位の再分析に使う。`_README.md` も含めて読まない。

`evidence/` を読んではいけない理由は `pending/` と同じ強さで守る。**ファイルパスが記事 slug になっており、中身はその記事の該当箇所そのものである。** 読むと**特定の記事の言い回しをなぞる**ことになり、「他の記事ファイルは文体の手本にしない」に正面から違反する。ルールの根拠を確かめたくなっても開かない。適用の判断はガイド本体に書かれた確度ラベルと適用条件だけで行う。

### ルール見出しの `[ID]`

ガイド本体のルール見出しには `### [WS-012] ルール名` のように ID が付いている。これは analyzer が支持記事数を機械集計するためのキーで、**執筆時は無視して読めばよい。** 生成する本文へ ID を書かない。

ガイド本体から `` `pending/…` `` や `` `evidence/…` `` を指す参照が出てきても、たどって読まない（本来ガイド本体にこれらの参照は置かれない）。

### 他の記事ファイルは文体の手本にしない

文体の出所は、上記のスタイルガイドだけである。個別の記事ファイル（他の `+page.svx` など）の本文を、言い回し・構成・導入の書き方の手本として読まない。

スタイルガイドは複数記事に**共通して言える傾向**を抽象化したもので、個々の記事の具体的な言い回しは意図的に落としてある。個別記事を直接手本にすると、その抽象化を飛び越えて特定の一文をそのまま持ち込むことになり、どの記事も似通ってしまう。共通する傾向はガイドから取り、具体的な文はこの記事のためにその都度考えて作る。

他の記事ファイルを開いてよいのは、**相互リンクのため**に限る。次を確認する目的でだけ参照する。

- リンク先が実在するか、正しいパス／slug は何か
- リンク先のタイトル・見出し・扱っている範囲（重複や矛盾を避けて正確にリンクするため）

参照の際にそこで目にした導入文・説明文・言い回しを、単語だけ差し替えて流用しない。文の構造や語順をなぞるのも流用にあたる。

導入文のように `writing-guides/syntax-guide.md` で書き方（テイスト）が定まっているものも同じである。規約に従うのであって、他記事の実際の導入文を写すのではない。規約を踏まえたうえで、今回の記事の目的・テーマに即して、その都度ゼロから考えて書く。

**流用チェック**: 書いた文が、名詞をほかの記事のものに入れ替えるだけで別の記事にもそのまま通用してしまうなら、それは流用である。スタイルガイドに立ち返り、この記事固有の目的から考え直して書き直す。

## 優先順位

スタイルガイド同士が競合する場合は、次の順序で判断する。

1. ユーザーが今回明示した指示
2. 記事の目的と技術的な正確さ
3. `writing-guides/syntax-guide.md`・`writing-guides/math-notation-guide.md`（記法・書式の必須ルール）
4. `thinking-flow.md`
5. `writing-style.md`
6. `refine-style.md`
7. `stylistic-quirks.md`

表面的な言い回しより、説明の目的、思考の流れ、情報構成を優先する。

この順序は、そのモードで読んだガイドの間で適用する。モードの範囲外で読んでいないガイド（編集モードの `writing-style.md` など）の内容を推測で補って優先順位に持ち込まない。必要になったらそのガイドを読む（→「モード別の読み込み範囲」）。

各ガイド内では、ルールに付いた `確度` ラベルで当てる強さを判断する。`強い傾向` は既定で当て、`条件付きの傾向` は適用条件に合うときだけ当て、`弱い傾向` は積極的に適用しない。確度の根拠は書かれていない（分析側の `evidence/` にある）。**書かれていないことを理由に確認しに行かず、ラベルをそのまま使う。**

## 記法・表記チェック

`math-notation-guide.md` の記法ルールのうち機械的に判定できる4つと、表記揺れの統一は textlint で検査できる。**生成・推敲・編集のどのモードでも、本文の変更を終えたら `app` ディレクトリで実行し、エラーを解消してから報告する。**

```bash
npm run lint:svx        # 検査する（記法＋表記揺れ）
npm run lint:svx:fix    # 自動修正できるものを直す
```

検査されるのは次の4つの記法ルール（詳細は `app/textlint/README.md`）。

| ルール | 内容 |
| --- | --- |
| `svx-number-in-code` | 数字は必ずインラインコードにする |
| `svx-math-function-in-code` | 数学で定義されている関数名（`sin`・`cos` など）もインラインコードにする |
| `svx-no-space-around-code` | インラインコードの前後には空白を置かない |
| `svx-inline-math-spacing` | インライン数式（`$$...$$`）の前後には半角スペースを置く |

あわせて、`app/textlint/prh.yml` の辞書で**表記揺れ**を検査する（主な項目は `もともと`→`元々`、形式名詞の `ぶん`→`分`、`あいだ`→`間` など。全項目は `app/textlint/README.md` の表）。指摘は辞書に基づくので、**指摘どおりに直し、辞書を書き換えて指摘を消すことはしない**（辞書に載せる表記を決めるのは著者）。

- **`npm run lint:svx:fix` に任せきりにしない。** 英字に隣接する数字（`600nm`・`3DCG` など）と、引数が続く関数名（`sin(x)`）は、どこまでを囲むかが判断を要するため自動修正されず報告だけが出る。書いた内容に照らして手で直す。
- **`.svx` だけの変更なら `npm run check` は不要**（CLAUDE.md「品質チェック」）。代わりにこの記法・表記チェックを通す。
- **textlint が見るのは上の4ルールと表記揺れの辞書だけ。** ボールド体の禁止・`:Anki[]` の乱用・分類タグとフロントマターの整合・ディレクティブの使い分けなどは検出されないので、`syntax-guide.md`・`math-notation-guide.md` の「仕上げチェックリスト」で自分で確認する。**エラー0件は記法ルールを満たした証明にはならない。**
- **既存記事は記法ルールのベースラインで対象外になっていることがある。** ルール導入時点で違反を含んでいた記事は `app/.textlintignore` に列挙されており、その記事を編集しても記法ルールは検査されない（`npm run lint:svx:syntax` のパスだけがこの影響を受ける）。その場合は、自分が書いた・直した箇所については記法ルールを守り、**記事全体の既存の違反をついでに直そうとしない**（依頼されていない変更になる）。ファイル単体で確認したいときは、ベースラインを無効にして次のように実行できる（記事の未修正部分のエラーも出るので、自分の変更箇所だけを見る）。

  ```bash
  npx textlint --rulesdir textlint/rules --ignore-path /dev/null src/routes/<...>/+page.svx
  ```

- **表記揺れはベースラインの対象外で、既存記事でも必ず検査される**（`npm run lint:svx:notation` は全記事が対象）。編集した記事で表記揺れの指摘が出たら、その箇所は直す。

## 基本ワークフロー（生成モード）

このワークフローは生成モードの手順である。`syntax-guide.md`・`math-notation-guide.md` と4ガイド全部を読んで進める（→「モード別の読み込み範囲」）。推敲・編集の場合は「既存文章を推敲する場合」「記事ページを編集する場合」へ進み、読み込み範囲もそちらに従う。

### 1. 執筆条件を整理する

執筆前に次を確認する。

- 記事の目的
- 想定読者
- 読者の前提知識
- 記事タイプ
- 扱う範囲
- 扱わない範囲
- 必要なコード、図、数式、例
- 既存記事との関係
- 目標とする長さ

情報が不足していても、合理的に推測できる場合は作業を進める。重要な仮定は成果物内で不自然にならない形に調整する。

対象ファイルにすでに中身がある場合は、この段階で執筆対象箇所と執筆済み箇所を仕分ける（→「既存コンテンツの扱い」）。

### 2. 思考の流れを設計する

`thinking-flow.md`（生成モードで読むガイド）を参照し、書き始める前に内部的な執筆方針を整理する。

次を検討する。

- 読者が最初に知るべきこと
- 最初に定義を置くべきか、現象や例を置くべきか
- 読者が疑問を持ちそうな地点
- 抽象説明と具体説明を往復する地点
- コード、図、例、数式が必要な地点
- 説明を深掘りする箇所
- あえて省略する箇所
- 最後に読者へ残す理解

ガイドを固定的な構成テンプレートとして扱わない。記事の目的に応じて判断する。

### 3. 構成を作る

`writing-style.md`（生成・推敲モードで読むガイド）を参照し、記事の構成を決める。

次を確認する。

- 導入から本題への移行が自然か
- セクションごとの役割が明確か
- 一つの段落に論点を詰め込みすぎていないか
- 定義、理由、例、注意点の順番が適切か
- セクション同士が断絶していないか
- 箇条書きや表に逃げすぎていないか
- 記事タイプに合った構成になっているか

対象ファイルにすでに見出しが置かれている場合は、その構成を維持する。ただし見出しが TODO 見出し1つだけの場合は、このステップで見出し構成そのものを決める（→「見出しが TODO 見出し1つだけの場合」）。

ユーザーが本文を直接求めている場合は、不要なアウトラインだけを提示せず、本文を作成する。

### 4. 初稿を書く

初稿では、表現上の模倣よりも内容と説明の流れを優先する。

次を守る。

- 読者を置き去りにしない
- 専門用語を必要以上に早く導入しない
- 一般論だけで段落を埋めない
- 抽象説明だけで終わらせない
- 例を機械的に挿入しない
- 同じ結論を何度も言い換えない
- 過剰なまとめを避ける
- 技術的な正確さを文体より優先する
- 他の記事ファイルの文章をなぞらない。とくに導入文は、他記事の実際の導入を写すのではなく、規約とこの記事の目的から書き起こす（→「他の記事ファイルは文体の手本にしない」）

相互リンクを張るために他の記事ファイルを開く場合も、リンク先の確認だけに使い、そこの文章を手本にしない（→「他の記事ファイルは文体の手本にしない」）。

既存コンテンツがある場合は、「既存コンテンツの扱い」の仕分けに従い、執筆済みの敬体文章と見出し構成を変更せず、執筆対象箇所だけを埋める。

`keywords` が与えられている場合は、そのすべてを本文中で必ず取り上げる。各キーワードが自然に馴染む箇所を見つけて含める。

### 5. 表現を調整する

`stylistic-quirks.md`（生成・推敲・編集モードで読むガイド）を参照し、表面的な語り口を調整する。

頻出表現を単純に挿入しない。次を確認する。

- その表現が本来使われる文脈に合っているか
- 同じ文末が連続していないか
- 著者らしさを誇張していないか
- AIが著者を物真似しているような不自然さがないか
- 記事テーマ由来の語彙を文体と混同していないか
- 特定の他記事の言い回しをなぞっていないか（→流用チェック）

`stylistic-quirks.md`は文章全体の設計には使用せず、最終的な表現調整に使用する。

### 6. 推敲する

`refine-style.md`（全モードで読むガイド）を参照し、AI草稿に対して著者が行いやすい修正を適用する。

次の順序で確認する。

1. 技術的に正確か
2. 読者に必要な前提が不足していないか
3. 説明順が自然か
4. 不要な一般論が含まれていないか
5. 冗長なまとめや重複がないか
6. 段落の分割と接続が適切か
7. AIらしい定型表現が残っていないか
8. 著者らしくない語彙や語尾が残っていないか

修正傾向を無条件に適用しない。記事の目的と適用条件を確認する。

### 7. スタイルレビューを行う

完成稿を4つの観点でレビューする（生成モード）。推敲・編集モードでは、そのモードで読んだガイドに対応する観点だけを使う。

#### Thinking Flow

- 読者の理解が自然に進むか
- 疑問への補足が適切な位置にあるか
- 抽象と具体の行き来が不自然でないか

#### Writing Style

- 全体構成と段落構成が著者の傾向に合うか
- 固定的なテンプレートに見えないか
- 説明の順番が記事タイプに合うか

#### Stylistic Quirks

- 語り口が自然か
- 頻出表現を使いすぎていないか
- 著者らしさを表面的に誇張していないか
- 特定の他記事の言い回しをなぞっていないか（→流用チェック）

#### Refine Style

- AI草稿で繰り返し修正されてきた問題が残っていないか
- 過剰な一般論、強調、まとめが残っていないか
- 情報の追加、削除、並べ替えが必要でないか

### 8. 記法・表記チェックを通す

`npm run lint:svx` を実行し、検出されたエラーを解消する（→「記法・表記チェック」）。あわせて `syntax-guide.md`・`math-notation-guide.md` の「仕上げチェックリスト」のうち textlint が見ない項目を自分で確認する。

## 既存コンテンツの扱い

対象ファイルが白紙・雛形（`## TODO` / `## :WithGradeTag[TODO]{...}` のような TODO 見出しだけ）ではなく、**すでに何らかの中身が書かれている**場合は、本文を書き始める前に次の2種類へ仕分ける。

**執筆対象箇所**（今回埋める）:

- 箇条書きメモ（`-` などの箇条書きで、敬体の文章になっていない覚書）
- `TODO`（`## TODO` 見出し、`<!-- TODO: ... -->` コメント、`TODO:` で始まるメモなど）。ただし**図版・デモの TODO**（「〜のグラフ」「〜の図解」のように、本文ではなく図を入れたい旨のメモ）は本文で埋める対象ではない（→「図版の TODO は `:::Todo` にする」）
- `:::Add`（加筆したい箇所の指示）・`:::Delete`（消す予定の記述）・`:::Fix{target="text"}`（既存の記述への修正指示）。いずれも著者が残した申し送りなので、指示どおりに本文へ反映する（→「`:::Add` / `:::Delete` / `:::Fix` は指示として扱う」）
- `::ComingSoon`（未執筆を表すプレースホルダ）

**執筆済み箇所**（変更しない）:

- 敬体（です・ます調）で書かれた文章は執筆済みとみなし、本文・表現・順序を変更しない。

仕分けた結果に応じて次のルールに従う。

- **見出し構成は維持する。** すでに置かれている見出し（`## :WithGradeTag[...]` / `## :WithGroupTag[...]` など）のテキスト・順序・分類タグ（`grades` / `group`）を変更しない。執筆対象は各見出し配下の本文を埋めることに限る。ただし、ページ内の見出しが TODO 見出し1つだけの場合は例外で、見出し構成を自分で設計する（→「見出しが TODO 見出し1つだけの場合」）。
- **既存の `:Anki[]` は絶対に勝手に外さない。** すでに付いている `:Anki[...]` は、ユーザーの明示的な指示がない限り、囲む語も範囲もそのまま残す。編集・推敲・言い換えで対象語を含む文に手を入れるときも `:Anki[]` を落とさず、文を作り替えて対象語が別の位置へ動く場合は `:Anki[]` も一緒に動かす。これは記法の必須ルール（`writing-guides/syntax-guide.md` ルール1）の再掲・強調であり、文体上の判断で外してよいものではない。**既存の `:Mark[]` も同じ扱いで、外さず `:Anki[]` へ変えもしない。** 新しく強調を付けるときは `:Anki[]` を使う。
- **元のメモはコメントで残す。** 執筆対象だった箇条書きメモ・`TODO` メモは、執筆後に削除せず HTMLコメント `<!-- ... -->` で囲んで（執筆した本文の直前または直後に）残す。`::ComingSoon` プレースホルダはコメント化せず、本文に置き換えて消してよい。図版・デモの TODO はこの対象外で、次のルールに従う。
- **図版の TODO は `:::Todo` にする。** 図解・グラフ・インタラクティブデモを入れたい旨の TODO メモ（`TODO：〜のグラフ`、`<!-- TODO: 〜の図解 -->` など）は、本文の文章では埋めず、`:::Todo` ディレクティブに書き換えて、図が入るべき位置に残す。HTMLコメントのままにしたり、地の文の `TODO：〜` のままにしたりしない。記法とプレースホルダの書き方は `writing-guides/syntax-guide.md` ルール4に従う。図が無い間にデモコンポーネントを `import` してはいけない。
- **`:::Pending` は採否が未決なので触らない。** 中身は指示ではなく「採用するか決めきれていない候補の本文」で、採用・不採用を決めるのは著者。**ブロックも中身もそのまま残す**（勝手に本文へ馴染ませる・削除するのはどちらも禁止）。採否を尋ねるのは、公開時ゲート（`/publish-article`）で残存が検出されたときだけ。
- **`:::Add` / `:::Delete` / `:::Fix` は指示として扱う。** `:::Add` のブロックは「ここにこれを書き足したい」という加筆指示なので、その内容を本文の文章として書き、**ブロックごと削除する**（HTMLコメントで残さない）。`:::Delete` で囲まれた記述は「消す予定」の申し送りなので、**囲まれた記述もろともブロックごと削除する**。`:::Fix{target="text"}`（`target` 省略時も文章）は既存の記述への修正指示なので、該当箇所を直して**ブロックごと削除する**。**`:::Fix{target="svg"}` / `{target="demo"}` は図版・デモへの修正指示なので、このスキルでは手を付けず残す**（それぞれ `/svg-diagram-component`・`/add-threejs-demo` の領域）。指示の解釈に迷う場合は、勝手に決めずユーザーに確認する。記法は `writing-guides/syntax-guide.md` ルール4に従う。
- **執筆対象が無い場合は新規生成しない。** ファイル全体が敬体の文章で、箇条書きメモ・`TODO`・`:::Add`・`:::Delete`・`:::Fix{target="text"}`・`::ComingSoon` のいずれも無い場合は、生成に進まない。手直し・加筆が目的なら「既存文章を推敲する場合」の手順へ切り替える。

仕分けた執筆対象（どの見出しの下に何を書くか、もとになるメモ）は、以降の各ステップで参照する。

### 見出しが TODO 見出し1つだけの場合

ページ内の見出しが **TODO 見出し1つだけ**（`## TODO`、`## :WithGradeTag[TODO]{grades="1"}`、`## :WithGroupTag[TODO]{group="{['CG']}"}` など、見出しテキストが `TODO` のもの）の場合、それは維持すべき見出し構成ではなく、`create-*-page` スキルが置いた雛形のプレースホルダである。この場合は「見出し構成は維持する」を適用せず、**見出し構成を自分で考えて決める。**

これは、ページの中身が白紙の場合も、TODO 見出しの下に箇条書きメモがある場合も同じである（メモがあっても、見出しが TODO 1つだけなら構成は未決定とみなす）。

- 記事の目的・扱う範囲・もとになるメモから、大見出し（`##`）と必要に応じた中見出し（`###`）の構成を設計する（→「基本ワークフロー」の 2・3）。
- TODO 見出しはそのまま残さず、設計した見出しに置き換える。`TODO` という語を見出しテキストに残さない。
- 見出しの書き方・分類タグの記法は `writing-guides/syntax-guide.md` に従う。雛形の TODO 見出しに付いていた分類タグ（`grades` / `group`）を出発点に、内容ごとに分けられるなら見出しごとに絞り、分ける必要がなければフロントマターの分類をそのまま全見出しに付ける。**本文中の各見出しタグに現れた分類の和集合が、フロントマターの分類と一致している状態を保つ**（雛形の分類を削って和集合が欠けることのないようにする）。
- 導入文は最初の見出しの前に置く。TODO 見出しを置き換えたからといって、記事を見出しから始めない。
- もとになった箇条書きメモ・TODO メモは、「元のメモはコメントで残す」の原則どおり HTMLコメントで残す。図版・デモの TODO だけは例外で、`:::Todo` ディレクティブに書き換える（→「図版の TODO は `:::Todo` にする」）。

見出しが2つ以上ある場合、または1つでもそれが TODO ではない（すでに内容を表す見出しになっている）場合は、この例外にあたらない。「見出し構成は維持する」に従い、テキスト・順序・分類タグを変更しない。

## 記事ページを編集する場合（編集モード）

すでに本文のある記事ページ（CG `app/src/routes/cg/**/<slug>/+page.svx`、色の理論 `app/src/routes/color-theory/<slug>/+page.svx`、色の活用分野 `app/src/routes/color-fields/<slug>/+page.svx`）へ、指示された編集を加えるモード。

### E1. 対象ファイルを特定する

- slug が渡されていれば、3ルートツリーを横断して `<slug>/+page.svx` を探す。

  ```bash
  find app/src/routes/cg app/src/routes/color-theory app/src/routes/color-fields -type d -name "<slug>"
  ```

- slug が省略された場合は、セッションの文脈から対象ファイルを特定する。特定できなければユーザーに尋ねる。
- 0件なら該当ページが無い旨を伝えて中止する。複数件（別ツリーに同名 slug 等）なら候補パスを提示して確認する。
- パスから記事の種類を判別する（`cg/`→CG、`color-theory/`→色の理論、`color-fields/`→色の活用分野）。フロントマター（`title` / `draft`、CGは `group`、色記事は `grades`(+`useful`)）を読み、本文がすでに書かれていることを確認する。まだ雛形（`## TODO` だけ等）なら、編集ではなく生成モードに切り替える。

### E2. 編集指示を確定する

- `edit_instruction` が与えられていればそれを使う。無ければユーザーに尋ねる。
- 指示が曖昧で、対象箇所や変更の方向性が読み取れない場合は、編集前にユーザーへ確認する。
- ただし、方向性が `writing-guides/syntax-guide.md` の規約で定まる内容（例: 導入文のテイスト）であれば、質問せず規約に従って編集する。

### E3. 編集する

- **読むガイドは `syntax-guide.md`＋`math-notation-guide.md`＋`refine-style.md`＋`stylistic-quirks.md`。** 語句の言い換え・文末の調整・表記の統一のように構成に触らない修正なら `refine-style.md` だけでよい。節の追加・並べ替え・見出し構成の変更に及ぶ指示なら `writing-style.md` を、新しい説明を書き足す指示なら `thinking-flow.md` も読む（→「モード別の読み込み範囲」）。
- 実際の文章変更は「既存文章を推敲する場合」の原則に従う（全面改稿しない、依頼された範囲に限る、元の意味と有効な表現を保つ）。`writing-guides/syntax-guide.md`・`writing-guides/math-notation-guide.md` と読み込んだ文体ガイド（特に `refine-style.md`）を適用する。
- **指示の直接対象だけでなく、前後の文章・前後のセクションの「流れ」も整える**（接続の唐突さや重複が生じないようにする）。
- 「既存コンテンツの扱い」の原則を守る。編集対象でない敬体の既存文章は、意味・表現・順序を変えない。見出し構成（テキスト・順序・分類タグ）は、編集指示が明示的に求めない限り変更しない。
- **既存の `:Anki[]` / `:Mark[]` は絶対に勝手に外さない。** 編集指示が明示的に求めない限り、囲む語も範囲も保持する。編集対象の文を書き換える場合でも落とさず、対象語が動くなら一緒に動かす。`:Mark[]` を `:Anki[]` に変えることもしない（→「既存コンテンツの扱い」）。
- 相互リンクを新たに張る場合も、リンク先の確認だけに使い、そこの文章を手本にしない（→「他の記事ファイルは文体の手本にしない」）。

### E4. 記法・表記チェックを通して報告する

- 報告の前に `npm run lint:svx` を実行し、検出されたエラーを解消する（→「記法・表記チェック」）。対象記事がベースラインで対象外の場合は、自分が直した箇所について記法ルールを守れているかを確認する。
- 編集したファイルパスと、何をどう変えたかの概要。
- 流れを整えるために、指示の直接対象**以外**で調整した箇所。
- 推測・保留した要確認項目。
- `draft: true` はレビューが済むまで残すこと。

フロントマター（`layout` / `title`）は変更しない。見出しの分類タグ（`:WithGroupTag` の `group` ／ `:WithGradeTag` の `grades`）を増減した場合のみ、フロントマターの分類を本文中の分類タグの和集合に一致させる。

## 既存文章を推敲する場合

ユーザーが既存文章の修正を求めた場合は、内容を最初から全面的に書き換えない。

**読むガイドは `syntax-guide.md`＋`math-notation-guide.md`＋`writing-style.md`＋`stylistic-quirks.md`＋`refine-style.md`。** `thinking-flow.md` は読まない。ただし依頼が「必要な説明が足りていないか見る」「構成から作り直す」に及ぶ場合は、`thinking-flow.md` も読んで生成モードと同じ範囲で扱う（→「モード別の読み込み範囲」）。

次の順序で処理する。

1. 文章の目的を把握する
2. 技術的または論理的な問題を確認する
3. `refine-style.md`に該当する修正傾向を探す
4. `writing-style.md`に基づき構成を調整する
5. `stylistic-quirks.md`に基づき表現を調整する
6. 元の文章の意味と有効な表現を維持する
7. `npm run lint:svx` を通す（→「記法・表記チェック」）

変更量は、ユーザーの依頼に合わせる。読み込み範囲も変更量に合わせる。

- 軽い調整（`refine-style.md` だけで足りることが多い）
- 文体の統一（`refine-style.md`＋`stylistic-quirks.md`）
- 構成からの見直し（`writing-style.md` を加える）
- 全面的なリライト（`thinking-flow.md` も加え、生成モードと同じ範囲にする）

依頼されていない範囲まで変更しない。

## ガイドが不足している場合

スタイルガイドが存在しない、内容が薄い、または互いに矛盾している場合は、推測だけで著者の特徴を補わない。`evidence/` や個別記事を開いて埋め合わせることもしない。

なお、ルールに根拠が書かれていないのは「内容が薄い」ことではない。根拠は分析専用の `evidence/` へ分離してあり、執筆に必要な情報はルール欄・適用条件欄・確度ラベルに揃っている前提である。それでも判断がつかない場合は、次のように対応する。

その場合は次のように対応する。

- 利用できるガイドの範囲だけを適用する
- 不明な点は一般的に自然な文章として処理する
- 強い模倣を避ける
- 必要に応じて、分析Skillによるガイド更新が必要であることを示す

## 禁止事項

- 著者の記事本文をそのまま組み合わせて新しい文章を作る
- 個別の記事ファイルを文体・構成の手本として読み、その言い回しをなぞる
- `writing-guides/pending/`・`writing-guides/evidence/` 配下を読む（分析専用。ルールの根拠を確かめる目的でも開かない）
- 相互リンクのために開いた他の記事ファイルの文章（導入文・説明文など）を、単語だけ差し替えて流用する
- 頻出表現をすべての段落へ挿入する
- 語尾や接続詞だけで著者らしさを再現しようとする
- すべての記事を同じ構成にする
- 技術的な正確さを文体の再現より下位に置く
- ガイドにない特徴を著者固有の癖として追加する
- 推敲時に元の意図を無視して全面改稿する
- AIらしさを消すためだけに不自然な崩し方をする
- 既存記事に付いている `:Anki[]` / `:Mark[]` を、明示的な指示なく外す・入れ替える（推敲・言い換え・書き換えのついでに落とすことも含め、絶対にしない）
- 自分の判断で `:Mark[]` を新しく書く（強調は `:Anki[]` に一本化する。`:Mark[]` の使い所は著者が決める）

## 完了条件

次を満たした場合に完了とする。

- 記事の目的と読者に合っている
- 技術的または論理的に正確である
- 記法・書式が `writing-guides/syntax-guide.md`・`writing-guides/math-notation-guide.md` に従っている
- `npm run lint:svx` が通っている（ベースラインで対象外の記事では、自分が書いた・直した箇所が記法ルールを満たしている）
- 思考の流れが自然である
- 構成が著者の傾向を反映している
- 表現上の癖が過剰でない
- 過去に繰り返された修正傾向が反映されている
- 著者の物真似ではなく、自然な文章として読める
