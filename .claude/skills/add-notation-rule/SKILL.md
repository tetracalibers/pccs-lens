# 表記揺れルール追加スキル

記事本文（`app/src/routes/**/+page.svx`）の表記揺れを統一する辞書 `app/textlint/prh.yml`（`textlint-rule-prh`）に、指定された項目を追加するスキルです。辞書の仕組みと運用の正典は `app/textlint/README.md` にあります。

**表記揺れの検査（`npm run lint:svx:notation`）はベースライン（`app/.textlintignore`）の対象外で、常に全記事を検査します。** 辞書に1項目足した瞬間から、既存記事のその表記もすべて指摘対象になります。だからこそ、パターンを絞る作業（手順3・4）と、既存記事をどうするかの確認（手順7）がこのスキルの中心です。

## 入力

- **表記揺れのペア**（必須）: `直す前 -> 直した後` の組を、カンマ・読点・改行で区切って複数渡せる。

  ```
  /add-notation-rule この時 -> このとき, 例えば -> たとえば, あいだに -> 間に, ほかに -> 他に
  ```

  - 矢印は `->` / `→` / `=>` のいずれも受け付ける。**左が「直す前」（`pattern`）、右が「直した後」（`expected`）** で、この向きは反転しない。
  - 引数が無い場合、矢印が無くて向きが読めない場合は、**推測せずユーザーに尋ねる**（どちらの表記に寄せるかを決めるのは著者）。
  - 「直した後」の側に揺れの原因があるように見えても（`元々` と `もともと` のどちらに寄せるかなど）、指定された向きをこちらで判断し直さない。明らかに逆に見えるときだけ、理由を添えて確認する。

## 前提（辞書の仕組み）

手順に入る前に押さえておく点。詳細は `app/textlint/README.md` と `app/node_modules/prh/lib/rule.js`。

- 1項目は `expected`（直した後）・`pattern`（直す前）・`specs`（自己テスト）の組。`pattern` を `/…/` で書くと正規表現になり、`expected` では `$1` の後方参照が使える。
- **正規表現には `gmu` フラグが自動で付く。** `u` が付くため、`\-` のような余計なエスケープは起動時に `Invalid escape` で落ちる。記号を含む語は `/…/` で書き、エスケープは本当に必要な文字だけに絞る。
- **`specs` は起動時に検証される自己テスト。** 失敗すると `<expected> spec failed. "…", expected "…", but got "…"` で textlint 全体が動かなくなる。
- **`specs` が検証するのはそのルール単体。** 追加した項目が別の項目のパターンに当たって二重に書き換わるような干渉は specs では検出できないので、手順2の突き合わせと手順6の実行で確かめる。
- 検査対象は `src/routes/**/+page.svx`。コードブロック・インラインコードは Markdown パーサが別ノードにするため対象外。地の文・見出し・`:Anki[]` の中身は対象。
- **表記揺れのパスは記法ルールと違い `textlint/lib/svx.js` のマスクを通さない。** ディレクティブの属性やSvelteコンポーネントの props もパーサからはただのテキストに見えるため、自動修正がそこに及ぶことがある（手順7で diff を確認する理由）。

## 手順

### 1. ペアを解釈する

引数を区切って `直す前` / `直した後` の組に分解し、表にして確認する。ここでは辞書には触らない。

| # | 直す前 | 直した後 |
| - | ------ | -------- |
| 1 | この時 | このとき |

分解できない要素（矢印なし・3つ以上に割れる）があれば、その要素だけを挙げてユーザーに尋ねる。解釈できたものだけ先に進めない（辞書の追記は手順5でまとめて行う）。

### 2. 既存辞書と突き合わせる

`app/textlint/prh.yml` を読み、次を確認する。1つでも当たったら**追記せずユーザーに確認する**。

- 同じ `expected` または同じ `pattern` の項目が既にある（重複）。
- **逆方向の項目がある**（既存が `もともと → 元々` なのに `元々 -> もともと` を足そうとしている）。どちらに寄せるかは著者の判断。
- 追加する `expected` が、**既存の項目の `pattern` にマッチする**（追加した結果が別ルールにまた書き換えられ、修正が往復する）。既存の `/(?<!ゅ)([のなるいうつくすむり])ぶん/` のような正規表現の項目は、目視ではなく実際に当ててみて確かめる。
- 追加する `pattern` が、既存の `expected` にマッチする（同上の逆向き）。

### 3. 記事での出現を調べる（誤検出の洗い出し）

**この手順を飛ばさない。** 辞書は全記事に効くので、「直す前」の文字列が別の語の一部として使われていると、既存記事を壊す修正が入る。

```bash
cd app
grep -rhoE "この時.{0,6}" --include='+page.svx' src/routes | sort | uniq -c | sort -rn
grep -rhoE ".{0,4}ほかに" --include='+page.svx' src/routes | sort | uniq -c | sort -rn
```

- 「直す前」を含むが**別の語**である例を集める（`この時` に対する `この時代`・`この時期`・`この時点`、`ほか` に対する `〜にほかなりません`、`間` に対する `間もなく` など）。記事に出ていなくても、一般に成立する複合語は誤検出候補として数える。
- **「直した後」の表記も検索して、記事全体でどちらが優勢かを見る。** 指定が少数派に寄せる向きだった場合は、その事実（既存記事で何件書き換わるか）を添えて確認する。
- 記事に1件も出現しない語でも、辞書には追加する（これから書く記事のためのルールなので、出現0は追加しない理由にならない）。

### 4. パターンを設計する

手順3の結果から、項目ごとにパターンを決める。

| 状況 | 書き方 |
| ---- | ------ |
| 別の語の一部にならない | リテラルのまま（`例えば`） |
| 後ろに文字が続くと別語になる | 否定先読み `/この時(?![代期点間刻])/` |
| 前に文字が付くと別語になる | 否定後読み `/(?<!ゅ)…/`（既存の「ぶん」の項目が実例） |
| 送り仮名・活用で前後が変わる | キャプチャして `expected` に `$1` |
| 記号を含む | `/…/` で書き、`u` フラグで有効なエスケープだけ使う |

- 否定先読みに並べる文字は、**手順3で実際に見つかった続き字＋一般的な複合語の続き字**にする。迷ったら広めに取る（取りこぼしは指摘が出ないだけだが、行きすぎは本文を壊す）。
- 漢字→かなの向き（`例えば -> たとえば`）でも、その漢字が別語を作るなら同じように絞る。
- 設計したパターンと、それぞれに付ける `specs`（置き換わる例／置き換わらない例）を**表で提示して承認を得てから**手順5へ進む。誤検出の危険が無いと判断した項目も、その判断を1行添える。

### 5. `prh.yml` に追記する

- 既存のコメント見出し（`# ---- 漢字で書く語 ---`）に沿ってグルーピングする。当てはまる見出しが無ければ、同じ体裁で新しい見出しコメントを作る（`# ---- かなで書く語 ---` など）。
- **各項目に必ず `specs` を書く。** 最低1件は「置き換わってほしい例」、誤検出の危険がある語には「置き換わってほしくない例」（`from` と `to` を同じにする）を必ず足す。
- **`specs` の例文は、手順3で見つけた実際の記事の一節から取る**（無ければ記事の文体に合う例文を作る）。インラインコードや `$$` を含む例文は既存項目に倣って YAML のクォートで囲む。
- パターンを絞った項目には、**なぜ絞ったかを1〜2行のコメントで残す**（既存の「ぶん」の項目が手本）。

```yaml
  # 「この時」は「この時代」「この時期」「この時点」と続くと別語になるため、
  # 後ろにその続き字が来ない場合だけ置き換える。
  - expected: このとき
    pattern: /この時(?![代期点間刻])/
    specs:
      - from: この時、光は波長ごとに
        to: このとき、光は波長ごとに
      - from: この時代のヨーロッパでは
        to: この時代のヨーロッパでは
```

### 6. 自己テストと検出件数を確認する

```bash
cd app
npm run lint:svx:notation
```

- `spec failed` で落ちた場合は**パターンか例文が間違っている**。`specs` を削って通すのは無し。
- 起動できたら、追加分の指摘が**何件・どの記事に出たか**を集計する（`npm run lint:svx:notation 2>&1 | tail -3` に合計が出る）。手順3の見積もりと大きく食い違うときは、パターンが行きすぎていないかを見直す。
- 手順2で確認した干渉（別ルールとの往復）が実際に起きていないかも、この出力で確かめる。

### 7. 既存記事の修正方針を確認する

**本文を書き換えるので、ここは必ずユーザーの判断を仰ぐ。**

- 手順6の結果（項目ごとの件数・対象記事数・誤検出に見える箇所）を提示し、**一括で自動修正するか、辞書の追加だけに留めるか**を確認する。
- 承認されたら実行する。

  ```bash
  cd app
  npm run lint:svx:notation -- --fix
  ```

- **修正後は必ず `git diff` を確認する。** 特に、ディレクティブの属性・Svelteコンポーネントの props・リンクのURL・見出し・`:Anki[]` の中で不自然な置換が起きていないか（表記揺れのパスは記法ルールと違ってこれらをマスクしない）。誤った置換が1件でもあれば、その箇所を戻したうえでパターンを絞り直し、手順5へ戻る。
- 「辞書の追加だけ」を選んだ場合は、**既存記事で `npm run lint:svx` が赤いまま残る**ことを報告に明記する。
- 表記揺れ以外の直し（言い回しの調整など）はついでに行わない。

### 8. 辞書を列挙しているドキュメントを追随させる

- **`app/textlint/README.md`「検査するルール（表記揺れ）」の表**に行を足す（直す前・直した後・補足）。パターンを絞った項目は、表の下の箇条書きにも条件を1行足す（既存の「ぶん」の説明が手本）。
- 辞書の項目を文中に列挙している次の2箇所も更新する。

  - `.claude/skills/author-style-writer/SKILL.md`（「記法・表記チェック」節）
  - `author-style-skills.md`（「機械的に検査できるルール」節）

  追記後の総項目数が**5件以下なら列挙に足す**。**6件以上になるなら列挙をやめ**、「主な項目は〜など（全項目は `app/textlint/README.md` の表）」の形に畳む。列挙の周りの記述（辞書を書き換えて指摘を消さない、という writer 側の約束など）は変えない。
- `writing-guides/syntax-guide.md` は表記揺れの辞書を持たないので触らない。

### 9. 報告する

- 追加した項目の表（直す前・直した後・パターン・誤検出対策）
- 自己テストの結果と、既存記事の検出件数・対応（一括修正した／辞書追加のみ）
- 更新したファイル一覧
- **コミットはしない。** 変更内容を報告して指示を待つ（コミットは `/commit-this`）。

## 注意事項

- **辞書に載せる表記を決めるのは著者。** 指定された向きを反転しない。指定されていない語を「ついでに」辞書へ足さない。
- **記事本文を書き換えるのは手順7で承認を得たときだけ。** 辞書の追加と本文の修正は別の判断。
- **`specs` を削って自己テストを通さない。** 落ちるのはパターンか例文が間違っているサイン。
- **辞書の対象は `.svx` の記事本文だけ。** `docs/`・`writing-guides/`・`spec/` の Markdown は検査対象外で、辞書の対象範囲を広げるのはこのスキルの仕事ではない。
- 追加した項目は `author-style-writer` が従うルールになる（writer は指摘どおりに直し、辞書を書き換えて指摘を消さない）。**辞書を増やすほど writer と既存記事への影響が広がる**ので、絞り込みを雑にしない。
- `.svx` と `.yml` / `.md` の変更だけなので `npm run check` は実行しない（CLAUDE.md「品質チェック」）。
