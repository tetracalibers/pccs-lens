# Output Contract

著者のスタイル分析で作成または更新する成果物について、共通の出力形式、品質基準、根拠の扱い、ファイル間の責務を定義する。

このドキュメントは、次の分析および統合処理で共通して適用する。

- `thinking-flow.md`
- `writing-style.md`
- `stylistic-quirks.md`
- `refine-style.md`

あわせて、各ガイドの根拠を記録する**根拠インデックス** `writing-guides/evidence/<観点>.md`（4ファイル）を定義する。

成果物は次の2層に分かれる。この分離が契約の中心である。

- **執筆側**（ガイド本体4ファイル）：`author-style-writer` が読む。実行可能なルールと適用条件、確度ラベルだけを置く。**量はルール数に比例させ、記事数に比例させない。**
- **分析側**（根拠インデックス4ファイル・保留プール `pending/`）：analyzer だけが読む。根拠・確度の判定理由・記事単位の記録を置く。量が記事数に比例してよいのはこちら。

各分析固有の出力構成は、それぞれの分析プロンプトに従う。ただし、記述形式、確度、根拠、更新方法については、この契約を優先する。

> 分析・反証段階で用いる判断基準（確度の定義／事実と推測の区別／記事タイプと適用条件／反例と例外の扱い／一般化の基準）は、
> 対象読者が異なるため [`output-contract-analysis.md`](./output-contract-analysis.md) に分離した。
> この文書は主に統合（Markdown 生成）時の記述形式・共通ルール・ファイル別必須要素を定義する。

## 目的

この契約の目的は、分析担当や実行時期が異なっても、次の状態を保つことである。

- 同じ意味のルールが異なる形式で乱立しない
- 根拠の強さと主張の強さが対応する
- 思考、構成、表現、修正傾向が混同されない
- 記事固有の特徴が著者全体の特徴として一般化されない
- 新しい記事を追加した際に、既存ガイドを差分更新できる
- 文章生成時に実行可能なルールとして利用できる
- 分析上の仮説と、本文から直接確認できる事実を区別できる

最終成果物は分析レポートではなく、文章生成および推敲時に参照できる実用的なガイドとする。

## 対象となる成果物

### `thinking-flow.md`

著者が文章を書く際に行っていると考えられる判断を扱う。

主な対象：

- 執筆時の問題認識
- 説明方法を選択する判断
- 読者の理解状態に関する想定
- 抽象と具体を切り替える条件
- 説明を補足、省略、展開する条件
- 次の話題へ進む判断
- 推敲時の判断

記事の見出し順や段落構成そのものは、主な対象にしない。

### `writing-style.md`

文章の構成として観察できる傾向を扱う。

主な対象：

- 記事全体の情報配置
- 導入から本題への移行
- セクションの分割と接続
- 段落の構造
- 一文の情報量
- 定義、理由、例、注意点の配置
- 記事タイプによる構成の変化

内面的な意図や頻出表現は、主な対象にしない。

### `stylistic-quirks.md`

文やフレーズのレベルで観察できる表現上の癖を扱う。

主な対象：

- 頻出する言い回し
- 文末表現
- 接続表現
- 語彙の選択
- 断定や推測の調整
- 記号や表記
- 読者との距離感
- あまり使用しない表現

文章全体の構成やGit差分は、主な対象にしない。

### `refine-style.md`

AI草稿と人間による編集との差分から確認できる修正傾向を扱う。

主な対象：

- 情報の追加と削除
- 説明順の変更
- 表現の書き換え
- 段落や見出しの変更
- AIらしい定型表現の除去
- 説明の粒度調整
- 技術的修正と文体修正の分類

完成記事だけから推測した特徴は、このファイルの根拠にしない。

### `evidence/<観点>.md`（根拠インデックス）

上記4ガイドに対応する根拠インデックス（`evidence/thinking-flow.md` など4ファイル）。各ルールを支持する記事を、記事 slug をキーとして記録する。

- **analyzer 専用。`author-style-writer` は読まない。** 保留プール `pending/` と同じ扱いとする。
- ガイド本体のルール欄に根拠を書かず、ここへ登録する（→「根拠の記載方法」）。
- 保留プールとは役割が異なる。`pending/` は「主要ルールに採用していない観察」を置く場所、`evidence/` は「採用済みルールの根拠」を置く場所である。

## ファイル間の責務

一つの現象が複数の階層に現れる場合は、各ファイルの抽象度に合わせて分解する。

例：

```text
thinking-flow.md:
読者が誤解する可能性を認識した場合、誤解が固定される前に補足する。

writing-style.md:
誤解が起きやすい説明の直後に、短い補足段落を配置する傾向がある。

stylistic-quirks.md:
補足の開始に「ここで注意したいのは〜です」を使用する場合がある。

refine-style.md:
AI草稿で離れた位置に置かれた注意事項を、関連する説明の直後へ移す傾向がある。
```

これは、同じ文を複数ファイルへ複製することを意味しない。

各ファイルでは、その責務に対応する情報だけを記述する。

配置に迷う場合は、次の問いで判断する。

- 「なぜそう書くか」という判断か
  - `thinking-flow.md`
- 「文章上、どこに何が置かれるか」という構造か
  - `writing-style.md`
- 「どのような言葉で書かれるか」という表現か
  - `stylistic-quirks.md`
- 「AI草稿をどう変更するか」という修正か
  - `refine-style.md`

## 共通の記述原則

### 観察結果ではなく、利用可能なルールにする

悪い例：

```text
具体例が多い。
```

良い例：

```text
抽象的な説明だけでは動作や用途を想像しにくい場合、概念説明の直後に具体例を置く傾向がある。
```

悪い例：

```text
文章がわかりやすい。
```

良い例：

```text
新しい専門用語を導入する前に、その用語が必要になる状況または既知の概念との関係を説明する。
```

### 条件を含める

ルールは、可能な限り次の形で記述する。

```text
〜の場合は、〜する。
ただし、〜の場合には適用しない。
```

常に適用する規則として表現するのは、十分な根拠がある場合に限る。

### 著者固有性を意識する

一般的な文章術として広く知られている原則を、そのまま著者固有の特徴として記載しない。

一般論と一致する場合でも、著者の文章でどのように現れているかを具体化する。

悪い例：

```text
読者にわかりやすく説明する。
```

良い例：

```text
定義から始めるよりも用途を先に示した方が理解しやすい概念では、必要性を示してから用語を導入する傾向がある。
```

### 主張の強さを根拠に合わせる

少数の記事でしか確認できない特徴に対して、「常に」「必ず」「一貫して」と書かない。

使用する表現の目安：

- 強い根拠がある
  - 「一貫して〜する」
  - 「多くの記事で〜する」
- 条件付きで確認できる
  - 「〜の場合に用いる傾向がある」
  - 「主に〜の記事で確認できる」
- 根拠が少ない
  - 「〜する場合がある」
  - 「現時点では弱い傾向として確認できる」

## ルールの基本形式

分析結果をルールとして記載する場合は、可能な限り次の形式を使用する。

```markdown
### ルール名

- 確度：
- 対象：
- ルール：
- 適用する状況：
- 適用しない状況：
- 使用量：
- 変種：
- 注意：
- 関連ルール：
```

`確度` は先頭に置き、**ラベル3語（`強い傾向` / `条件付きの傾向` / `弱い傾向`）だけ**を書く。判定理由・確認した記事数・記事タイプの幅は書かない（→「確度はラベルだけを書く」）。

`根拠` 欄は置かない。根拠は `evidence/<観点>.md` へ登録する（→「根拠の記載方法」）。

`反例・例外` 欄も置かない。反例のうち一般化できるものは `適用しない状況` へ吸収し、記事固有の反例は `evidence/<観点>.md` の `※` 注記へ回す。

`使用量`（頻度・分量の上限）、`変種`（記事タイプ・条件による現れ方の違い）、`注意`（運用上の注意）は、ルールを実行するために必要な操作的制約を書く受け皿として使う。「1段落に2回以上重ねない」「1記事1〜2回」のような制約は、根拠の散文ではなくこれらの欄に書く。

ファイル固有の項目が必要な場合は追加してよい。

### `thinking-flow.md`で追加できる項目

```markdown
- 認識する問題：
- 選択する説明戦略：
- 読者に起こそうとする理解の変化：
- 次の判断へ進む条件：
```

### `writing-style.md`で追加できる項目

```markdown
- 配置位置：
- 前後の要素：
- 記事タイプ：
- 構成上の効果：
```

### `stylistic-quirks.md`で追加できる項目

```markdown
- 表現：
- 使用目的：
- 使用されやすい文脈：
- 近いが著者らしくない表現：
- 過剰使用への注意：
```

### `refine-style.md`で追加できる項目

```markdown
- 修正前の特徴：
- 修正後の傾向：
- 修正操作：
- 修正の目的：
- 差分の種類：
```

すべての項目を機械的に埋める必要はない。意味のある情報がない項目は省略する。とくに `使用目的` / `使用されやすい文脈` / `構成上の効果` / `前後の要素` は、`ルール` 欄・適用条件欄の言い換えになるなら書かない（同じ内容を2度書くと、執筆側の量がルール数以上に膨らむ）。

ただし、少なくとも次は含める。

- 確度（ラベルのみ）
- ルール
- 適用条件
- 適用しない条件

ルール欄・適用条件欄には、**そのルールを実行するために必要な制約をすべて書く**。ガイド本体だけを読んで判断できる状態にする。適用範囲の線引き・頻度の上限・記事タイプによる出入りを、確度や根拠の説明の中に埋めない（分析側のファイルへ移した時点で執筆側から失われる）。

### 確度はラベルだけを書く

ガイド本体の `確度` 欄には、`強い傾向` / `条件付きの傾向` / `弱い傾向` のいずれか1語だけを書く。

執筆側が必要とするのは「このルールをどのくらい強く当てるか」だけである。一方「なぜその確度なのか」は、次の分析ラウンドで確度を上げ下げするときにしか使わない。したがって次はガイド本体に書かない。

- 確認できた記事数・記事タイプの幅・シリーズ名・時期
- 「一般的な文章術とも重なる」「媒体慣習の交絡が残る」「著者固有性は〜に限る」のような判定理由
- 「〜は未検証」「〜は推測にとどまる」のような検証状態の記述

これらは `evidence/<観点>.md` の前置き（観点固有の確度判定基準）または各記事の `※` 注記へ書く。

`確度` を判断する基準そのものは `output-contract-analysis.md`「確度の定義」に従う。

## 根拠の記載方法

### 根拠はガイド本体へ書かない

根拠は、ガイド本体のルール欄に書かず、観点ごとの根拠インデックス `writing-guides/evidence/<観点>.md` へ、**記事 slug をキーとして**登録する。

ルール側に散文で根拠を積むと、次の2つの問題が起きる。

- 分析ラウンドごとに追記される台帳になり、執筆側の量が記事数に比例して増える（コンテキストを圧迫する）
- 記事を改稿したとき、その記事由来の根拠だけを撤回できない（根拠がルール単位で組まれているため、「シリーズ10本すべてが〜」のような集約表現は1本分だけ減らせない）

根拠を記事単位に正規化することで、執筆側の量をルール数に比例させ、記事単位の再分析を可能にする（→「既存ファイルの更新規則」の「記事単位の再分析」）。

### 根拠インデックスの形式

```markdown
## /color-theory/color-vision-types
分析時点: `1d2e87dd`

- ヘッジ文末：主観・一般則を和らげる（「異なる傾向があります」）
- 双方向の括弧グロス（「透明度（$$\alpha$$値）」）
  ※ 節頭の反語的な問いかけは反例（この記事には見当たらない）
```

- `##` は記事 slug（記事名ではない）をキーとする。**この階層は slug の予約とし、注記に使わない**（機械的に記事ブロックを取り出せる状態を保つ）。
- 見出しの直下に `分析時点` 行を置く（→「`分析時点` の記録」）。
- 値は、その記事から採れた**支持ルール名のリスト**。ルール名はガイド本体の `###` 見出しと一致させる（表記が揺れると追跡できなくなる）。括弧内に本文中の該当箇所を短く添える。`refine-style.md` では該当箇所の代わりに修正前後のコミット対（`16758df→78ba48c：変更の要約`）を書く。
- 反例・除外は `※` で注記する。「反例」はそのルールが働かなかった箇所、「除外」は記事タイプ由来・テーマ由来などで根拠に数えない箇所。
- 各ファイルの先頭には、位置づけの注記（analyzer 専用／writer は読まない）と、**その観点固有の確度判定基準**を置く。ガイド本体から除いた判定理由の一般的な部分はここへ集約する。

### `分析時点` の記録

各記事ブロックの見出し直下に、**分析した時点の記事コミット**の短縮SHAを記録する。

```markdown
分析時点: `1d2e87dd`
```

- 値は `git log -1 --format=%h -- app/src/routes/<slug>/+page.svx` で取得する（分析に使った本文のコミット）。
- 4ファイルとも同じ記事について同じ SHA を持つ（記事1本の分析は4観点を同時に更新するため）。値が食い違っていたら、どこかの観点で更新漏れが起きている。
- **記録した SHA が現在の最終更新コミットと違えば、その記事は分析後に改稿されている＝再分析の候補。** これがインデックスに SHA を持たせる理由である。
- ただし SHA の差分は再分析が必要であることの十分条件ではない。frontmatter のタグ改名のような一括修正でも SHA は変わる。`git diff <記録した SHA>..HEAD -- app/src/routes/<slug>/+page.svx` で本文の差分を確認してから判断する。
- 記事のパスが変わった場合は、キー（slug）を現在のパスに合わせて書き換え、`分析時点` はそのまま残す（分析した本文の実体は変わらないため）。

### 確度は導出値である

ルールを支持する記事数・記事タイプの幅は、インデックスを数えて算出する。**ガイド本体には書かない**（書くと再び追記対象になる）。

単純な出現回数だけで確度を決めない。次も考慮する。

- 記事数
- 記事タイプの幅
- 執筆時期の幅
- 同一シリーズへの偏り（インデックスの slug の分布で判定する）
- 同じ編集者や媒体による影響
- 反例の数
- 一つの特徴が文章全体へ及ぼす影響

### 根拠の引用

記事本文を長く転載しない。インデックスに添える該当箇所は、特徴を確認できる最小限の長さにする。

全文や長い段落の複製ではなく、必要に応じて要約を使用する。差分の生ログはインデックスに含めない。

## 用例の扱い

用例は、ルールを理解するための補助として使用する。

用例だけを並べてルールの説明を省略しない。

### 良い用例

- 短い
- ルールとの対応が明確
- 文脈が必要な場合は要約が付いている
- 特定テーマの専門用語に依存しすぎていない
- 著者の文章を大量に複製していない

### 避ける用例

- 記事の段落全体
- ルールと関係のない長い引用
- 一度しか使われていない特殊な表現
- 記事テーマ固有の専門用語
- 出典のない創作例を実例として扱うこと

創作した例を用いる場合は、「再現例」などと明示し、実際の記事からの用例と区別する。

## 重複と参照関係

同じ意味のルールを複数箇所へ記載しない。

既存ルールの一部として説明できる場合は、独立したルールを追加せず、次のいずれかで処理する。

- 既存ルールの条件を追加する
- 既存ルールの具体例として追加する
- 関連ルールとして参照する
- 上位ルールへ統合する
- 下位の表現例として配置する

関連する別ファイルのルールを参照する場合は、内容を全文コピーせず、**裸の参照だけ**を書く。参照の理由や関係の説明を添えない。

```markdown
- 関連ルール：→ thinking-flow.md「読者の誤解を先回りする判断」、→ 本ファイル「〜」
```

見出し名は、参照先で安定して使用できる名前にする。ルール名を変更するときは、参照している側と `evidence/<観点>.md` も同時に直す。

保留項目（`pending/<観点>.md`）への参照は、ガイド本体に書かない。`author-style-writer` はたどれないため、執筆側にとってノイズになる。保留項目との関係は保留プール側に書く。

## 既存ファイルの更新規則

既存ガイドがある場合は、まず現在の内容（ガイド本体・根拠インデックス・保留プール）を読み、有効な記述を保持したうえで更新する。全面的な書き直しや既存内容の破棄はしない。新しい分析結果は、既存記述への加筆・修正・調整として、次のいずれかへ分類する。

- 補強
- 条件追加
- 例外追加
- 確度上昇
- 確度低下
- 新規ルール
- 既存ルールへの統合
- 別ファイルへの移動
- 廃止候補
- 保留

更新時は、次の形式で変更内容を記録する。

```markdown
### 更新対象

- 対象ファイル：
- 対象ルール：
- 更新区分：
- 更新前：
- 更新後：
- 更新理由：
- 新しい根拠：
- 反例：
```

この更新記録を最終ガイドへ常に残す必要はない。

分析ログまたは作業記録として保持し、最終ガイドには更新後のルールを反映する。

### 根拠インデックスの更新

ガイド本体を更新するときは、同じラウンドで `evidence/<観点>.md` も更新する。

- **新しく分析した記事**：`## /<slug>` ブロックを追加し、`分析時点` に分析した本文のコミット SHA を書く。支持ルール名を列挙する。
- **既存ルールを補強した場合**：該当記事のブロックへそのルール名を足す（ルール側に「根拠が増えた」旨を書かない）。
- **ルールを廃止した場合**：全記事ブロックからそのルール名を外す。インデックスに残ったルール名がガイド本体に存在しない状態を作らない。
- **ルール名を変更した場合**：インデックス側の記述も同時に変える（ルール名がキーであるため、揺れると追跡できなくなる）。
- **記事が削除された場合**：当該ブロックを削除する。確度は導出値なので自動的に追随する。

### 記事単位の再分析（撤回）

すでに分析済みの記事が改稿された場合は、その記事だけを再分析できる。再分析は「足す」だけでなく**「撤回する」**操作を含むため、次の手順で行う。

1. **対象を検出する。** `evidence/<観点>.md` の `分析時点` と、`git log -1 --format=%h -- app/src/routes/<slug>/+page.svx` の現在値を比べる。異なる記事が候補。`git diff <記録した SHA>..HEAD -- <path>` で本文が実際に変わっているかを確認する（メタデータのみの変更なら再分析は不要）。
2. **記事ブロックを丸ごと消して書き直す。** 4ファイルとも、当該記事の `## /<slug>` ブロックだけを削除し、新しい分析結果で書き直す。**他の記事のエントリには触らない。** `分析時点` は新しい SHA へ更新する。
3. **撤回の影響を確度へ反映する。** 書き直しによってあるルールの支持記事が減った場合は、残った記事数・記事タイプの幅を数え直して確度ラベルを再評価する。支持記事が0になったルールは、廃止候補として「廃止と保留の扱い」に従って判断する（無条件に削除しない。改稿前の本文で確認していた特徴が、他の記事では成立している可能性がある）。
4. **ルール側の適用条件を見直す。** 改稿によって反例になった箇所は、`適用しない状況` を狭める／広げる根拠になる。

ブロック単位で消して書き直すため、古い根拠の撤回は原子的に行える。ルール側の散文を横断して1記事分だけ外科手術的に取り除く必要はない。

### 新しい記事が少数の場合

新しく追加された記事が一つまたは少数の場合は、既存の強いルールを即座に変更しない。

次の順序で検討する。

1. 既存ルールの例外か
2. 記事タイプによる違いか
3. 読者や目的による違いか
4. 執筆時期による変化か
5. 既存ルールの確度を下げる必要があるか
6. 新しいルール候補として保留すべきか

## 廃止と保留の扱い

### 廃止する場合

既存ルールを削除または廃止するのは、次のいずれかの場合とする。

- 根拠の誤読が判明した
- AI草稿由来の特徴だった
- 一般的な文章術以上の特徴ではなかった
- 反例が多く、条件による説明もできない
- 新しい分析により、別の上位ルールへ統合された
- 現在の著者の文章には当てはまらなくなった

削除前に、削除理由を記録する。削除したルール名は、`evidence/<観点>.md` の全記事ブロックからも外す。

### 保留する場合

次の特徴は保留する。

- 根拠記事が少ない
- 別の解釈が有力である
- 記事タイプの偏りが大きい
- 反例の理由を説明できない
- 著者固有か判断できない
- 担当Agent間で結論が出ていない

保留した特徴は、本体ガイドではなく対応する保留プール `writing-guides/pending/<観点>.md` に置く。ここへ置いた特徴を、生成時の主要ルールとして使用しない（`author-style-writer` は保留プールを読まない）。各保留プールの先頭には「このファイルの位置づけ」注記を残す。

保留プールと根拠インデックスを混同しない。`pending/` は主要ルールに**採用していない**観察を置く場所、`evidence/` は**採用済み**ルールの根拠を置く場所である。保留の根拠は保留プールの項目内に書き、`evidence/` へは登録しない（インデックスのルール名は、ガイド本体に存在するルールだけを指す）。

### 保留を昇格する場合

保留プールの既存項目は、次の場合に本体ガイドの主要ルールへ**昇格**する。

- 新たな分析で根拠記事が増え、複数記事・複数タイプで一貫することを確認できた
- 反証（Evidence 反証）を通り、一般的な文章術・テーマ由来との切り分けができた

昇格するときは、本体ガイドへルールを加え、保留プールから当該項目を削除する（本体と保留プールで同じ特徴を重複させない）。昇格の判断がつかない項目は保留プールに残す。

## Markdownの記述規則

### 見出し

- ファイル内では見出し階層を一貫させる
- `#`はファイルタイトルに一度だけ使用する
- 主要分類に`##`を使用する
- 個別ルールに`###`を使用する
- ルールの中で過度に深い見出しを使わない

### 箇条書き

箇条書きは、条件、根拠、例外などの構造化に使用する。

説明そのものを短い箇条書きの羅列だけで済ませない。

必要な箇所では文章で理由や関係を説明する。

### 表

表は、複数項目を同じ軸で比較するときに限って使用する。

長文を表のセルへ詰め込まない。

条件や例外を詳しく説明する必要がある場合は、見出しと箇条書きを使用する。

### コードブロック

コードブロックは、次の用途に限定する。

- 思考フロー
- 擬似コード
- 出力形式の例
- 修正前後の短い比較
- 再利用可能なテンプレート

通常の説明文をコードブロックへ入れない。

### 用語

次の用語は意味を統一する。

- ルール
  - 文章生成や推敲時に利用できる条件付きの指針
- 特徴
  - 記事から観察された現象
- 根拠
  - 特徴またはルールを支える本文やGit差分。`evidence/<観点>.md` に記事単位で記録する
- 根拠インデックス
  - `evidence/<観点>.md`。記事 slug をキーに、その記事が支持するルール名と分析時点のコミットを記録した索引
- 分析時点
  - 根拠インデックスの各記事ブロックに記録する、分析に使った本文のコミット（短縮SHA）
- 反例
  - ルールに該当しない、または反対の現象が確認できる事例
- 例外
  - 条件によって説明可能な非適用事例
- 確度
  - 分析結果を著者固有の傾向として扱える強さ
- 推測
  - 本文に明示されていない意図や判断についての仮説

## ファイルごとの必須要素

各ファイルの「ガイドの目的」節は、そのファイルが扱う対象（判断／構成／表現／修正傾向）と役割、他ファイルとの守備範囲の違いの説明に限る。分析対象とした記事・シリーズの名称、本数、分析を重ねた経緯（「さらに〜シリーズを追加で分析し統合した」といった記述）は、成果物であるガイド本体には書かない。これらは分析ログ・作業記録側に保持し、差分更新でもこの節へ更新履歴を積み増さない。各特徴の裏づけは `evidence/<観点>.md` で扱う。

これは「ガイドの目的」節に限らない。**分析対象の記録は、節の前書き・ルール欄・確度欄を含め、ガイド本体のどこにも書かない。**「根拠はCG基礎2記事に偏る」「色の理論9本すべてで確認」のような記述は、ルールの一部ではなく分析メタである。節の前書きには、その節を運用するうえでの注意だけを残す。

### `thinking-flow.md`

最低限、次を含める。

- ガイドの目的
- 執筆前の判断
- 説明を進める基本的な思考の流れ
- 読者の疑問を扱う判断
- 抽象と具体を切り替える判断
- 説明を深める、または省略する判断
- 話題を展開する判断
- 推敲時の判断
- 再現可能な条件付きルール
- 適用上の注意
- 一般化できない判断

思考フローは、見出し順の言い換えではなく、問題認識と判断の連鎖として記述する。

### `writing-style.md`

最低限、次を含める。

- ガイドの目的
- 全体構成
- 導入
- セクション構成
- 段落構成
- 文の構成
- 定義と例の配置
- 補足や注意事項
- 記事タイプによる変化
- 生成時のガイドライン
- 避ける構成

### `stylistic-quirks.md`

最低限、次を含める。

- ガイドの目的
- 全体的な語り口
- 導入表現
- 説明を展開する表現
- 話題をつなぐ表現
- 例示表現
- 対比、否定、限定の表現
- 推測と断定の調整
- 文末表現
- 表記上の癖
- あまり使わない表現
- 再現時の注意

頻出表現の一覧だけで終えず、使用文脈と目的を記述する。

### `refine-style.md`

最低限、次を含める。

- ガイドの目的
- 修正時の基本方針
- 追加する傾向
- 削除する傾向
- 並べ替える傾向
- 書き換える傾向
- 構成を変更する傾向
- 技術説明を修正する傾向
- AIらしい文章を除去する基準
- 条件付きの修正
- 修正手順
- 一般化しない修正

修正傾向は、Git差分によって確認できるものを根拠とする。

## 最終検証

成果物を保存する前に、次を確認する。

### 責務

- 各ルールが適切なファイルに配置されているか
- 思考、構成、表現、修正傾向が混在していないか
- 同じ内容が複数ファイルへそのまま複製されていないか

### 根拠（`evidence/<観点>.md` 側を検証する）

- 各主要ルールが、インデックスの少なくとも1記事から支持されているか
- インデックスに現れるルール名が、ガイド本体の `###` 見出しと一致しているか（表記が揺れて追跡できなくなっていないか）
- 根拠が主張を実際に支えているか
- 一つの記事だけを根拠に強い傾向としていないか
- Git差分を使う場合、修正前後のコミット対が明確か
- 今回分析した記事のブロックが4ファイルに存在し、`分析時点` が4ファイルで一致しているか
- 再分析した記事について、当該ブロックが書き直され、他の記事のエントリが変わっていないか

### 確度

- インデックスから数えた記事数・記事タイプの幅と、確度ラベルが対応しているか
- `確度` 欄がラベル3語のみで、判定理由・記事数・シリーズ名が混入していないか
- 条件付きの傾向から条件が抜け落ちていないか
- 弱い傾向が主要ルールとして書かれていないか

### 執筆側と分析側の分離

- ガイド本体に `根拠` 欄・`反例・例外` 欄が残っていないか
- ガイド本体に記事名・シリーズ名・出現件数・分析経緯が書かれていないか（節の前書きも含む）
- ルールの実行に必要な制約が、確度・根拠の説明としてではなく `ルール` / `適用する状況` / `適用しない状況` / `使用量` / `変種` / `注意` に書かれているか
- ガイド本体の量が、記事数ではなくルール数に比例する状態を保てているか

### 一般化

- 一般的な文章術を著者固有として扱っていないか
- 記事テーマ固有の特徴を一般化していないか
- 媒体や編集者の影響を無視していないか
- AI草稿由来の表現を著者の癖として扱っていないか

### 実用性

- 文章生成時に何をすればよいか判断できるか
- 適用条件と非適用条件がわかるか
- 固定テンプレートではなく判断ルールになっているか
- 頻出表現を機械的に挿入する指示になっていないか
- スタイルの物真似ではなく、自然な文章を作るためのガイドになっているか

### 更新可能性

- 新しい記事を追加した際に、既存ルールを更新できる形か
- 根拠と反例を `evidence/<観点>.md` から追跡できるか
- 改稿された記事を、その記事のブロックを書き直すだけで再分析できる形か
- ルールの統合、条件追加、廃止が可能な構造か

## 禁止事項

以下を行わない。

- ガイド本体のルール欄へ根拠（記事名・シリーズ名・出現件数・本文の引用・コミット）を書く。根拠は `evidence/<観点>.md` へ登録する
- ガイド本体の `確度` 欄へ、ラベル3語以外（判定理由・記事数・記事タイプの幅・検証状態）を書く
- ガイド本体へ `根拠` 欄・`反例・例外` 欄を復活させる
- 「ガイドの目的」節や節の前書きへ、分析対象（分析した記事・シリーズの名称、本数、分析を重ねた経緯）を列挙・記録する
- 分析結果を記事の要約として出力する
- 観察された特徴を、条件のない命令へ変換する
- 根拠の少ない特徴へ強い確度を付ける
- 一つの記事や一つのシリーズだけから著者全体を一般化する
- 一般的な文章術を著者固有の特徴として記述する
- 記事テーマ固有の専門用語を表現上の癖として扱う
- AI草稿由来の表現を著者本人の特徴として扱う
- 技術的な誤りの訂正を文体修正として扱う
- 推測を事実として記述する
- 反例や例外を削除して、ルールを強く見せる
- 同じルールを複数ファイルへそのまま複製する
- 頻出表現をすべての文章へ使用するよう指示する
- すべての記事を同じ構成へ当てはめる
- 用例を大量に転載する
- 分析ログやAgent間の議論を、そのまま最終成果物へ含める
- 既存ガイドを理由なく全面的に書き直す
- 保留中の仮説を生成時の主要ルールとして使用する
- ルールの実行に必要な制約（適用範囲の線引き、頻度・分量の上限、記事タイプによる出入り）を、ルール欄・適用条件欄に書かず分析側のファイルだけへ残す
- 再分析で、対象記事以外のブロックまで `evidence/<観点>.md` を書き換える
- ガイド本体に存在しないルール名を `evidence/<観点>.md` へ登録する（保留項目の根拠をインデックスへ書く）
