# Author Style Analyzer

過去記事と編集履歴を分析し、著者固有の執筆スタイルを再利用可能なガイドとして整理する。

## 成果物

次のファイルを、リポジトリ直下の `writing-guides/` 配下に作成または更新する。

- `writing-guides/thinking-flow.md`
- `writing-guides/writing-style.md`
- `writing-guides/stylistic-quirks.md`
- `writing-guides/refine-style.md`

`writing-guides/` が存在しない場合は作成する。既存ガイドが別の場所にある場合は、リポジトリ内を検索し、その場所を優先して更新する。

各ルールの見出しには**安定した ID** を付ける（`### [WS-012] ルール名`）。

- 形式は観点略号2文字＋連番3桁。`TF`（thinking-flow）／`WS`（writing-style）／`SQ`（stylistic-quirks）／`RS`（refine-style）。
- ID は根拠から支持記事数を機械集計するためのキーである。**ルール名を改名しても ID は変えず、廃止したら欠番にする**（採番の再利用はしない）。
- 採番は `node scripts/style-rule-ids.mjs --write` が行う。**手で番号を決めない。**
- 本文中の `関連ルール` 参照は名前のまま書く（`→ writing-style.md「◯◯」`）。writer が読むファイルであり、ID だけでは人間が辿れない。

あわせて、各ガイドに対応する根拠 `writing-guides/evidence/<観点>/<slug>.md` を維持する。**記事1本につき1ファイル**で、ファイルパスがそのまま slug に対応する。

- ガイド本体のルール欄に根拠を書かず、こちらへ**ルールIDで**登録する（ルール名は書かない）。ガイド本体に置くのは、実行可能なルールと適用条件、確度ラベル3語だけ。
- 各ファイルの先頭に `分析時点`（分析した本文のコミットの短縮SHA）と `記事タイプ` を記録する。同じ記事なら4観点で同じ SHA になる。
- `- <ID>（該当箇所）` の行だけが支持である。`※` 行は反例・除外の注記で、支持には数えない。
- 根拠は分析専用で、`author-style-writer` は読まない（`pending/` と同じ扱い）。
- 各観点の `_README.md` に凡例と観点固有の確度判定基準を置く。
- 形式・更新規則・記事単位の再分析（撤回）の手順は `references/output-contract.md`「根拠の記載方法」「既存ファイルの更新規則」に従う。

**執筆側の量はルール数に比例させ、記事数に比例させない。** 記事が増えるほど増えていい情報（根拠・確度の判定理由・記事単位の記録）は、すべて `evidence/` と `pending/` 側に置く。

さらに、各ガイドに対応する保留プール `writing-guides/pending/<同名>.md`（`pending/thinking-flow.md` など4ファイル）を維持する。

- ガイド本体には、生成時に適用する主要ルール（強い傾向・条件付きの傾向）だけを置く。
- 根拠不足・単一記事偏り・一般技法との切り分け困難などで主要ルールに満たない観察（保留）は、本体ではなく対応する保留プールへ置く。
- 保留プールは分析専用の補助記録で、`author-style-writer` は読まない。①根拠が増えた保留を本体ルールへ**昇格**、②新たな保留を**追記**、③不要になった保留を**棄却**、の対象とする。
- **保留は1項目1行で書く。**

  ```markdown
  - SQ-P045｜支持2記事のみ・媒体機能への依存が大きい｜支持: /color-theory/color-area-proportion, /color-theory/hue-tone-difference
  ```

  全角縦棒で「保留ID｜保留の理由｜支持記事」の3欄に分ける。**支持記事を機械的に読めることが、昇格判定を機械化できる条件である。** 散文で書くと1項目ずつ読み直すしかなくなり、保留プールが追記専用の倉庫になる。保留IDは `<観点略号>-P<連番3桁>`。
- **昇格の閾値は支持3記事以上。** `node scripts/style-pending-promote.mjs` が候補を出す。件数は必要条件にすぎず、3記事あっても単一シリーズに閉じている・一般技法と切り分けられない候補は昇格させない。昇格の判断そのものは機械化しない。
- 各保留プールの先頭には「このファイルの位置づけ」注記（writer は読まない／analyzer が昇格判断で読む）を必ず残す。無ければ作成する。
- 保留プールと根拠の役割を混同しない。`pending/` は主要ルールに**採用していない**観察、`evidence/` は**採用済み**ルールの根拠を置く場所。保留の根拠は `pending/` の項目内に書き、`evidence/` へは登録しない。

さらに、進捗記録として文体解析タスクリスト `writing-guides/STYLE-ANALYSIS-TASKLIST.md` を維持する。

- どの記事を分析済みかを記事単位のチェックボックスで記録したリスト。ガイドではなく進捗記録なので、`author-style-writer` は読まない。
- スコープの解決（手順1）と、分析後のチェック更新（手順7）で使う。
- 記事単位の行を、スキルへ渡せるスコープ（`#<id>`）ごとの見出しでまとめている。凡例・並び順の規約はファイル冒頭に書いてある。

各ファイルの役割を混同しない。

- `thinking-flow.md`
  - 完成した文章からリバースエンジニアリングした、著者の判断と思考の流れ
- `writing-style.md`
  - 記事全体、セクション、段落、文の構成上の傾向
- `stylistic-quirks.md`
  - 頻出する言い回し、語尾、接続表現、表記などの表現上の癖
- `refine-style.md`
  - AI草稿を人間が修正した際の追加、削除、並べ替え、書き換えの傾向

同じ特徴を複数のファイルへ重複して記載しない。分類に迷う特徴は、各分析結果を比較した後で配置先を決定する。

## スクリプト

前処理・記帳・集計は `scripts/` 配下のスクリプトが担う。**エージェントに数えさせない・書かせないための分担である。**

| スクリプト | 用途 |
| --- | --- |
| `style-rule-ids.mjs --list` | ルールID一覧を作る（判定エージェントへ渡す唯一のガイド情報） |
| `style-rule-ids.mjs --write` | 新しく追加されたルールへ ID を採番する |
| `style-evidence-write.mjs <json> --write` | 判定結果から `evidence/<観点>/<slug>.md` を機械生成する（根拠モードの記帳） |
| `style-evidence-tally.mjs` | 支持記事数を集計し、確度の降格候補・廃止候補・ID不整合を検出する |
| `style-pending-promote.mjs` | 保留プールから昇格候補（支持3記事以上）を抽出する |

`style-evidence-split.mjs` は移行専用（1回きり）で、通常の分析では使わない。

**Workflow スクリプトはファイルシステムへ触れない**（Node の API を持たない）ため、これらはすべてメインセッションが Bash で実行する。

## 2つのモード

分析には目的の異なる2種類がある。「新しく書いた記事が既存ルールを支持するか記録する」ことと「溜まった根拠からガイドを見直す」ことは別の作業なので、手順を分ける。

| | 根拠モード（既定） | 発見モード（`--discover`） |
| --- | --- | --- |
| 目的 | 記事が既存ルールを支持するかを記録する | ガイドそのものを見直す |
| 書き込み権限 | `evidence/` のみ | 本体・`evidence/`・`pending/` の3層 |
| 新しい特徴 | `pending/` へ1行で積む | 昇格・採用を判断する |
| ガイド本体 | 触らない（確度の降格を除く） | 更新する |
| 境界レビュー | 実行しない | 実行する |
| 記事指定なしの実行 | 不可 | 可（棚卸しのみ） |
| エージェント数 | 8体（Git 履歴なしなら6体） | 10〜13体 |

呼び出し形式：

```
/author-style-analyzer #cg-basics              → 根拠モード（既定）
/author-style-analyzer #cg-basics --discover   → 発見モード
/author-style-analyzer --discover              → 棚卸しのみ（記事を読まない）
```

**根拠モードでも発見は起きる。** 変わるのは「見つけた特徴をその場で本体に入れるかどうか」だけで、根拠モードでは `pending/` に積み、採用の判断を発見モードへまとめる。発見の機会を捨てる設計ではない。

引数に `--discover` が無ければ根拠モードとして扱う。ユーザーが「ガイドを見直したい」「保留を棚卸ししたい」と述べた場合は、`--discover` が無くても発見モードでよいかを確認する。

### 移行前のデータ形式を検出したら止まる

分析に入る前に次を確認し、満たされていなければ**移行が未完了である旨を報告して停止する**（不完全な状態で書き込むと、ID の欠番や根拠の取りこぼしが起きる）。

- `node scripts/style-rule-ids.mjs --check` が成功する（全ルールに ID がある）
- `writing-guides/evidence/<観点>/` がディレクトリとして存在する（分割前の `evidence/<観点>.md` が残っていない）

`pending/` の1行化は移行済みで、`node scripts/style-pending-promote.mjs` は旧形式0件を報告する。旧形式の散文項目が再び現れた場合、それは1行形式を守らずに追記したということなので、機械的な昇格候補の抽出から漏れる。追記するときは必ず `保留ID｜特徴：保留の理由｜支持: <slug>, <slug>` の3欄で書く（4欄目を足すと旧形式として数えられる）。

## 基本ワークフロー

### 1. 分析対象を確認する

次を確認する。

- 既存のスタイルガイドの有無（あれば内容を読み、更新は上書きではなく差分で行う）
- 文体解析タスクリスト `writing-guides/STYLE-ANALYSIS-TASKLIST.md` の該当行（分析済みか未分析か、draft かページ未作成か）
- Git履歴を利用できるか
- 記事タイトルとコミットメッセージの対応規則

タスクリストは分析状況の一次情報源として使う。

- 引数で指定されたスコープに、すでに `[x]`（分析済み）の記事が含まれる場合は、**再分析するか、未分析（`[ ]`）の記事だけに絞るかをユーザーへ確認する**。勝手にどちらかへ倒さない。記事が公開後に加筆・推敲されている場合は再分析に意味があるため、機械的に除外もしない。
  - 判断材料として、`writing-guides/evidence/<観点>/<slug>.md` に記録された `分析時点` と、`git log -1 --format=%h -- app/src/routes/<slug>/+page.svx` の現在値を比べる。異なる記事は分析後に改稿されている候補なので、`git diff <記録した SHA>..HEAD -- <path>` で本文が実際に変わっているかを確かめ、結果を添えて確認する（メタデータのみの変更なら再分析の必要はない）。
- 「まだ分析していない記事」「未分析の◯◯カテゴリ」のような自然言語でスコープを指定された場合は、タスクリストの `[ ]` 行から対象を解決し、**解決したルート一覧（件数つき）を提示して承認を得てから分析に進む**。
- タスクリストに載っていない記事が対象に含まれる場合（新規カテゴリの追加直後など）は、その旨を報告し、手順7で行を追加してよいかを確認する。

#### 参照する過去記事の指定

分析対象とする過去記事は、引数で指定する（引数は任意）。引数は**カンマ区切りのリスト**で、各要素は「`#id`（先頭が `#`）」または「slug」のいずれか。`#id` と slug は**混在させて複数指定できる**。引数を渡さないこともできる。

- **要素が `#id`（先頭が `#`）の場合**：`app/src/lib/content-pages` 配下の YAML から該当 id を探し、その id に含まれる実装済み記事を対象にする。
  - id は YAML 上のカテゴリ／セクションの識別子。色記事はカテゴリ単位（`color-theory.yaml` / `color-fields.yaml` の top-level の `id`）、CG記事はセクション単位（`cg/*.yaml` の `sections[].id`）。
  - 該当 id の配下から、`slug:` を持つリンク（`PageLink`＝実装済みページ）をすべて集める。`title:` だけのリンク（`DraftLink`＝未実装でページが無い）は対象外。
  - 集めた slug を `app/src/routes/{cg,color-theory,color-fields}/**/<slug>/+page.svx` へ解決したものが分析対象。
  - id が見つからない、または複数の YAML で重複して見つかる場合は、その旨を報告して確認する（見つからない要素があっても、残りの要素で続行する）。
- **要素が slug の場合**：指定された slug に対応する記事を対象にする。
  - slug は記事のディレクトリ名。`app/src/routes/{cg,color-theory,color-fields}/**/<slug>/+page.svx` を再帰的に探して特定する（CG記事は `cg/<分野>/<slug>/` のように階層が深いことがある）。
  - 見つからない slug は報告し、残りの要素で続行する。
- **複数要素・`#id` と slug の混在**：各要素をそれぞれ上記の規則で解決し、得られた記事を**すべて統合**して分析対象にする。異なる要素から同じ記事が得られた場合は1本にまとめる（重複排除）。
- **引数が渡されていない場合**：**全記事の一括分析は既定で行わない**。解説記事（`layout: guide-content`）は多数（数十〜100本超）あり、一度に分析するとフリーズの原因になる。引数なしで呼ばれた場合は、分析に進む前に**まず `#id` や slug（カンマ区切りで複数・混在可）で範囲を指定するよう求める**（`AskUserQuestion` などで案内する）。このとき、タスクリストで `[ ]` の記事が残っているスコープを候補として提示する。
  - どうしても全記事を対象にしたい場合に限り、ユーザーが明示的に同意したうえで、**カテゴリ／セクション（`#id`）単位のチャンクに分割して順に実行**する（一度に全記事を読ませない）。分割実行では、各チャンクの結果を既存ガイドへ差分更新として積み上げる。
  - 対象の目安は `layout: guide-content` の `.svx`。`app/src/routes/concept/+page.svx`（`layout: concept`）など記事以外のページは除外する。

いずれの場合も、フロントマターが `draft: true` の記事は分析対象から除外する（`draft` フィールドが無い記事は非draft＝公開済みとして扱う）。記事本文以外のファイル（デモコンポーネント、レイアウト、YAML など）は分析対象に含めない。

### 2. 記事を分類する

記事を可能な限り次の種類に分ける。

- 概念解説
- 実装解説
- チュートリアル
- 比較記事
- 導入記事
- エッセイまたは体験記事
- その他

記事タイプによる違いを無視して、すべての特徴を一律に一般化しない。

### 3. 各観点を独立して分析する

各分析は、先に他の分析結果へ引っ張られないよう独立して行う。次の4観点を、それぞれ独立したエージェントが担当する。

- Thinking Flow Analyst
- Writing Structure Analyst
- Stylistic Quirks Analyst
- Revision Diff Analyst

**実行方式は Workflow ツールによる決定論的オーケストレーションを用いる。** teammate（Agent Teams / `SendMessage`）は使わない。teammate 同士のピア通信はアイドル・デッドロックでハングしやすいためである。代わりに、同梱の正典スクリプト `references/analysis-workflow.js` を Workflow で実行する。制御フローが JS のため待機による停止が起きず、各エージェントは構造化出力を返して終了する（idle プロセスが残らない＝`TaskStop` 不要）。

**進行は観点ごとのパイプラインで流す。** 4観点を揃える必要があるのは境界レビューだけなので、これを統合の後段へ移し、`分析→反証→統合` を観点ごとに独立して流す。`gitAnalyzable` が空の回は Revision Diff Analyst の系列を起動しない（「確認できないと明記する」だけの成果物を作らせない）。

#### 根拠モードの手順

1. **前処理（メインセッション）**：スコープを解決し、`node scripts/style-rule-ids.mjs --list` でルールID一覧（251行・約1万字）を作る。各記事の `分析時点` SHA を `git log -1 --format=%h -- <path>` で確定する。
2. **判定（Workflow・観点ごと4体）**：ルールID一覧と記事本文を渡し、「この記事がどのルールIDを支持するか／反例か」を構造化出力で返させる。**ガイド本体・`evidence/`・`pending/` は読ませない。**
3. **反証（Workflow・観点ごと4体）**：過剰な当てはめを弾く。
4. **記帳（スクリプト）**：Workflow の戻り値を `node scripts/style-evidence-write.mjs <json> --write` へ渡し、`evidence/<観点>/<slug>.md` を機械生成する。**統合エージェントは起動しない。**
5. **確度の降格（スクリプト＋メインセッション）**：`node scripts/style-evidence-tally.mjs --round <今回のslug群>` で、支持が2記事以下に落ちたルールを検出し、該当ルールの `確度` 欄のみ「弱い傾向」へ更新する。**該当が無ければ本体は一切変更しない。** `--round` を必ず付ける（付けないと全ルールの棚卸しになり、根拠が未登録なだけのルールまで降格対象に出る）。
6. **新特徴の記録**：戻り値の `newFeatures` を `pending/` へ1行で追記する。
7. **後処理**：タスクリストの更新、報告。報告には**昇格候補の件数と未処理の保留件数**（`node scripts/style-pending-promote.mjs`）を必ず含め、閾値を超えていれば発見モードの実行を推奨する。

#### 発見モードの手順

1. **前処理**：根拠モードと同じスコープ解決に加え、`node scripts/style-evidence-tally.mjs --json` でルールごとの支持記事数を集計し、`node scripts/style-pending-promote.mjs --json` で昇格候補を抽出する。**この2つを manifest へ入れることで、統合エージェントが `evidence/` 全体や `pending/` 全文を読み直さずに済む。**
2. **分析（Workflow・観点ごと4体）**：現行と同じ深さで特徴を抽出する。
3. **反証（Workflow・観点ごと4体）**：Evidence Reviewer が根拠を検証する。
4. **統合（Workflow・観点ごと4体）**：ガイド本体・`evidence/`・`pending/` を更新する。渡すのは**自観点の特徴のみ**（他観点の特徴は渡さない）。
5. **境界レビュー（Workflow・1体・後段）**：書き上がった本体4ファイルを読み、重複・配置の誤りを検出して報告する。**修正はしない。** 重複・配置誤りの解決は「書く前の事前回避」から「書いた後の事後検出」に変わる。検出結果は報告し、修正は次のラウンドまたは個別の指示で行う。
6. **後処理**：`node scripts/style-rule-ids.mjs --write` で追加されたルールへ ID を採番し、`node scripts/style-evidence-tally.mjs` で不整合を確認する。タスクリストの更新、報告。

いずれのモードも、`Workflow({ scriptPath: '.claude/skills/author-style-analyzer/references/analysis-workflow.js', args: <manifest> })` で実行する。manifest の形は `references/analysis-workflow.js` 冒頭のコメントに定義されている（`mode: 'evidence' | 'discover'`）。各ステージの意図・役割の内訳・レビュー観点は `references/collaboration-workflow.md` を参照。

Workflow を使えない環境では、`Agent` ツール（サブエージェント）を同じ順で呼ぶか、単一エージェントの役割切り替えで代替する。いずれの場合も、1つの観点の中では分析が終わるまで反証を始めない。各担当は、自分の対象外の特徴を成果物へ混在させない。

### 4. 反証・境界レビューする

分析（判定）の直後に、その観点の結果を反証エージェントが検証する。境界レビューは**発見モードのみ**で、統合の後段に置いて4ファイル間の責務を横断確認する。

確認項目：

- 単一記事の特徴を一般化していないか
- 一般的な技術記事の特徴を著者固有の癖としていないか
- 根拠の弱い推測を断定していないか
- 他の成果物と内容が重複していないか
- 記事タイプによる条件を落としていないか
- 反例となる記事が存在しないか

意見が分かれた特徴は、無理に採用しない。次のいずれかに分類する。

- 採用
- 条件付きで採用
- 保留
- 棄却

### 5. 根拠と確度を整理する

分析の途中では、各特徴に次を付けて扱う。

- 確度（強い傾向／条件付きの傾向／弱い傾向）
- 支持する記事（slug）と該当箇所
- 対象となる記事タイプ
- 反例の有無
- 事実か推測か

**このうち、ガイド本体に書くのは確度ラベル3語だけである。** 残りは `writing-guides/evidence/<観点>/<slug>.md` にルールIDで登録する。「何記事で確認したか」「なぜその確度なのか」をルール欄・確度欄へ書かない。

そのうえで、根拠・確度の説明に埋もれた**実行可能な制約**（適用範囲の線引き、頻度・分量の上限、記事タイプによる出入り）は、ルール欄・適用条件欄・`使用量` / `変種` / `注意` へ書く。ここを取り違えると、分析側へ根拠を移した時点で執筆側から判断材料が失われる。

記事本文の長い転載は避ける。根拠に添える該当箇所は特徴を確認できる最小限の長さにする。

**確度は導出値であり、`node scripts/style-evidence-tally.mjs` が唯一の正である。** ただし移行で作られた根拠は意図的に不完全で（集約表現の根拠を個別記事へ展開できていない）、**支持記事数が少ないことは根拠が弱いことを意味しない。** 降格を機械的に当てるときは `--round` で今回書き直した記事に関係するルールへ絞る。

### 6. 既存ガイドを差分更新する（発見モードのみ）

根拠モードではガイド本体を触らない（確度の降格を除く）。以下は発見モードの手順である。

既存ファイルがある場合は、**まずその内容を読み、有効な記述は保持する**。全面的に書き直して既存内容を破棄することはしない。新しい分析結果は、既存記述への加筆・修正・調整として反映し、次のいずれかに分類する。

- 既存ルールを補強する（ルール本文は変えず、`evidence/` の当該記事ファイルへルールIDを足す）
- 適用条件を追加する
- 例外を追加する（一般化できる反例は `適用しない状況` へ、記事固有の反例は `evidence/` の `※` 注記へ）
- ルールの確度を下げる／上げる（集計から数え直した記事数・記事タイプの幅に基づく）
- 新しいルールを追加する（**ID は振らない。** 後処理の `style-rule-ids.mjs --write` が採番する）
- 根拠不足のルールを削除する（`evidence/` の全記事ファイルからもIDを外す。**ID は欠番として残す**）
- 保留プール（`pending/`）の保留を本体ルールへ昇格する（支持3記事以上かつ反証も通った場合）
- 主要ルールに満たない観察を保留プールへ1行で追記する／不要になった保留を削除する

**根拠は同じラウンドで更新する。** 新しく分析した記事は `evidence/<観点>/<slug>.md` を作り、`分析時点` に分析した本文のコミット SHA、`記事タイプ` に分類した種別を書く。

**すでに分析済みの記事を再分析する場合は、4観点ともその記事のファイルを丸ごと書き直す**（他の記事のファイルには触らない）。`分析時点` も新しい SHA へ更新する。書き直しで支持記事が減ったルールは確度を再評価する。手順の詳細は `references/output-contract.md`「記事単位の再分析（撤回）」に従う。

保留（held）は本体ではなく保留プールへ書く。本体と保留プールで同じ特徴を重複させない。変更理由が追跡できる形で更新する。

### 7. タスクリストを更新する

分析が完了したら、`writing-guides/STYLE-ANALYSIS-TASKLIST.md` の該当行を更新する。これはスキル層（メインセッションの後処理）の責務で、Workflow のスクリプトや統合エージェントは行わない。

**根拠モードでも `[x]` を付ける**（その記事の分析は完了しているため）。ガイド本体が変わらないことと、記事を分析済みにすることは別である。

- **実際に分析した記事の行だけ**を `- [x] \`/<route>\`` に更新する。スコープに含まれていても draft で除外した記事、解決できずに落とした記事はチェックしない。
- 該当行は現在の表記により次のいずれか。いずれの形でも最終的に `- [x] \`/<route>\`` にそろえる。
  - `- [ ] \`/<route>\``（未分析）→ そのまま `- [x] \`/<route>\`` にする。
  - `- [draft] \`/<route>\``（`draft: true` のため通常は分析対象外。ユーザーが明示的に draft 記事の分析を指示した場合のみ）→ **`[draft]` 注釈を外し** `- [x] \`/<route>\`` にする。
  - 既に `[x]` の場合（再分析）はそのままにする。
- `[ページ未作成]` の行は、そのページが実装されない限り更新しない。分析対象の記事が `[ページ未作成]` のタイトルとしてしか載っていない場合は、行ごと `- [x] \`/<route>\`` に置き換える（タイトル表記をルート表記に差し替える）。
- **該当行を一意に特定できないときは、勝手にタスクリストを更新しない。** ガイドの更新結果は報告しつつ、該当行が見つからない／どの行か確定できない旨を伝え、どう更新するか確認を取る（推測で行を追加・書き換えしない）。
- 記事の追加・公開・draft 解除でリストと実体がずれている場合は、ついでの整合修正としてその行の状態（`[ページ未作成]` → `[ ]`、`[draft]` → `[ ]` など）も直してよい。ただし分析していない記事を `[x]` にはしない。
- 更新したタスクリストはガイド本体・根拠インデックス・保留プールと同じコミットに含める。

## Git履歴の分析

`refine-style.md`を作成または更新するときは、Gitのコミット履歴を使用する。

コミットメッセージを次の規則で解釈する。

- `記事タイトル` と `[ai-draft]` の両方を含むコミット
  - AIによる生成（修正前）。`記事タイトル [ai-draft]`（主に初稿）や `記事タイトル：修正内容 [ai-draft]`（初稿ではないが、AIによる修正しか含まない場合）が該当する
  - 後方互換のため、従来の `記事タイトル：草稿を書かせた` も同じ扱いとする
- 同じ`記事タイトル`で始まり、`[ai-draft]` を含まないその後のコミット
  - 人間による編集

同一記事のコミットを時系列に追跡し、AI草稿から人間による編集までの変更を分析する。

次の変更は、文体上の修正から分離する。

- 誤字脱字のみの修正
- メタデータのみの変更
- リンク更新
- フォーマット整形
- 技術的誤りの訂正
- 記事内容とは無関係なリファクタリング

Git差分を文字単位で列挙するだけで終えず、修正の目的を分類する。

## 出力時の共通ルール

- ガイド本体4ファイルには、分析対象そのものを書かない。記事名・シリーズ名・出現件数・分析を重ねた経緯（「さらに〜シリーズを追加で分析し統合した」など）を、「ガイドの目的」節・節の前書き・ルール欄・確度欄のいずれにも書かない。ガイド本体は「どの記事を分析したか」の記録ではなく再利用可能なスタイルガイドとする。記事単位の記録は `evidence/<観点>/<slug>.md`、更新履歴は分析ログ・作業記録側に保持する（詳細は `references/output-contract.md`）
- ガイド本体に `根拠` 欄・`反例・例外` 欄を作らない。`確度` 欄はラベル3語のみとする
- ルール見出しの `[ID]` を消さない。新しいルールへ手で番号を振らない（採番はスクリプト）
- ルールの実行に必要な制約は、根拠や確度の説明ではなくルール欄・適用条件欄・`使用量` / `変種` / `注意` に書く
- 一般論ではなく、著者固有の特徴を記述する
- 固定テンプレートではなく、条件付きの判断として表現する
- 頻出するだけの表現を機械的に推奨しない
- 反例や適用しない条件を記載する
- 推測は推測であることを明示する
- 根拠のない心理状態を断定しない
- 著者の文章を過度に単純化しない
- 4つの成果物の責務を保つ

## 完了条件

### 両モード共通

- 分析した記事について、`evidence/<観点>/<slug>.md` が4観点分（Git 履歴が無い記事は3観点分）生成され、`分析時点` の SHA が一致している
- 再分析した記事については、当該ファイルが書き直され、他の記事のファイルが変わっていない
- `node scripts/style-rule-ids.mjs --check` と `node scripts/style-evidence-tally.mjs` が不整合を報告しない（本体に存在しないIDが根拠に残っていない・ID未採番のルールがない）
- 分析した記事について、`writing-guides/STYLE-ANALYSIS-TASKLIST.md` の該当行が `[x]` に更新されている（一意に特定できずスキップした行があれば、その旨をユーザーへ確認している）
- 後処理として、変更をファイルシステム上で検証し、ユーザーへ変更内容を報告している

### 根拠モード

- 起動したエージェントが8体以下である
- **ガイド本体4ファイルがエージェントに Read されていない**（確度の降格が発生した場合を除く）
- 確度の降格対象が0件なら、ガイド本体が一切変更されていない
- 完了報告に**昇格候補の件数と未処理の保留件数**が含まれている
- 既存ルールに当てはまらない特徴が `pending/` へ1行で追記されている

### 発見モード

- 4つのガイド本体が作成または更新されている（`evidence/`・保留の増減があれば `pending/` も）
- 各特徴の配置先が適切である（主要ルールは本体、根拠は `evidence/`、保留は `pending/`）
- ガイド本体に `根拠` 欄・`反例・例外` 欄がなく、`確度` 欄がラベル3語のみである
- 追加されたルールへ `style-rule-ids.mjs --write` で ID が採番されている
- 強い傾向と弱い傾向が区別されている
- 記事タイプによる差が反映されている
- **境界レビューの結果が報告されている**（重複・配置誤りの検出結果。その回で直さなかった指摘は次ラウンドへ持ち越すことを明記する）
- 既存ガイドを更新した場合、変更内容が説明できる
