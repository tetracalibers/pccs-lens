# デモ誘導文（`:::Action{fixme}`）の書き直しスキル (refine-action-text)

`:::Action{fixme}` は「AIが書いたまま人手が入っていないデモ誘導文」の印で、著者はこれを簡潔な誘導文へ書き直してから `{fixme}` を外す（→ `writing-guides/syntax-guide.md` ルール4）。このスキルは、その書き直しの**案を出すところ**を担う。

**書くのは案であって確定稿ではない。** 置き換えたあとも `{fixme}` は残り、最後に文面を確定させるのは著者。

## 適用範囲

記事ページに残っている `:::Action{fixme}` の文面の書き直し。

| 記事の種類 | パス |
| --- | --- |
| CG・画像処理 | `app/src/routes/cg/<ユニット>/<slug>/+page.svx` |
| 色の理論 | `app/src/routes/color-theory/<slug>/+page.svx` |
| 色の活用分野 | `app/src/routes/color-fields/<slug>/+page.svx` |

対象外:

- **`{fixme}` の付いていない `:::Action`** — 著者が確定させた文面。読まない・触らない（前後の Action を参考にするのは可）
- **地の文・他のディレクティブ** — `:::Add` / `:::Delete` / `:::Fix` は `/apply-edit-requests`、本文は `/author-style-writer` の担当
- **デモそのもの** — Tweakpane のラベル・初期値・見た目を変えるのは `/add-threejs-demo`（`:::Fix{target="demo"}`）の担当。**合わせるのは Action の側**
- **1回の実行で扱うのは1記事だけ**

## 引数

```
/refine-action-text [<記事>] [<絞り込み>]
```

- **`<記事>`（省略可）** — 次のいずれかで指定できる。省略時はセッションの文脈から特定し、特定できなければユーザーに尋ねる
  - `.svx` のパス（`app/src/routes/cg/basics/area-filling/+page.svx`）
  - URL（`/cg/basics/area-filling/`・`https://.../cg/basics/area-filling/`）
  - slug だけ（`area-filling`）
- **`<絞り込み>`（省略可）** — 対象の Action を絞る指定（行番号・節の見出し・デモのコンポーネント名）。省略時は記事内の全 `:::Action{fixme}` を上から順に1つずつ扱う

### 記事の解決

パス・URL が渡されたら、そのまま（URL は先頭の `/` と末尾の `/` を落として `app/src/routes/<パス>/+page.svx`）に解決する。slug だけなら3ルートを横断して探す。

```bash
find app/src/routes/cg -maxdepth 2 -type d -name "<slug>"
find app/src/routes/color-theory app/src/routes/color-fields -maxdepth 1 -type d -name "<slug>"
```

- **0件なら該当ページが無い旨を伝えて中止する。複数件なら候補パスを提示して確認する。** 推測でどれかに決めない
- **`draft: true` の記事も対象**（公開前の手直しで呼ばれる想定）。`draft` は外さない

## 読むもの

作業前に、次の箇所だけを読む（ガイド全文の通読はしない）。

| 何を | どこ |
| --- | --- |
| `:::Action` と `{fixme}` の規約 | `writing-guides/syntax-guide.md` ルール4の「5.」と、ディレクティブ一覧の `:::Action` の行 |
| `:::Action` の記法（数式・数字） | `writing-guides/math-notation-guide.md`「`:::Action` のテキストではインライン数式を使わない」「数字は必ずインラインコードにする」 |
| 文体（レジスター・一文の畳み方） | `writing-guides/stylistic-quirks.md` の `[SQ-003]`・`[SQ-077]` |
| 置き方・分量 | `writing-guides/writing-style.md` の `[WS-065]`、`writing-guides/refine-style.md` の `[RS-038]` |

## 手順

### 1. 対象の `:::Action{fixme}` を洗い出す

```bash
grep -nE '^:{3,}Action\{[^}]*fixme' <対象ファイル>
```

- ディレクティブは**入れ子のとき外側のコロンが増える**。`:{3,}` で拾い、**閉じは開始行と同じコロン数の `:` だけの行**とみなして範囲を確定する
- **1件も無ければ、書き直す対象が無いことを報告して終わる。** `{fixme}` の無い `:::Action` を代わりに書き直さない
- 引数で絞り込みが渡されていれば、その1件に絞る
- **2件以上あれば、最初に一覧（行番号・属する節の見出し・デモのコンポーネント名）を示してから1件目に入る。** 何件を順に扱うのかを著者が把握できるようにする

  ```bash
  grep -nE '^#{2,3} |^:{3,}Action\{[^}]*fixme' <対象ファイル>
  ```

  見出しと Action を一緒に拾えば、どの Action がどの節に属するかを行番号の前後関係で確定できる

### 2. 案を作るための材料を集める

対象の Action ごとに、次を読む。

- **直前の説明**（その Action が属する節の見出しと、直前の1〜2段落）。**Action は「本文で説明済みのことの観察指示」に限る**ので、ここに無い用語・事実を案に持ち込まない（→ `[WS-065]`）
- **直後のデモ**。`<CanvasWrapper>` / `<SVGWrapper>` の中のコンポーネント名から、`<script>` の `import` で実体のパスを引く
- **デモの操作パラメータ**。`<デモ名>Demo.svelte` の `buildPane` を読む

  ```bash
  grep -nE 'addBinding|addButton|addFolder|options:|ariaLabel' <デモのSvelteファイル>
  ```

  - `label:` の値が画面に出るパラメータ名（`readonly: true` の読み出し欄・`options` の選択肢名・folder / button のタイトルも含む）
  - `ariaLabel` には「何が見えて、何を動かすと何が変わるか」が1文で書いてあることが多い。着眼点の候補になる
  - Tweakpane を持たないデモ（OrbitControls だけ・SVGのクリック操作だけ）もある。その場合は操作＝ドラッグ・ズーム・クリックになり、`:Mark[]` で囲むラベルは無い
- 必要なら `scene.ts` で、そのパラメータを動かすと**画面のどこが**変わるかを確認する

### 3. 案を8つ提示する（4つの型 × 2案）

**この時点でファイルを1文字も書き換えない。**

- **案の前に、どのデモに付く Action なのかを見出しで明示する。** 記事内に Action が複数あるので、どこの話かが一目で分かるようにする

  ```markdown
  ## :WithGroupTag[スキャンライン塗りつぶし]{group="{['CG']}"}（L233・`ScanlineFillDemo`）
  ```

  - **節の見出しはテキストをそのまま写す**（ディレクティブ・属性込み）。省略形に言い換えない
  - 対象が `###` の小見出しの下にあるときは、**上位の `##` から `>` でつないで示す**（例: `## 塗りつぶす領域 > ### スキャンラインの交点`）
  - あわせて Action の行番号とデモのコンポーネント名を添える
  - **今の文面（draft）も引用する。** 何を書き直そうとしているのかを、案と並べて見比べられるようにする
- **次の4つの型それぞれで2案ずつ、計8案を出す。** 型ごとにまとめ、どの型の案かを見出しで示す

  | 型 | 形 | 性格 |
  | --- | --- | --- |
  | 1文集約 | 「〈操作〉と、〈変化〉が〜のを観察しよう」 | 既定。操作と観察を1文に畳む（→ `[SQ-077]`） |
  | 箇条書き | **導入1文＋**観察点3つ（常体・言い切り） | 着眼点が3つ以上あって1文に収まらないとき |
  | 見比べ | 「左の〜と見比べながら、右の〜を観察しよう」 | 2つを並置したデモ、操作の前後を対照させたいとき |
  | 誘導のみ | 「ドラッグして〜を見てみよう」 | 操作パラメータが無いデモ、節末のデモへの誘導。パラメータのあるデモでも、パネルを触る前の一言として書ける |

- **同じ型の2案は、言い換えではなく中身で分ける。** 次のいずれかの軸をずらす
  - **着眼点**（節の主題のうち、どの現象を見せるか）
  - **絞り込みの幅**（1点に絞る／複数を並べる）
  - **操作の入口**（どのパラメータから触らせるか、どこを起点に見るか）
- draft に並んでいる観察点を全部拾い直す必要はない（節の主題と関係の薄い項目は落とす → `[RS-038]`）
- **型が対象のデモに噛み合わないと感じても、8案は必ず揃える。** そのうえで、噛み合わなさを1行の狙いに書いて著者の判断に委ねる（案を減らして代わりに決めてしまわない）
- 各案は**そのまま記事に入る形**（`:::Action{fixme}` の開始行と閉じの `:::` まで含めたブロック全体）で示し、**1行の狙い**（何を見せる案か）を添える
- あわせて次を示す
  - そのデモの Tweakpane ラベル一覧（読者がパネルで探す語がどれかを著者が確認できるようにする）
  - **ラベルと言い方がずれる案**があれば、その旨（例: ラベルは「入力の明るさ」だが案では「丸める前の明るさ」）
  - 判断に迷った点（着眼点が節の主題とずれる、デモに該当する操作が無い、など）
- 選び方は**番号で答えてもらう**（`AskUserQuestion` は選択肢が4つまでなので使わない）。「案3をベースに〜」のような指定を受けたら、直して**もう一度提示し**、承認を得てから置き換える

**承認を得るまで記事を書き換えない。**

### 4. 文面を置き換える

- **置き換えるのはブロックの中身だけ。** 開始行（`:::Action{fixme}`）と閉じの `:::` はそのまま残す。属性が他にも付いていればそれも保つ
- **`{fixme}` を外さない。** AIが書いた文面である限り印は残る（外すのは著者が手を入れたとき → `writing-guides/syntax-guide.md` ルール4）
- 箇条書きの案は、導入文と箇条書きの間に空行を1行入れる
- ブロックとデモ（`<CanvasWrapper>` / `<SVGWrapper>`）の間の空行は1行のまま保つ
- 対象が複数あるときは、**1件ずつ「提示 → 承認 → 置き換え」を回す**。まとめて提示してまとめて置き換えない（案の判断が混ざる）

### 5. 自己チェック

```bash
grep -nE '^:{3,}Action\{[^}]*fixme' <対象ファイル>
(cd app && npx textlint --rulesdir textlint/rules --ignore-path /dev/null src/routes/<...>/+page.svx)
```

- `{fixme}` の件数が実行前と変わっていないことを確かめる
- **置き換えた行に指摘が出ていないことを確かめる**（数字のインラインコード漏れ・ラベル内のインラインコード・インラインコードの前後の空白がここで出る）。出たら文面の側を直す（`--fix` を単発で当てない。自動修正が要るときは `npm run lint:svx:fix`）
- **他の箇所の既存の指摘はこのスキルでは直さない**（記法の整備は `/format-math-notation` の担当）。件数だけ報告に添える
- **`npm run check` は実行しない**（`.svx` だけの変更 → `CLAUDE.md`「品質チェック」）

### 6. 報告する

- 置き換えた Action ごとに、**採用した案の文面全文**と、その位置（行番号・節）
- `:Mark[]` で囲んだラベルと、囲まなかったパラメータがあればその理由
- 案に入りきらなかった着眼点（著者が箇条書きへ足すときの材料になる）
- ラベルと文言がずれている箇所（デモ側のラベルを直す選択肢もあることを添える）
- **`{fixme}` は残してあること**と、著者が文面を確定させたら外すこと
- **コミットはこのスキルではしない。** `/commit-this` に渡す。**文面はAIが書いた下書きのままなので、コミットメッセージは `[ai-draft]` 付き**（例: `画像の量子化：デモの誘導文を書き直し [ai-draft]`）

## 文面のルール

- **文体は casual な意志形**（「〜してみよう」「〜に注目しよう」「〜を観察しよう」「〜を確認しよう」）。本文の丁寧体（です・ます）にしない。**動詞は固定しない**（記事ごとに替わる → `[SQ-003]`）
- **操作と観察を対で書く。** 「デモで確認してみよう」のように、動かす対象も読み取りの中身も無い文にしない（→ `[SQ-077]`）
- **疑問形で閉じない。** 「〜はどう変わる？」のような問い掛けの誘導は案として出さず、誘い掛けの語尾（「〜てみよう」「〜を観察しよう」）で閉じる（`[SQ-077]` は問い形も変種として挙げているが、このスキルでは使わない）
- **短くする。** 1文集約が既定で、1ブロックに操作＋観察の文を3行以上並べない。箇条書きにするのは着眼点が3つ以上になるときだけで、各項は**常体・言い切り**でそろえる（「〜こと」の名詞止めで並べない）
- **箇条書きだけのブロックにしない。** 箇条書きを使う案には、必ず地の文の導入文（何を動かして何を見るのかを示す1文）を先頭に置く。導入文なしで観察点を並べただけの文面は案として出さない
- **1ブロック1着眼点を目安にする。** draft が複数の観察点を詰め込んでいたら、節の主題に効く1つへ絞るか、箇条書きへ割る
- **新しい用語・事実を Action で初出させない。** 記事の地の文で説明済みの語だけで書く
- **前提・限定条件は Action に混ぜない**（それは `:::Note` の担当）

### 記法

- **インライン数式（`$$...$$`）を使わない。** ギリシャ文字も `` `θ` `` のようにインラインコードで書き、添字・分数・行列のように Unicode で書けない式は**日本語に言い換える**（`$$f_s$$` → 「標本化周波数」）。例外のないルール（→ `writing-guides/math-notation-guide.md`）
- **数字はインラインコードにする**（`` `4` ``連結、`` `0.5` ``）。ただし `:Mark[]` / `:Anki[]` のラベルとリンクのテキストの中では囲まずそのまま書く
- インラインコードの前後に半角スペースを置かない
- **`:Anki[]` を書かない**（暗記の穴埋めは本文側で著者が決めるもの）

### `:Mark[]` の付け方

**Tweakpane の UI ラベルとして使われているパラメータ名は `:Mark[]` で囲む。** これは著者の明示的な指示によるもので、「AIは自分から `:Mark[]` を書かない」という一般則（`writing-guides/syntax-guide.md`）に対する、このスキルに限った例外。

- 囲む対象は **Tweakpane のラベル**（操作パラメータ・`readonly` の読み出し欄・`options` の選択肢名・folder / button のタイトル）。Tweakpane を持たないデモでも、画面に出ている操作名・表示名があれば同じ扱いにする
- **囲むのはパラメータ名だけ。** 用語・現象名（`:Mark[擬似輪郭]` のようなもの）はAI側から選ばない。著者が付けた既存の `:Mark[]` は残す
- **表記はラベルどおりにする。** 読者がパネル上で探せることを優先する。ただし**括弧の補足は落としてよい**（ラベル「格子の分割数（1辺）」→ `:Mark[格子の分割数]`）
- ラベルと違う言い方をした案には、**手順3で必ずその旨を添える**
- `:Mark[]` の中にインラインコードを入れない（textlint の `svx-no-code-in-label` に掛かる）。数字を含むラベルはそのまま囲む（`:Mark[4連結で届いた画素]`）

### 書き直しの例

Tweakpane のラベルが「段階の数」「入力の明るさ」「出力の画素値」のデモで、draft が次のようになっている場合。

```markdown
:::Action{fixme}
段階の数と入力の明るさを動かして、次の点に着目して観察してみよう

- 入力の明るさを少しずつ動かすと、出力の画素値が階段状にとびとびに切り替わること
- 同じ画素値に丸められる明るさの範囲が、1つの段の横幅になっていること
- 段階の数を増やすと段の幅が狭くなり、丸める前の明るさとのずれが小さくなること
:::
```

1文集約型の案（3つの観察点を、節の主題である「段の幅と丸めのずれ」の1点へ畳んだ形）。

```markdown
:::Action{fixme}
:Mark[段階の数]を増やすと階段の幅（同じ画素値に丸められる明るさの範囲）が狭くなり、:Mark[入力の明るさ]と:Mark[出力の画素値]のずれが小さくなることを観察しよう
:::
```

## やってはいけないこと

- 手順3の承認を得る前に記事を書き換える
- **`{fixme}` を外す**（外すのは著者。「外して」と明示的に言われたときだけ）
- `{fixme}` の付いていない `:::Action` を書き直す
- 地の文を1文字でも変える（Action に合わせて本文を直さない。合わせるのは Action の側）
- デモの実装（Tweakpane のラベル・初期値・見た目）を変える
- 他のディレクティブ（`:::Todo` / `:::Add` / `:::Delete` / `:::Fix` / `:::Pending` / `::ComingSoon`）を処理する・消す
- パラメータ名以外の語を `:Mark[]` で囲む／既存の `:Anki[]`・`:Mark[]` を外す
- 型を欠かす・1つの型で1案しか出さない（4つの型 × 2案の8案を必ず揃える）
- 同じ型の2案が言い換えになっている（着眼点・絞り込みの幅・操作の入口のいずれかで分ける）
- 疑問形（「〜はどう変わる？」）で閉じる案を出す
- **導入文なしの箇条書きだけで文面を作る**（箇条書きには必ず地の文の導入文を伴わせる）
- `:::Action` にインライン数式・です・ます・新出用語・前提条件を持ち込む
- `draft: true` を外す・フロントマターを変える
- 複数の Action をまとめて置き換える

## 完了条件

- 4つの型 × 2案の計8案を提示し、承認された案で対象の `:::Action{fixme}` の中身だけが置き換わっている
- 文面が箇条書きだけになっていない（箇条書きがあるなら、その前に導入文がある）
- `{fixme}` が実行前と同じ件数だけ残っている
- Tweakpane のラベルとして使われているパラメータ名が `:Mark[]` で囲まれ、それ以外の語は囲まれていない
- 記法パス（`npx textlint --rulesdir textlint/rules`）が、置き換えた行に対して0件
- 地の文・デモの実装・他のディレクティブに差分が無い
