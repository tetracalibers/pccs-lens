# リンク先ページ準備スキル

これから書く記事のキーワード一覧を受け取り、**本文からリンクで関連付けるべきページを洗い出して、リンク先がまだ無いものだけ雛形（`+page.svx`）を起こす**ためのスキルです。

記事本文は書きません。本文の執筆とリンクの差し込みは `author-style-writer` の担当です。このスキルは、その前段で「リンクを張れる状態」を作るところまでを担います。

## 入力

- **キーワード一覧**（必須）: 記事で扱う語を読点・カンマ・空白のいずれかで区切ったもの（例: `不可視, バックフェースカリング, 法線, 内積, Zバッファ法`）。
- **対象記事**（任意）: 記事の slug・日本語タイトル・ルート（例: `hidden-surface-removal-methods`、`/cg/rendering/hidden-surface-removal-methods`）。渡されたら手順 0 で実体を解決する。省略された場合はキーワードだけで進めてよい（記事の特定は分類の精度を上げる補助情報にすぎない）。

## リンク先の状態（4分類の前提）

| 状態 | 実体 | リンクできるか |
| --- | --- | --- |
| 実装済みページ | `+page.svx` に本文がある | できる |
| 雛形ページ | `+page.svx` が `draft: true` ＋ `## TODO` だけ | **できる**（ルートは存在する。既存記事も雛形ページへリンクしている） |
| 下書きリンク | YAML の `sections[].links[]` に `title` だけのエントリ（`CgDraftLink` / `DraftLink`）。ルートが無い | できない → **このスキルで雛形にする対象** |
| 未登録 | どの YAML にも無い | できない（一覧の構成に関わるため、このスキルでは作らない） |

## 手順

### 0. 対象記事を特定する（引数にあれば）

```sh
# slug から実体を探す
ls -d app/src/routes/*/*/<slug> app/src/routes/*/*/*/<slug> 2>/dev/null
# 日本語タイトルから探す
grep -rn "^title: <タイトル>" --include=+page.svx app/src/routes/
```

- 見つかったら frontmatter の `title` と、所属するユニット（`app/src/routes/cg/<ユニット>/` や `color-theory` / `color-fields`）を控える。同じユニットの YAML が、キーワードの主戦場になる。
- 本文がすでにある記事なら、**そのページが既に張っているリンクを控える**（`grep -n '](/' <file>`）。既にリンク済みの先を「新たなリンク先候補」として重複提案しない。
- 0件・複数ヒットのときは推測せず、どの記事かユーザーに確認する。
- **この手順で記事の `.svx` は書き換えない。** 記事側への反映は執筆時（`author-style-writer`）に行う。

### 1. キーワードごとにリンク先候補を探す

キーワード1つずつ、次の2方向で引く。

```sh
# 一覧データ（YAML）に項目として載っているか
grep -rn "<キーワード>" app/src/lib/content-pages/

# 既存ページ（実装済み・雛形どちらも）に現れるか
grep -rln "<キーワード>" --include=+page.svx app/src/routes/
```

検索時の注意:

- **括弧つき表記は分解して両方引く。** `スクリーン（投影面）` なら「スクリーン」と「投影面」、`画素（ピクセル）` なら「画素」と「ピクセル」。
- **複合語は部分語でも引く。** `法線ベクトル` → 「法線」、`スキャンライン法` → 「スキャンライン」。
- **ヒットしたページが「その語を一言使っているだけ」か「その語を主題にしている」かを見分ける。** 主題でないページはリンク先にしない。見出しで判断できる。

  ```sh
  grep -n '^#' <ヒットしたファイル>
  ```

- YAML 側のヒットは、`- title:` 行（下書きリンク）なのか `heading:` / `- slug:` なのかを見る。`title` 行だけのエントリなら分類 C（次の手順）。

### 2. キーワードを4種に分類する

| 分類 | 条件 | 処置 |
| --- | --- | --- |
| **A: 本文で扱う概念** | 記事自身の主題、または記事内で定義・説明される語彙（例: `バックフェースカリング`・`鈍角`・`凹形状`・`物体空間アルゴリズム`） | 別ページにしない。報告で理由を添える |
| **B: 既存ページがリンク先** | 実装済み／雛形いずれかのルートがあり、その語を主題にしている | リンク先として対応表に載せる（リンク挿入は執筆時） |
| **C: 下書きリンクのみ** | いずれかの YAML に `title` だけのエントリがあり、対応するルートが無い | **雛形を作成する**（手順 4） |
| **D: 未登録** | どの YAML にも項目が無い | **報告のみ。YAML へのエントリ新設はしない**（一覧の構成はユーザーの判断） |

分類の指針:

- **A と C の境目**は「単独で1ページ立つ規模か」で見る。記事の説明の途中で定義して終わる語は A、その語を主題に節が組める規模なら C の候補。ただし C は**既に YAML にエントリがあること**が条件なので、エントリが無ければ規模にかかわらず D。
- **数学・前提知識の語**（`内積`・`判別式` など）は、このリポジトリに数学単元が無いため通常 D になる。本文で吸収する想定として報告する。
- 迷ったキーワードは断定せず、手順 3 の表で「A?」「C?」と示してユーザーに判断を仰ぐ。

### 3. 対応表を提示して合意を得る

**雛形を勝手に作らない。** 次の形の表を出し、C の作成対象と slug 案について採否を得る。

| キーワード | 分類 | リンク先／作成予定 | 根拠 |
| --- | --- | --- | --- |
| Zバッファ法 | C | `/cg/rendering/z-buffer-algorithm`（新規） | `cg/rendering.yaml` #hidden-surface の下書きリンク（CG 4-2-5） |
| 画素（ピクセル） | B | `/cg/basics/image-digitization` | 既存ページが主題として扱う |
| 内積 | D | なし（本文で吸収） | どの YAML にも項目が無い |

slug 案の作り方:

- 命名ルールは委譲先スキル（手順 4）と同じ（英小文字ケバブケース・意味を反映・既存の命名に揃える）。
- **兄弟項目は接尾辞を揃える。** 同じ節に並ぶ項目がバラバラの語尾になると一覧が読みにくい（例: 隠面消去の4手法 → `priority-algorithm` / `scanline-algorithm` / `z-buffer-algorithm` / `ray-tracing-algorithm`）。
- 既に同名ディレクトリが無いことを確認しておく。

### 4. 雛形を作成する

合意した C の各項目について、**エントリが載っていた YAML でカテゴリを判定**し、対応するスキルの手順に従って雛形と YAML の置き換えを行う。

| エントリのあった YAML | 従う手順 | 雛形の frontmatter |
| --- | --- | --- |
| `app/src/lib/content-pages/cg/*.yaml` | `create-cg-page` | `group`（行末コメントを `title:` 行に引き継ぐ） |
| `app/src/lib/content-pages/color-theory.yaml` | `create-color-theory-page` | `grades`（`:WithGradeTag` の扱いを含む） |
| `app/src/lib/content-pages/color-fields.yaml` | `create-color-fields-page` | `grades` |

- 複数項目をまとめて処理してよい。ただし**1項目ごとに委譲先スキルの雛形フォーマット（frontmatter の項目・順序・コメントの引き継ぎ）を守る**。カテゴリを跨ぐ場合はカテゴリ単位でまとめる。
- 作った雛形の中身は `## TODO` のまま、`draft: true` のまま残す。**本文は書かない。**
- YAML の `CgDraftLink` / `DraftLink` エントリは `- slug: <slug>` に置き換える（行末コメントは引き継がない。雛形の frontmatter に写してある）。
- 置き換え後、同じ節で行の取り残し（`group:` / `grades:` の残骸）や並びのずれが無いことを確認する。

### 5. タスクリストを追随させる

`node scripts/sync-tasklists.mjs --write` を、**すべての雛形を作り終えてから1回だけ**実行する（項目ごとに繰り返さない）。

```sh
node scripts/sync-tasklists.mjs --write
```

> `Cannot find package 'yaml'` で落ちたら `npm --prefix scripts install` を実行してからやり直す。

- 更新されるのは `ogimage/OGP-TASKLIST.md` と `writing-guides/STYLE-ANALYSIS-TASKLIST.md`。今回の項目の行が `- [ページ未作成] <タイトル>` から ``- [draft] `/<route>` `` に変わる。
- **出力に今回の項目以外の変更が並んだら、それ以前から溜まっていたズレ。** 揃えてしまってよいが、報告で触れる。
- **エラーで終了した場合は1行も書き込まれない。** メッセージをそのまま報告し、**タスクリストを手で書き換えて取り繕わない**。

### 6. 報告する

- **作成した雛形**: ルート・タイトル・どの YAML のどの節から起こしたか。
- **B の対応表**: 執筆時にリンクする先（キーワード → ルート）。本文を書くときにそのまま使えるよう、キーワード単位で示す。
- **雛形を作らなかったキーワード**: A（本文で扱う）と D（一覧に未登録）を分けて列挙し、理由を1行添える。
- **タスクリストの更新結果**（今回以外のズレを含んでいたらその旨）。
- **次のアクション**: 記事本文の執筆と、起こした雛形それぞれの執筆コマンドを列挙する。

  ```
  /author-style-writer <記事slug>
  /author-style-writer <作成した雛形のslug>
  ```

  記事本文へのリンク挿入は執筆時に行われるため、キーワードを織り込ませたい場合は `/author-style-writer <記事slug> <keywords(カンマ区切り)>` が使えることも添える。

## 注意事項

- **雛形は `draft: true` / `## TODO` のまま。本文は書かない。** 執筆は `author-style-writer` の担当。
- **記事本文（`.svx`）をこのスキルで書き換えない。** リンクの差し込みも執筆時に行う。
- **YAML に無いキーワード（D）のエントリを勝手に新設しない。** 一覧の構成（どのユニット・どの節に何を置くか）はユーザーの判断。必要そうなら報告で提案するにとどめる。
- **既存ページ（雛形ページを含む）がリンク先になるキーワードには雛形を作らない。** 同じ主題のページを二重に作ってしまう。
- **表記ゆれ・括弧つき表記・複合語を分解して検索する**（手順 1）。1回の完全一致検索で「無い」と判断しない。
- **対応表の合意を得るまで雛形を作らない**（手順 3）。分類は判断を含むため、勝手に確定させない。
- `scripts/sync-tasklists.mjs` は最後に1回。手作業でタスクリストを突き合わせない。
- `npm run check`（型チェック）は実行しない。触るのは `.svx`・`.yaml`・`.md` だけ。
